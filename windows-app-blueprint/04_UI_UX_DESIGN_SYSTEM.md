# 04. Windows 판매용 앱 UI/UX 디자인 시스템

작성·공식 자료 확인일: 2026-09-26 · 대상: Windows 통합 앱 개발자·디자이너·검수자

[읽는 순서](README.md) · [화면별 설계](05_SCREEN_SPECIFICATIONS.md) · [실행 가능한 정적 시안](prototype/index.html)

> 이 문서는 구현 목표다. 첨부 시안은 화면과 일부 조작을 검토하는 가짜 데이터 기반 HTML이며 설치형 앱, 실제 방송 연결, 결제, 인쇄를 구현한 결과가 아니다. 웹의 기능 보존 기준은 원본 [App.tsx](../src/App.tsx)와 [웹 상세 설계](../docs/replication/02_WEB_DESIGN.md)다. 제품 화면에 개발 용어와 가짜 성공 메시지를 넣지 않는다.

## 1. 제품의 인상과 사용 목적

제품명은 기존 VoiceCAP를 유지한다. 중심 경험은 **방송을 들으며 댓글의 구매자를 확인하고 정확하게 판매를 기록하는 Windows 작업대**다. 판매 업무 중 사용자는 빨리 스캔하고, 한눈에 연결 상태를 확인하고, 의심스러운 판매를 안전하게 보류할 수 있어야 한다.

시각 방향은 밝은 도자기색 바탕, 짙은 남색 내비게이션, 청색 주 작업 버튼, 청록색 정상 상태다. 넓은 여백은 읽기 영역과 입력 영역을 분리하는 데 쓰고, 주문 표 자체는 촘촘하게 유지한다. 큰 제목, 과한 그라데이션, 카드마다 그림자, 움직이는 축하 효과는 라이브 운영 화면에 사용하지 않는다. 상품 사진과 구매자·금액에 시선을 모은다.

최신 디자인 원칙은 다음 공식 자료에서 참고했다. 이에 따른 아래 수치·색·레이아웃은 이 제품에 맞춘 **설계 결정**이며 Microsoft의 의무 규격을 그대로 옮긴 것이 아니다.

| 공식 자료 | 확인한 원칙 | 제품 적용 |
|---|---|---|
| [Windows 11 design principles](https://learn.microsoft.com/en-us/windows/apps/design/design-principles) | 차분함, 익숙함, 일관성, 의미 있는 위계 | Windows 창 조작 유지, 안정된 사이드바, 상태를 색과 문구로 표시 |
| [Fluent 2 design tokens](https://fluent2.microsoft.design/design-tokens) | 원시 값과 의미 토큰 분리, 테마 전환 | 컴포넌트에서 HEX 직접 쓰지 않고 semantic token 사용 |
| [Fluent accessibility](https://fluent2.microsoft.design/accessibility) | 키보드, 초점 복구, 명암 대비, 확대, 의미 구조 | 대비 수치 검사, 다이얼로그 초점 관리, 200% 텍스트 확대 검수 |
| [Windows responsive design](https://learn.microsoft.com/en-us/windows/apps/design/layout/responsive-design) | 재배치·크기 조정·흐름 변경·축약 | 화면 넓이에 맞춰 3영역→2영역→1영역으로 전환 |

## 2. 화면 골격

```text
┌ Windows 제목줄: VoiceCAP · 작업공간                       최소화 / 최대화 / 닫기 ┐
│ 내비게이션  │ 상단: 작업공간 / 현재 회차 / 검색 / 알림 / 연결 센터                  │
│ 220px      ├─────────────────────────────────────────────────────────────┤
│ 라이브     │ 페이지 제목 + 주 작업                마지막 동기화 / 단축키           │
│ 판매       ├──────────────┬─────────────────────┬────────────────────────┤
│ 정산·배송  │ 현재 상품     │ 실시간 댓글           │ 판매 작성 / 근거                │
│            │ 오디오·자막  │ 최신/검색/선택         │ 구매자·단가·수량                 │
│ 규칙·훈련  │ 상품 목록    │ 선택 행 명확히 표시     │ 확정 / 보류 / 최근 기록           │
│ 기기       ├──────────────┴─────────────────────┴────────────────────────┤
│ 설정       │ 하단 상태줄: 댓글 · 음성 · 클라우드 · 프린터 / 미전송 개수 / 버전       │
└────────────┴─────────────────────────────────────────────────────────────┘
```

제목줄은 실 앱에서 OS 기본 창 동작을 유지한다. 커스텀 타이틀바를 쓸 경우 최대화 버튼의 Windows Snap, 드래그, 더블클릭, 시스템 메뉴, 키보드 조작을 별도로 검증한다. 파일 시안의 상단은 로컬 시안임을 표시하는 안내 영역이며 창 버튼을 흉내 내지 않는다.

왼쪽 내비게이션은 작업 단위로 묶는다. `운영`에는 라이브·상품 판매·판매 내역·보류 검토·댓글 기록, `매출 관리`에는 정산·정산서·배송, `운영 설정`에는 인식 규칙·음성 연습·기기 및 연결, 하단에는 구독·내 계정·설정·관리자를 둔다. 관리자 그룹은 서버가 반환한 권한이 있을 때만 보인다.

현재 방송 회차는 페이지가 바뀌어도 상단에 남는다. 작업공간 변경 시 녹음·댓글 스트림·임시 판매·미전송 건수를 먼저 보여 준다. 변경 가능한지 판단한 뒤 진행하며 다른 작업공간의 주문이 섞여 보이지 않도록 캐시 키에 작업공간과 회차를 포함한다.

## 3. 크기와 밀도

수치는 물리 픽셀이 아니라 CSS 논리 픽셀 기준이다. Windows 디스플레이 배율에 따라 실제 물리 크기가 달라지므로 해상도와 배율을 별도로 검증한다.

| 사용 가능 너비 | 내비게이션 | 본문 방식 | 라이브 판매 작성 |
|---|---|---|---|
| 1600px 이상 | 220px 고정 | 3영역, 상품 30% / 댓글 35% / 작성 35% | 항상 보임, 최신 판매 보조 표 추가 |
| 1280~1599px | 204~220px | 3영역, 각 최소 260px, 간격 16px | 항상 보임, 하단 부가 통계 축약 |
| 1000~1279px | 68px 아이콘 레일 | 2영역, 상품은 상단 가로 카드 | 댓글·판매 입력을 나란히 표시 |
| 720~999px | 접힌 메뉴 | 1영역 + `상품/댓글/판매` 탭 | 작성 탭, 선택 구매자 요약 고정 |
| 320~719px | 상단 메뉴 버튼 | 세로 1영역 | 입력 후 주 작업이 아래에 보이도록 배치 |

작은 화면을 위해 기능을 삭제하지 않는다. 보조 필드·통계는 펼치기 또는 상세 화면으로 옮긴다. 판매·댓글의 긴 표는 표 내부만 가로 스크롤할 수 있고, 행 상세에서도 같은 데이터에 접근할 수 있어야 한다. 폼과 주요 업무 동선은 가로 스크롤 없이 사용할 수 있어야 한다.

| 항목 | 표준 | 컴팩트 | 적용 |
|---|---:|---:|---|
| 페이지 바깥 여백 | 28px | 20px | 1000px 미만은 16px |
| 카드 안쪽 여백 | 20px | 16px | 작은 상태 카드 12px |
| 폼 컨트롤 높이 | 40px | 34px | 라이브 확정 버튼은 44px 유지 |
| 표 행 높이 | 52px | 40px | 여러 줄 근거는 자동 높이 |
| 내비게이션 행 | 40px | 36px | 아이콘 18px, 텍스트 14px |
| 영역 간 간격 | 20px | 12px | 입력 라벨~컨트롤 8px |

밀도는 보기 환경만 바꾸며 저장 데이터와 기능을 바꾸지 않는다. 200% 확대에서 강제로 데스크톱 3영역을 유지하지 않는다. 사용자가 지정한 글자 크기가 줄어드는 CSS scale 기법을 쓰지 않는다.

각 상태의 배경은 별도 연한 tint 토큰으로 정의한다. 색만으로 확정/보류/실패를 구분하지 않고 체크/시계/느낌표 아이콘과 문구를 병기한다. 위 HEX는 초안 값이다. 실제 컴포넌트 조합의 일반 텍스트 대비 4.5:1, 큰 텍스트·필수 아이콘 3:1 이상을 릴리스 검수 목표로 측정한다. 비활성 상태는 시각적 흐림만으로 설명하지 않고 이유를 가까이 둔다.

```css
:root {
  --color-blue-600: #2458d6; /* 원시 값 */
  --color-white: #fff;
  --action-primary: var(--color-blue-600); /* 의미 */
  --button-primary-background: var(--action-primary); /* 컴포넌트 */
  --space-1: 4px; --space-2: 8px; --space-3: 12px;
  --space-4: 16px; --space-5: 20px; --space-6: 24px; --space-8: 32px;
}
.sale-confirm { background: var(--button-primary-background); }
```

### 4.2 글꼴과 숫자

외부 CDN 글꼴에 의존하지 않는다. 기본은 `"Segoe UI Variable", "Segoe UI", "Malgun Gothic", system-ui, sans-serif`다. 한국어는 맑은 고딕으로 대체될 수 있으므로 혼합 문장의 높이를 기준으로 검수한다. 추후 Pretendard를 번들에 넣으려면 라이선스·파일 용량·한글 굵기 검수를 거친다.

| 스타일 | 크기 / 줄 높이 | 굵기 | 용도 |
|---|---|---|---|
| Display | 32 / 40px | 650 | 정산의 주요 합계, 남용 금지 |
| Page title | 26 / 36px | 700 | 페이지당 한 번 |
| Section | 17 / 26px | 650 | 카드 제목 |
| Body | 14 / 22px | 400 | 본문·댓글·폼 |
| Label | 12 / 18px | 600 | 필드·열 제목 |
| Caption | 12 / 18px | 400 | 타임스탬프 |
| Amount | 20~28 / 32px | 650 | 작성 합계·상품 가격 |

주요 금액과 표 숫자는 `font-variant-numeric: tabular-nums`를 사용한다. KRW는 소수점 없이 천 단위 쉼표로 표시한다. 단가·수량·합계를 명확히 구분하고, 정산 합계를 `매출 확정액`, 미수 금액을 `입금 대기`로 표시한다. 구매자 닉네임이 길면 한 줄 말줄임만 제공하지 말고 상세 또는 포커스에서 전체 값을 읽게 한다.

### 4.3 모양·깊이·움직임

버튼·입력 반경 8px, 카드 12~16px, 다이얼로그 16px. 작은 배지는 전체 둥근 모양을 사용한다. 일반 업무 카드는 1px 경계선, 떠 있는 메뉴·서랍·다이얼로그만 그림자를 갖는다. 배경 블러는 Windows 비활성 창·저전력·투명 효과 비활성 조건을 고려해 선택적으로 사용하며 글자 아래 과한 반투명을 피한다.

상태 변경 120ms, 메뉴 160ms, 서랍 200ms를 목표로 한다. 실행 완료를 기다리게 만드는 연출은 금지한다. `prefers-reduced-motion: reduce`와 제품의 `움직임 줄이기` 설정은 이동 애니메이션을 제거한다. 계속 흐르는 댓글을 보는 사용자에게는 새 댓글 자동 스크롤의 일시정지를 제공한다.

## 6. 라이브 화면의 우선순위

1. 방송 회차와 연결 상태를 보여 준다. 수집이 멈췄는데 정상 초록불을 남겨 두지 않는다.
2. 현재 상품에 단가·상품번호·이미지·등록 시간을 배치한다. 이전 상품 선택 시 상품을 바꾸는 행동임을 명확히 보여 준다.
3. 댓글 행은 구매자, 원문, 시간, 선택 표시로 구성한다. 최신 댓글이 와도 선택한 행과 작성 내용은 바뀌지 않는다.
4. 판매 작성에는 구매자 근거, 단가, 수량, 합계, 메모를 둔다. 근거가 없는 경우 `구매자 확인 필요`를 표시한다.
5. 확정은 주 버튼 하나로 통일한다. 저장 중 중복 클릭을 막고 서버가 성공했을 때만 `확정됨`으로 전환한다. 대기열에만 저장했다면 `전송 대기`다.
6. 보류는 확정 옆의 보조 버튼이며, 보류 사유를 선택한다. 보류 작업도 저장 결과와 주문 식별자를 보여 준다.
7. 확정 이후 최근 판매를 같은 화면에서 확인한다. 단순 알림만 띄우지 않고 구매자·상품·금액이 일치하는지 검토할 수 있게 한다.

`신뢰도 98%`와 같은 정밀한 값은 실제로 보정·검증된 모델 출력이 있을 때만 보여 준다. 근거 없이 꾸민 수치 대신 `댓글 일치`, `확인 필요`, `후보 2명`을 쓴다. AI 판정과 사용자의 확정은 다른 사건으로 저장·표시한다.

## 7. 통합 댓글 도우미의 사용자 경험

별도 설치 안내를 기본 업무 화면에서 제거한다. 판매자는 앱의 `기기 및 연결 → 댓글`에서 TikTok 계정명, 연결 방식, 재연결 상태, 수집 범위를 관리한다. 창이 하나라고 모든 서비스가 정상인 것은 아니므로 댓글·오디오·STT·클라우드·프린터를 각각 표시한다.

`연결 끊김`은 원인과 다음 행동을 보여 준다. 예: `TikTok 방송이 종료되어 댓글 수집을 멈췄습니다. 방송을 다시 시작한 뒤 연결하세요.` 보안·인증 문제는 무한 재시도하지 않는다. 로그를 공유할 때 사용자명·토큰·댓글·고객 정보의 비식별화 미리보기를 제공한다.

첫 실행은 로그인 → 작업공간 선택 → Windows 마이크/화면 권한 안내 → 댓글 계정 → STT 방식 → 프린터 선택/테스트 → 준비 완료 순서다. 프린터와 Android 기기 연결은 나중에 설정할 수 있다. `권한 허용` 버튼이 실제 OS 권한을 우회해 주는 것처럼 표현하지 않는다.

## 8. 키보드와 초점

| 키 | 기본 동작 | 제한 |
|---|---|---|
| `Ctrl+K` | 명령 검색 | 입력 중에도 동작, 판매 자동 저장 금지 |
| `Ctrl+1 / 2 / 3` | 라이브 / 판매 / 정산 | OS·입력기 충돌 검증 후 사용자 재설정 지원 |
| `Ctrl+Enter` | 현재 판매 확정 | 라이브 작성 영역에 초점, 필수값 유효, 저장 중 아님 |
| `Esc` | 가장 위 임시 화면 닫기 | 저장 중단 여부와 미저장 변경 안내 |
| `Tab / Shift+Tab` | 다음/이전 조작 | 논리 순서: 메뉴 → 페이지 도구 → 상품 → 댓글 → 작성 |
| `Enter / Space` | 버튼·선택 활성화 | 댓글 row는 실제 button/radio 사용 |
| `F1` | 현재 화면 도움말 | 오프라인 도움말 제공 |

기본 `Enter`만으로 금액 입력 중 판매를 확정하지 않는다. 화면 전환 시 H1 또는 새 본문 시작으로 초점을 옮기고, 서랍/다이얼로그를 닫으면 열었던 버튼으로 돌려준다. 모달은 초점을 가두고, 배경은 inert 처리한다. 스크린리더에 모든 신규 댓글을 읽게 하지 않고 선택 상태·수집 상태·요약 개수만 공지한다.

## 9. 필수 예외 상태와 카피

| 상황 | 보여 줄 내용 | 복구 |
|---|---|---|
| 첫 회차 없음 | `아직 시작한 방송이 없습니다` | `새 방송 만들기` |
| 댓글 없음 | `댓글을 기다리고 있습니다` + 연결 상태 | `연결 확인` |
| 검색 없음 | 검색어·필터·0건 | `필터 초기화` |
| 로딩 | 200ms 이후 스켈레톤, 마지막 성공 자료는 유지 | 장기 지연 시 재시도 |
| 오프라인 | `인터넷 연결 없음 · 전송 대기 3건` | 로컬 안전 저장·연결 후 재전송 정책 표시 |
| 서버 확정 여부 불명 | `저장 결과를 확인하고 있습니다` | operationId로 조회, 새 판매로 무작정 재전송 금지 |
| 수정 충돌 | 내 수정과 서버 최신 값을 나란히 | 최신으로 다시 편집 / 허용된 필드만 재적용 |
| 권한 없음 | 필요한 역할과 가능한 읽기 범위 | 재로그인·작업공간 변경 |
| 인증 만료 | `다시 로그인하면 이어서 작업할 수 있습니다` | 임시 입력 보존, 비밀 정보 캐시 금지 |
| 프린터 실패 | 주문은 확정됨 / 출력은 실패함 분리 | 재출력·다른 프린터 |
| STT 모델 없음 | 크기·저장 위치·필요 여유 용량 | 모델 다운로드·다른 엔진 |
| 되돌리기 | 되돌릴 대상과 남은 시간 | 수정 이벤트 생성, 감사 기록 유지 |
| 앱 종료 | 활성 방송·녹음·전송 대기 수 표시 | 트레이 유지 / 저장 후 종료 / 취소 |

삭제·구독 해지·청구·문자 발송은 영향과 대상을 먼저 표시한다. 단순 보기 전환, 필터, 테마 변경에는 확인 다이얼로그를 사용하지 않는다. 오류 메시지는 `원인 + 보존된 것 + 다음 행동` 순으로 작성한다.

## 10. 상용 제품 품질 인수 기준

아래는 출시 전에 실제 구현으로 통과해야 하는 **목표**다. 정적 시안 통과만으로 Windows 앱이 이를 만족했다고 주장하지 않는다.

- 1280×720, 1440×900, 1920×1080에서 100/125/150/200% Windows 배율을 조합하여 확대·잘림·드래그 영역을 검사한다. 실제 유효 너비에 맞춰 다른 레이아웃이 나오는 것은 정상이다.
- 라이트/다크/고대비·표준/컴팩트·움직임 줄이기를 검사한다. 화면색을 강제 지정하는 OS 접근성 모드에서도 경계와 선택 상태가 남아야 한다.
- 모든 주 업무는 마우스 없이 완료 가능해야 한다. 키보드만으로 댓글 선택→수량 수정→보류→상세 수정→확정 과정을 수행한다.
- 긴 한국어 상품명, 40자 닉네임, 0원 정책, 1억 원 이상 금액, 이미지 실패, 1만 건 표, 빠른 댓글 스트림을 검사한다.
- 데이터가 없는 화면에서도 다음 행동이 명확해야 한다. 폼 입력을 한 상태로 다른 화면에 갔다 돌아오면 제품 정책에 맞게 내용이 유지되어야 한다.
- 녹음·댓글 수집·주문 저장의 상태가 서로 일치해야 한다. 프린터 실패가 판매 저장 실패처럼 보이거나 그 반대여서는 안 된다.
- 애니메이션과 가상 목록 때문에 선택 행이 다른 구매자로 바뀌지 않아야 한다. 선택 기준은 배열 인덱스가 아니라 고유 ID다.
- 그림자·색·간격·아이콘 크기를 페이지마다 새로 만들지 않는다. 토큰 변경 한 번으로 전체 적용되는지 검사한다.
- 개발·샘플 모드 배너는 지울 수 없는 별도 환경 표시다. 데모 성공을 실제 결제·발송·판매 성공으로 표현하지 않는다.

## 11. 초보 개발자의 구현 순서

1. 빈 React 프로젝트에 AppShell과 토큰을 먼저 만든다. 서버 연결 없이 화면 너비·테마·초점을 검수한다.
2. Button, TextField, StatusChip, Table, Dialog, Drawer를 만들고 위 상태를 채운다.
3. 가짜 데이터로 라이브 작성 화면을 만든다. 구매자와 상품 선택이 입력값을 어떻게 바꾸는지 먼저 확인한다.
4. 타입이 지정된 서비스 인터페이스 뒤에 실제 API/IPC를 연결한다. 컴포넌트에서 Electron/파일/키에 직접 접근하지 않는다.
5. 저장 처리 상태를 `idle → validating → saving → confirmed | queued | failed | unknown`으로 명시한다.
6. 판매·정산·청구·배송 화면에 동일한 주문 상태 표시를 재사용한다.
7. 전체 화면을 이 문서와 다음 화면 명세의 인수 기준으로 검수한다. 레이아웃이 좋아도 기능 누락이 있으면 완료가 아니다.

정적 시안은 첫 번째부터 세 번째 단계의 대화용 결과물이다. 실제 구현에서는 허용된 IPC, 서버 권한, 저장·재시도 계약, 개인정보 보호를 별도 문서대로 완성한다.
