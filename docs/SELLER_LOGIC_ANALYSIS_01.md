# 판매자 로직분석01

**2026-10-05: 아래 2단계 흐름을 구현했으며 자동 테스트 817개와 웹 빌드가 통과했다. 실제 AI 원문 회귀의 일부 기대 결과가 미충족인 상태를 확인한 뒤, 사용자가 직접 테스트하기 위해 커밋·배포를 요청했다.** 이번 배포는 그 요청에 따른 테스트용 공개이며, 자동 테스트 통과를 AI의 의미 정확도 통과로 간주하지 않는다. 최근 검증과 이전 검증은 문서 뒤에서 구분한다.

관리자 메뉴 **판매자 로직분석01** (`/admin/seller-logic-analysis-01`)은 1차 AI가 판매 발화를 탐지하고 2차 AI가 발화 전후 60초 대화에서 구매자·상품·최종 가격을 연결한다. **판매 적재함**의 결과는 이 분석 화면의 회차에만 존재한다. 기존 판매 장부 DB에는 등록하지 않으며, 화면을 닫기 전에 **결과 내려받기**로 원문과 결과를 JSON으로 보관한다.

## 사용

1. **관리자 → 판매 AI 설정 (보류 해결 · 음성 정정)**에 저장하고 운영 적용한 기존 슬롯 1·2를 그대로 사용한다. 화면의 선택 목록에 실제 공급자와 모델명, 운영 적용 버전이 표시되고 기존 우선 슬롯이 기본 선택된다. 선택한 동일 슬롯이 1차 탐지와 2차 연결을 모두 처리한다. 슬롯 번호와 처리 단계 번호는 서로 다르다.
2. 실시간 방송은 Soniox API 키와 실행 중인 VoiceCAP 댓글 도우미가 필요하다. 기존 청취·댓글 수집을 종료하고 방송 TikTok 아이디를 입력한 뒤 **실시간 청취 시작**에서 방송 탭과 탭 오디오를 공유한다.
3. 저장된 대화는 **대화 텍스트로 분석하기**에 붙여넣거나 텍스트 파일로 연다. 한국 기준 방송 시작 날짜를 선택하고 **대화 자료 적용 → 지금 AI 분석**을 누른다.
4. **판매 적재함**에서 판매 확정 / 대화 진행 중 / 확인 필요 / 취소와 근거 대화를 확인한다. 충분한 근거로 확정된 판매는 바로 표시된다. 연결하지 못한 발화와 확인 중인 발화는 별도 목록에서 시각·내용·인용 원문을 펼쳐 확인한다. 후속 대화가 거래를 정정하면 같은 거래 결과가 갱신된다.
5. 실시간 탐지 주기는 기본 5초다. 자동 분석을 끄거나 **분석 중지**를 누르면 분석을 멈추고 수집된 원문과 완료 결과를 유지한다. 청취를 종료하면 마지막 STT를 받은 뒤 남은 발화를 마감 분석한다. 진행 중인 AI 요청이 있으면 완료 뒤 이어서 실행한다. 다른 방송은 **새 분석**으로 시작한다.

수집한 댓글은 **실시간 댓글** 패널에 닉네임·시각·내용과 함께 표시한다. AI 응답과 관계없이 도착 즉시 갱신하며 최근 200개를 표시하고 전체 댓글은 로컬 원문과 내려받기에 보존한다.

텍스트 입력 형식:

```text
[고객 댓글]
오후 11:59:59 · xou.3z: 저여 맨투맨
[판매자 멘트]
오후 11:59:57 · 맨투맨 가격 18,000원.
오전 12:00:18 · 맨투맨 드릴게요. 엑소 언니.
```

시각은 `오전/오후 h:mm:ss` 또는 `HH:mm:ss`를 사용한다. 각 입력 구역은 시간순이어야 한다. 자정 전후 시각이 함께 있으면 다음 날짜로 연결한다. 두 구역 모두 자정 이후에 시작한다면 방송 시작 날짜에 실제 해당 날짜를 입력한다. 댓글은 첫 `:` 앞이 닉네임이므로 닉네임 자체에 `:`가 있는 자료는 이 텍스트 형식으로 구분할 수 없다.

## AI와 코드의 역할

구매의사 여부, 판매자 확정 여부, 숫자가 상품번호·가격·사이즈 중 무엇인지, 상품 전환, 이전 상품 재요청, 가격 정정과 흥정, STT 호칭과 댓글 닉네임 연결은 모두 AI가 판단한다. `ㅈㅇ`, `저여`, `1`, `6` 등을 코드의 구매 키워드나 정규식 분류기로 판정하지 않는다.

**판매자 선행 발화 기준:** 판매자가 고객에게 상품의 주문 번호를 안내하면 구매 댓글이 없어도 1차 발화로 탐지한다. 예를 들어 “7,000원, 1번”, “그레이 니트 번호 1번”은 발화다. 원단·색상·사이즈·가격만 설명하는 말은 발화가 아니며 숫자가 있다는 이유만으로 주문 번호로 보지 않는다. 판매자의 구매자 배정·확정·협상·정정·취소와 구매자의 구매 요청은 기존처럼 발화에 포함한다.

상품 번호 안내를 탐지한 뒤 아직 구매 요청이나 배정 근거가 없으면 2차는 판매 거래를 만들지 않고 `UNMATCHED`로 반환한다. 화면에서는 **연결 확인 중**으로 후속 댓글을 관찰하고, 관찰이 끝나도 연결하지 못하면 번호 안내의 시각·원문을 **미연결**로 남긴다. 단순 설명으로 오탐지한 후보의 `NOT_SALE`과 구분한다. 뒤늦은 주문과 확정은 기존 번호 안내 신호에 이어 연결한다.

코드는 입력 형식·날짜·크기와 결과 계약을 검증한다. AI가 인용한 댓글/STT ID가 실제 입력에 존재하는지, 닉네임이 인용 댓글의 정확한 원문인지, 수량·가격이 허용된 형태인지 확인한다. 이 검증은 AI의 의미 판단을 대신하지 않는다. 댓글의 emoji, 영문, 기호가 포함된 닉네임을 그대로 반환하며 STT 호칭은 별도 표시한다. 근거가 부족한 이름이나 금액은 미확정 상태로 남겨야 한다.

전체 방송 원문은 브라우저에 보관하며 매 요청에 서버로 다시 보내지 않는다. 1차에는 새로 들어오거나 수정된 원문과 필요한 AI 맥락을, 2차에는 탐지한 발화의 전후 60초 원문과 관련 판단을 제한된 크기로 전달한다. 원문 ID와 수정 이력을 추적하여 늦게 도착하거나 같은 ID로 수정된 STT를 다시 반영한다. 요청 한도로 아직 보내지 못한 원문도 로컬에 보존한다.

1차의 5초는 문장의 종료 기준이 아니다. 신규·수정 원문을 최대 5초·30개·10,000자씩 묶고, 최근 15초의 겹침 원문과 AI가 이어 읽기를 요청한 근거를 함께 보낸다. Soniox의 확정 토큰(`isFinal`)과 발화 종료(`utteranceEnded`)를 구분한다. 종료 신호가 늦어도 중간 조각을 분석하며, 이어지는 조각과 메타데이터 수정은 같은 원문 ID·수정 번호로 추적한다. 경계를 넘어 이어진 말인지, 판매 거래와 관련된 말인지는 AI가 판단한다.

1차 AI는 새 판매 발화와 기존 사건의 후속 가능성을 판단한다. 2차 AI는 구매자·상품·가격·확정 여부와 근거를 판단한다. 거래를 합칠지, 가격을 정정할지도 AI가 결정한다. 코드는 거래 ID로 결과를 합치고 변경하지 않은 이전 거래를 유지한다. 긴 근거 ID를 짧은 별칭으로 전송한 경우에는 응답을 원본 ID로 복원한 뒤 근거를 검증한다.

실시간에서는 발화 뒤 60초가 아직 도착하지 않아도 현재 근거로 연결을 시도한다. 판매 확정 여부와 후속 대화 관찰 여부는 별개다. 화면의 주기적 시각 확인은 로컬 큐를 실행하며, 새 자료나 처리할 마감이 없으면 공급자 요청을 하지 않는다. 후속 자료와 관찰 마감은 엔진이 처리하며, 이미 마감한 발화를 같은 자료로 반복 분석하지 않는다. 저장된 전체 자료는 실제로 60초를 기다리지 않고 원문 시각에 따라 처리한다.

같은 STT 행의 종료 시각이 수정되면 관찰 마감도 갱신한다. 다른 STT 조각이나 구매자 댓글이 기존 거래의 후속으로 탐지되면 새 시각 주변을 읽고 과거의 명시된 근거는 유지한다. 판매자가 오래 연속해서 말해도 동일 발화 묶음 ID만을 이유로 원문 창이 방송 전체까지 늘어나지 않는다. PENDING/REVIEW 거래는 오래 지났더라도 제한된 후속 후보 목록에 포함될 수 있다. 선택하지 못한 과거 후보는 브라우저에 보존한다.

각 AI 호출은 서버 응답 제한 안에서 수행한다. 의미 검수를 매번 추가 호출하는 방식 대신 탐지와 연결의 역할을 분리한다. 계약 오류 교정은 정상 판단 호출과 구분한다. 실패하면 원문·이전 거래·완료된 파이프라인 상태를 유지하고 자동 분석을 멈춘다. 다시 실행하면 마지막 성공 상태에서 이어간다. 완료된 비실시간 자료에서 **지금 AI 분석**을 누르면 기존 거래를 유지하며 탐지 상태를 초기화해 다시 검토한다. 실시간의 조용한 주기에서는 상태를 초기화하지 않는다.

| `supabase/functions/sales-api/handlers/sellerLogicAnalysis.ts` | 관리자 권한, 선택 슬롯 호출, 계약 오류 교정 |
| `supabase/functions/sales-api/handlers/sellerLogicDetection.ts` | 관리자 권한과 기존 선택 슬롯을 사용하는 1차 탐지 요청 |

브라우저의 `analyzeSellerLogic` 입력은 `sessionId`, `slotNumber`, 전체 로컬 `comments`·`transcripts`, `previousDecisions`, 선택적인 `analysisState`·`pipeline`이다. 이 로컬 함수 입력을 그대로 네트워크 요청 본문에 넣지 않는다. 실행 옵션 `live`는 실시간 관찰과 보관 자료 처리를 구분한다. 결과에는 누적 거래와 구매 의사 댓글 ID, 처리 상태와 발화 사건 목록이 들어간다. `pipeline`은 브라우저 상태이며 전체를 서버에 보내지 않는다.

거래 상태 `CONFIRMED`, `PENDING`, `REVIEW`, `CANCELLED`는 AI가 판단한다. 발화 목록에는 `WATCHING`, `LINKED`, `UNMATCHED`, `DISMISSED` 상태와 원문 근거, 연결된 거래 ID, 관찰 마감 정보가 있다. 미연결·확인 중 목록에는 `WATCHING`과 `UNMATCHED`를 표시한다. 거래 결과에는 정확한 원문 닉네임, 원 단위 가격, 수량, 이유와 인용 댓글/STT ID가 포함된다.

`seller-logic-slots`는 기존 `getOperationalAiSetting()`을 통해 운영 적용된 동일 설정을 조회하고 `appliedVersion`, `primarySlot`, 슬롯 번호·공급자·모델만 반환한다. 기존 설정 화면에 미적용 초안이 있으면 실제 운영 버전의 모델을 표시한다. API 키와 연결 설정은 기존 서버 저장값을 사용한다. 슬롯 정보를 읽는 동안이나 조회에 실패하면 분석 시작을 막고 다시 불러올 수 있다.

화면의 분석 작업은 직렬화한다. 처리 중 새 대화가 여러 번 들어오면 다음 작업은 최신 로컬 자료와 직전 완료 상태를 사용해 필요한 요청만 만든다. 진행 결과는 화면과 Soniox 구매자 우선 힌트에 즉시 반영한다. 회차 초기화·페이지 종료·분석 중지는 후속 호출을 막고, 늦은 이전 결과가 새 화면을 덮어쓰지 않게 한다.

## Soniox 닉네임 힌트와 연결 교체

최신 댓글에서 정확한 닉네임을 최대 50명 선정한다. 영문 닉네임은 원문과 한글 발음 힌트를 함께 전달하므로 실제 `context.terms`는 최대 100개다. 발음 변환은 STT 보조 힌트에만 사용하며 구매자 확정에는 쓰지 않는다.

일반 닉네임 목록 변경은 마지막 교체로부터 최소 30초 후 반영한다. AI가 새롭게 구매의사로 판정한 댓글의 닉네임이 현재 STT 힌트에서 빠져 있으면 우선 포함해 교체를 요청한다. 누적 AI 결과에 다시 포함된 과거 구매의사 댓글은 재우선 처리하지 않으며, 새 분석을 시작하면 이 이력을 초기화한다. 이는 AI 응답 이후의 동작이므로 AI 응답 대기 시간이 포함된다.

새 STT 연결을 기다리는 음성은 메모리에 보관한다. 소켓이 열리면 보관 음성을 전달하고, 새 연결의 정상 응답을 확인하면 이전 세션을 종료하며 마지막 토큰을 받는다. 정상 응답까지 보관본을 유지하므로 후보 연결이 실패했지만 기존 연결이 살아 있으면 보관 음성을 기존 연결로 되돌릴 수 있다. 음성 시각은 재전송 도착 시각이 아닌 캡처 시각과 토큰 오프셋으로 계산한다.

연결 대기는 12초, 음성 버퍼는 최대 60초다. 한도 초과 또는 최종 응답 지연에는 경고를 표시한다. 네트워크 오류나 브라우저 종료까지 포함한 무손실 보장은 제공하지 않으며 오디오를 디스크에 영속 저장하지 않는다.

## 한도와 확인 사항

- 방송 전체의 2,000행·450,000자 도달을 이유로 청취를 중지하지 않는다. 요청별 크기 한도와 방송 전체 보관량은 별개다. 화면을 열어 둔 동안 전체 원문을 메모리에 보관하므로 장시간 방송의 실제 수용량은 브라우저 메모리에 영향을 받는다.
- 최근 타임라인 200개만 화면에 보이며, 내려받기에는 전체 근거가 포함된다. 서버에는 각 단계에서 필요한 제한된 원문만 보낸다. 모델 입력 한도나 응답 시간 초과 시 완료 결과와 원문을 유지하고 오류를 표시한다.
- 2차 원문 구간이 32,000자 전송 한도를 넘으면 새 원문을 최대 30개·10,000자씩 나누어 읽는다. 각 요청에 감지 발화·이전 거래·AI가 지정한 문맥의 근거를 보존하고, 전체 원문 처리가 끝나야 해당 구간을 완료한다. 중간 실패 시 1차 탐지 체크포인트부터 2차를 재시도할 수 있다. 단일 원문 한 행이나 필수 근거 자체가 한도를 넘으면 원문을 자동으로 자르지 않고 오류를 표시한다.
- 5초는 기본 입력 처리 주기이며 AI 응답 지연까지 포함한 결과 도착 보장은 아니다. 전후 60초 범위를 넘는 협상, 오래전 상품 재지목, 음성·댓글 전달 지연은 추가 근거가 필요한 사례다. 마감이나 형식 검증만으로 의미 정확도가 보장되지는 않는다.
- 슬롯 호출은 기존 판매 AI의 공통 어댑터와 저장된 연결 설정을 재사용한다. 공급자·모델·API 키를 이 화면에서 다시 설정할 필요가 없다. 기존 어댑터가 반환하는 연결 오류는 분석 오류로 표시한다.
- 본 화면은 관리자 분석 도구다. 판매 장부 DB 저장, 특정 판매자 계정에 대한 판매 커밋, 페이지 재접속 후 회차 복원은 구현 범위에 포함되지 않는다.
- 자동 회귀 테스트는 제공자 응답과 캡처 연결을 대역으로 검증한다. 실제 API 검증은 아래의 별도 유료 스크립트로 수행한다. 생성 음성을 이용한 실제 Soniox 전송 검증과 실제 TikTok 방송·브라우저 탭 공유 검증은 구분한다.

## 실제 Soniox 연결 검증 (2026-10-05)

한국 시각 02:36:52~02:37:16에 실제 Soniox `stt-rt-v5`를 호출했다. Windows 한국어 합성 음성으로 만든 가상 판매 멘트를 운영 `SellerLogicCapture`의 PCM 입력에 공급했으며, 실제 마이크나 고객 음성은 사용하지 않았다. 결과는 `artifacts/soniox-live-validation.json`에 기록되어 있다.

- 음성 21.4249375초, 216개 청크가 실제 WebSocket으로 각각 한 번씩 전송됐다. 최대 대기 버퍼는 28,800바이트(약 0.9초)였다.
- 최초 연결과 닉네임 갱신 2회에 해당하는 세션 3개 모두 `finished:true`를 반환했다. 공급자의 최종 처리 시각은 전송한 전체 음성을 포함하며 프레임 반올림 차이는 각 세션 200ms 미만이었다.
- `u`/`유`, `mint`/`민트` 힌트가 새 연결에 전달됐다. 루비의 가디건 18,000원, 유의 니트 9,000원, 민트의 청바지 20,000원 및 마지막 종료 멘트가 실제 전사 결과에 포함됐다. 정상 완료 실행의 경고는 0개였다.
- 최초 실행에서는 빈 바이너리 종료 프레임 뒤 `finished:true`가 도착하지 않았다. 종료 신호를 [Soniox 공식 예제](https://soniox.com/docs/stt/rt/real-time-transcription)의 빈 텍스트 프레임 `send('')`으로 바꾼 후 다시 실행해 정상 종료를 확인했다.

다음 명령은 실제 유료 API를 호출하는 선택적 통합 검증이다. 한국어 Windows 합성 음성이 설치되어 있어야 한다. `--key-file`에는 Git에서 제외된 키 파일을 지정하며, 대신 `SONIOX_API_KEY` 환경 변수를 사용할 수 있다. 보고서에는 API 키를 기록하지 않는다.

```powershell
powershell -NoProfile -File scripts/generate-soniox-test-audio.ps1
node scripts/verify-soniox-live.mjs --audio-dir scratch/soniox-integration.local --key-file "<Git에서 제외한 Soniox 키 파일>" --output artifacts/soniox-live-validation.json
```

이 검증의 댓글과 오디오 입력 장치는 합성 대역이다. 실제 Soniox 네트워크 연결·전사·사전 교체·버퍼 전송·종료 응답을 검증했으며, 브라우저의 탭 선택/오디오 캡처와 실제 TikTok 댓글 API 연결까지 검증한 것은 아니다. 실방송 소음, 방언, 겹치는 발화의 인식률 및 모든 네트워크 장애에서의 무손실을 보장하지 않는다. 이후의 최근 닉네임 보관 수정은 유료 API를 재호출하지 않고 500개 초과 댓글 후 지연된 AI 구매 판정이 이전 구매자를 다시 포함하는 회귀 테스트로 확인했다.

## 배포된 AI API 검증

`scripts/verify-seller-logic-live.mjs`는 관리자 인증으로 배포된 `seller-logic-slots`, `seller-logic-detect`, `seller-logic-analysis`를 호출한다. 브라우저와 같은 2단계 파이프라인으로 가상 대화를 시간순 재생하며 전체 원문을 한 요청에 보내지 않는다. 실제 운영 적용된 슬롯 1·2의 공급자·모델이 응답과 일치하는지 확인하고, 숫자 주문·흥정·복수 상품 4건을 닉네임·확정 상태·원 단위 가격·수량까지 비교한다. `--soniox-report`를 지정하면 실제 전사 결과의 3건도 두 슬롯에서 확인한다. 모든 행 수가 일치해야 통과하므로 중복 판매도 검출한다. 단계별 요청 크기·소요 시간·실패 시 부분 상태도 기록한다. TypeScript 직접 실행을 지원하는 Node.js에서 실행한다.

실제 유료 AI API를 호출한다. 기존 관리자 세션의 `access_token`을 포함한 Git 제외 JSON 파일을 전달하거나 `SELLER_LOGIC_ADMIN_JWT` 환경 변수를 사용한다. Supabase CLI 관리 토큰은 사용하지 않는다. 스크립트는 계정·AI 설정·판매 장부를 변경하지 않으며, 인증값을 보고서에 저장하지 않는다.

```powershell
node --env-file=.env.local scripts/verify-seller-logic-live.mjs --session-file "<Git에서 제외한 관리자 세션 JSON>" --soniox-report artifacts/soniox-live-validation.json --output artifacts/seller-logic-live-validation.json
```

이 검증은 정해진 가상 거래와 실제 Soniox 전사의 분석을 확인한다. 모든 방송의 AI 의미 정확도와 실제 TikTok 수집을 보장하는 검증은 아니다. 긴 원문과 후속 정정은 별도 사례 검토가 필요하다.

운영 적용 v33의 기존 슬롯을 변경하지 않고 호출했다. 슬롯 1은 `LM_STUDIO / gemma-4-e4b-it`, 슬롯 2는 `DEEPSEEK / deepseek-flash`였다. 실제 호출에는 저장된 동일 모델·연결 설정·키를 사용했다. 플랫폼 댓글 166개와 판매자 STT 500개로 된 제공 자료를 검토했으며, 외부 모델 호출 전 전화번호는 제거했다.

- 짧은 가상 거래의 숫자 주문·흥정·복수 상품과 생성 음성의 Soniox 전사를 두 슬롯에 연결해 구매자와 가격이 일치하는 실행을 확인했다. 이것만으로 긴 실제 대화의 의미 정확도가 입증되지는 않았다.
- 슬롯 1은 가격·치수 문의를 구매 의사나 거래로 오분류했다. 동일 모델의 추가 검수·형식 교정 이후에도 긴 자료의 결과 계약 검증을 통과하지 못했다. 진단용으로 구간을 20개까지 줄여도 문제가 재현됐다. 운영 코드의 구간 크기는 60개로 유지했다.
- 슬롯 2는 성공한 처리 상태에서 재개하여 전체 666개를 12개 구간으로 처리했다. 주요 가격 정정은 확인했지만, 같은 구매자의 앞선 레이스 나시 10,000원 거래와 뒤의 니트 20,000원 거래를 합쳐 나시 20,000원으로 잘못 확정했다. 질문만 있는 거래 후보와 판매자 확답을 놓친 대기도 남았다.
- 원문 근거와 출력 형식을 검증하고 AI가 재검수하더라도, 현재 두 모델의 의미 오류가 모두 제거되지는 않았다. 형식 검증 성공이나 HTTP 200을 의미 정확도 통과로 취급하지 않는다.

따라서 **문제가 없으면 커밋·배포한다는 조건은 충족되지 않았다.** 개선 코드는 작업 폴더에 보존했으며, 이번 검증에서 기존 AI 설정·판매 장부·운영 배포를 변경하지 않았다. 검증용 관리자 세션만 해제하고 임시 키·세션 파일을 삭제했다. 긴 대화의 구매 의사 분류와 상품별 거래 식별을 다시 검증하기 전에는 이 기능을 무문제 상태로 배포할 수 없다.

이전 구현의 웹 빌드는 통과했다. 당시 전체 자동 테스트는 697개 중 696개가 통과했고, 기존 `pre-deployment-integration.test.mjs`의 GPU 모의 측정 테스트 1개가 `SAFE` 대신 `MODERATE`를 반환했다. 해당 모의 측정은 `Math.random()`으로 지연을 생성한다. 변경 없이 해당 파일을 단독 재실행했을 때 18개 모두 통과했으나, 최초 전체 실행의 실패도 함께 기록한다. 최신 2단계 코드의 전체 테스트 결과는 아래에 별도로 기록한다.

## 2단계 구현과 실제 연결 재검증 (2026-10-05)

최신 전체 자동 테스트는 **817/817**, 웹 빌드는 성공했다. 기존 웹 번들의 500kB 초과 경고는 남는다. 1차 탐지·2차 연결, 분절 발화, 수정된 STT 시각, 구매자만의 늦은 응답, 오래 보류된 거래, 관찰 종료, 같은 거래 ID 유지, 입력 분할, 오류 후 재시도, 자동 캡처 장애 종료를 검증했다. 120초 안의 원문 241개를 한 행도 자르거나 빠뜨리지 않고 여러 요청으로 처리하는 테스트를 포함한다.

Soniox를 한국 시각 04:41:12~04:41:36에 다시 호출했다. 생성 음성 21.4249375초·216청크, 연결 3개가 모두 종료 응답을 반환했으며 최대 버퍼 25,600바이트, 경고 0개였다. 최종 전사 6개는 공급자 확정 토큰과 일치했고 시각·발화 경계 정보도 확인했다. 이 실행에서 메타데이터만 바뀌는 동일 ID 수정은 발생하지 않았으며, 해당 경로는 자동 테스트로 확인했다. 상세 기록은 `artifacts/soniox-two-stage-validation.json`이다.

기존 운영 적용 v33의 슬롯 1(`LM_STUDIO / gemma-4-e4b-it`)과 슬롯 2(`DEEPSEEK / deepseek-flash`)를 변경 없이 호출했다. 두 슬롯 모두 실제 Soniox 전사의 루비 18,000원·유 9,000원·민트 20,000원 세 거래를 정확하게 반환한 실행을 확인했다. 슬롯 2는 별도의 짧은 분절 발화·가격 문의·같은 구매자의 다른 상품 사례도 통과했다. LM Studio 요청에는 [공식 JSON Schema 형식](https://lmstudio.ai/docs/developer/openai-compat/structured-output)을 추가했지만, 형식과 근거 검증은 계속 서버에서 수행한다. 설정을 전달했다는 사실만으로 모델 출력의 유효성을 보장하지 않는다.

슬롯 1도 마지막 수정 뒤 같은 짧은 회귀의 공곰 7,000원·나시 10,000원·니트 20,000원을 모두 반환했고 가격 문의를 거래로 추가하지 않았다. 직전의 잘못된 응답을 기존 거래로 오해하지 않도록 교정 지시를 보완하고, 실제 이전 거래가 없으면 D0 같은 예시를 보내지 않도록 수정했다. 반복된 과거 원문은 새 탐지 대상으로 적용하지 않으며, 같은 원문 ID의 수정은 기존 발화 ID를 유지한다.

슬롯 1은 5초 입력 주기에 비해 응답이 길어 처리 대기가 쌓일 수 있다. 이 기능의 요청은 직렬 처리하며 동일 단계의 요청을 무제한 병렬 실행하지 않는다. 단계·공급자별 호출 수, 요청 크기, 시각과 기대 결과 확인은 `artifacts/seller-logic-two-stage-validation.json`에 기록했다. 해당 보고서에는 고객 원문과 인증값을 포함하지 않는다.

슬롯 2의 실제 원문 재생은 댓글 29개와 판매자 멘트 96개, 총 125개를 모두 처리했다. 1차 62회·2차 55회였으며 전체 원문을 한 요청에 보내지 않았고 입력 한도 초과도 없었다. 뒤늦은 니트 20,000원 확정은 기존 거래와 연결했고 나시와 별도 상품으로 유지했다. 다만 나시 10,000원 거래를 가격 미확정 PENDING으로 남겨 기대한 회귀 결과는 통과하지 못했다. 가격 문의도 거래 후보 PENDING으로 남았다. 이전 실행의 가격 문의 오확정과 달리 이 마지막 실행에서는 해당 문의가 CONFIRMED로 남지 않았다.

이는 배포 전 로컬 핸들러에서 실제 공급자를 호출한 검증이며, 새 API의 운영 배포 검증은 아니다. 실제 방송의 일부 시간 구간을 재생했으며 전체 666개 원문 또는 실시간 TikTok·브라우저 탭 캡처의 종합 검증으로 해석하지 않는다. 5초는 기본 탐지 주기이고 실제 표시에는 각 모델의 응답 시간이 더해진다. 소스·거래 ID를 검증하는 코드와 실제 AI의 의미 정확도는 구분한다. 검증 당시 자동 배포 조건은 미충족이었으며 보고서의 `committed:false`·`deployed:false`는 그 시점의 기록이다. 이후 사용자의 명시적인 테스트 요청에 따라 커밋·배포를 진행하며, 알려진 정확도·지연 한계는 그대로 공개한다.
