## 1. 제품 정의와 권장 방향

VoiceCAP은 판매자별 클라우드 작업공간에 Windows PC 여러 대와 Android 휴대폰이 접속하는 라이브커머스 업무 서비스로 설계한다. 방송 수집은 지정 PC 한 대가 담당하고, 나머지 PC는 같은 판매·댓글·판매 멘트·고객·문자·정산·배송 상태를 공유한다.

공유 업무 데이터의 최종 기준은 Supabase PostgreSQL이다. 각 PC의 SQLite는 전송 전 기록 보존, 최근 데이터 캐시, 작업 복구를 담당한다. SQLite 파일 자체를 클라우드에 올려 동기화하는 방식은 사용하지 않는다. 변경 명령과 서버가 확정한 결과를 교환한다.

Windows 앱은 C#/.NET 10 LTS/WPF를 권장한다. 다만 개발의 첫 중심은 공통 클라우드 API와 Android 문자 신뢰성이다. UI 재개발만으로 여러 기기의 일관성이나 문자 발송 신뢰성이 해결되지는 않는다.

## 3. 판매자 A의 실제 사용 구조

| 구성 | 담당 업무 | 동작 원칙 |
| --- | --- | --- |
| 방송 PC | 방송 오디오·화면 캡처, STT, 댓글 수집, 판매 입력 | 현재 회차의 수집 권한을 가진 한 기기 |
| 관리 PC 1 | 판매 검토·수정, 구매자 확인, 고객 문의 | 클라우드의 현재 상태와 수정 이력을 사용 |
| 관리 PC 2 | 정산, 입금 대조, 배송, 문자 작성 | 방송 PC의 실행 여부와 독립적으로 기존 자료 관리 |
| Android 업무폰 | 실제 번호의 SMS/MMS 수신·발송, 촬영·현장 보조 | 클라우드 작업을 받아 수행하고 결과 보고 |
| 출력 PC | 지정 프린터로 전표 출력 | 최초에는 방송 PC 겸용, 이후 별도 지정 가능 |

판매자 A의 모든 PC는 같은 계정으로 로그인할 수 있다. 로그인마다 독립 세션과 설치별 `device_id`를 부여한다. 토큰을 PC 간에 복사하지 않는다. 휴대폰도 같은 계정 또는 일회용 연결 승인으로 같은 작업공간에 등록한다.

`user_id`는 로그인한 사람, `workspace_id`는 판매자 사업 공간, `device_id`는 설치 기기, `session_id`는 방송 회차다. 같은 계정의 여러 PC도 기기별 변경 이력과 연결 해제가 가능해야 한다. 직원 계정은 향후 선택 기능으로 추가할 수 있다.

Supabase는 여러 기기 세션을 지원한다. 운영 설정에서 단일 세션 강제를 사용하지 않고, 기본 로그아웃은 해당 기기만 종료한다. 전체 기기 로그아웃은 별도 기능으로 제공한다. [세션 문서](https://supabase.com/docs/guides/auth/sessions), [로그아웃 범위](https://supabase.com/docs/reference/javascript/auth-signout).

## 4. 권장 기술과 책임 분리

| 구성요소 | 권장 기술 | 책임 |
| --- | --- | --- |
| Windows | C#/.NET 10 LTS/WPF | 방송 장치 제어, 판매 업무 UI, 프린터, 설치·업데이트 |
| PC 저장소 | SQLite | outbox, 최근 데이터, 동기화 커서, 출력 실행 기록 |
| Android | Kotlin 네이티브, Room, WorkManager | 문자·MMS, 영속 작업, 촬영, 모바일 업무 화면 |
| 공통 업무 API | ASP.NET Core | 판매 확정·수정, 권한, 장치 역할, 문자·출력 명령, 과금 검증 |
| 데이터 플랫폼 | Supabase Auth/PostgreSQL/Storage/Realtime | 인증, 공유 원본, 첨부 파일, 기기별 변경 통지 |
| 백그라운드 처리 | API와 같은 코드베이스의 별도 worker | 판매 판단·AI 작업, 재시도, 정리, 사용량 집계, 알림 |
| Android 알림 | FCM | 새 작업 알림·동기화 계기 |
| 운영자 웹 | TypeScript/React | 회원, 구독, 사용량, 장애·기기 현황 관리 |

이는 기존 웹 UI 재사용을 가정하지 않은 기술 제안이다. 백엔드 언어 변경보다 API 계약과 트랜잭션 경계가 더 중요하다. 현재 TypeScript Edge Function을 정비해 동일한 계약을 먼저 구현하는 것도 가능한 이행 경로다. 현재 API를 전부 먼저 C#으로 번역하는 것을 출시의 선행조건으로 두지 않는다.

공통 API는 기능별 모듈을 둔 하나의 서비스로 시작하고, worker만 실행 자원과 생명주기를 분리한다. 판매자마다 별도 서버를 만드는 방식은 기본 구성으로 삼지 않는다. 별도 고객 환경은 용량·계약상 필요할 때 제공한다.

앱과 API는 HTTPS로 통신한다. 방송 PC 내부 STT는 별도 프로세스와 로컬 IPC로 연결한다. 화면 로딩용 localhost HTTP 서버는 필요하지 않다. Supabase Edge Function은 짧은 요청에 쓸 수 있지만, 수시간 방송 연결이나 장기 작업의 생명주기를 맡기지 않는다. [Edge Function 실행 제한](https://supabase.com/docs/guides/functions/limits).

## 5. 저장할 데이터와 소유권

| 자료 | 클라우드 보관 | PC·Android 보관 |
| --- | --- | --- |
| 판매·상품·구매자·정산·배송 | PostgreSQL 원본 및 변경 이력 | 필요한 회차·최근 데이터 캐시 |
| 댓글 | 원문, 플랫폼 메시지·사용자 ID, 회차, 수신 시각 | 업로드 전 대기열과 최근 댓글 |
| 확정 STT 발화 | 별도 발화 테이블, 공급자·모델·오디오 구간·기기·회차 | 전송 전 발화와 실시간 화면 |
| 판매에 사용한 멘트 | 원문과 정정문 구분, 발화 ID와 판매 ID 연결 | 화면에 필요한 근거 캐시 |
| STT 중간 결과 | 실시간 표시 중심, 기본 영구 저장 대상에서는 제외 | 짧은 메모리 버퍼 |
| 판매 캡처·상품사진·MMS | private Storage 파일 + DB 메타데이터 | 업로드 대기 파일·제한된 캐시 |
| 오디오 근거 | 선택한 근거 구간을 private Storage에 저장 | 짧은 순환 버퍼, 업로드 대기 |
| 고객 SMS/MMS | 수신·발신 본문, 첨부, 연결 판매, 처리 상태 | 업무폰의 실제 메시지·처리 기록 |
| 출력·문자 명령 | 서버 작업 ID, 지정 기기, 진행 상태·이력 | 실행 직전·직후 journal |
| 재전송 작업 | 서버에는 수신한 작업과 처리 결과 | 각 기기의 아직 확인받지 못한 outbox |

전체 방송 오디오·영상의 무조건 장기 보관은 기본으로 정하지 않는다. 필요한 증거 구간과 전체 녹화 옵션을 구분해 보관비를 측정한다. 댓글과 확정 발화는 클라우드에 저장하고, 오래된 대용량 기록은 보관 정책에 따라 압축 아카이브와 검색용 색인을 함께 관리할 수 있다.

구매자 신원은 닉네임 문자열만으로 확정하지 않는다. 플랫폼 사용자 ID와 확인된 전화번호 연결을 보관하고, 동명이인·닉네임 변경·복수 주문은 검토 상태로 처리한다. 문자에서 추출한 주소·금액과 판매 기록이 다르면 원문을 보존한 채 차이를 표시한다.

## 6. 동기화와 판매 확정

1. 방송 PC는 오디오·댓글·확정 발화를 수집하고, 업로드할 이벤트와 판매 명령을 SQLite에 먼저 저장한다.
2. 고정된 작업 ID로 공통 API에 전송한다. 재전송해도 작업 ID와 내용은 바뀌지 않는다.
3. 서버는 계정·기기·회차·수집 권한·현재 데이터 버전을 확인한다.
4. PostgreSQL 트랜잭션 하나로 판매, 근거 연결, 수정 이력, 필요한 출력 작업, 처리 결과를 저장한다.
5. 관리 PC와 Android에 변경 통지를 보내고, 각 기기는 해당 변경분을 가져온다.
6. 클라우드 저장 확인을 받은 PC는 로컬 작업을 완료로 표시한다. 확인 응답이 유실되면 같은 작업 ID로 조회·재시도한다.

사용자에게는 `이 PC에 저장됨`, `클라우드에 반영됨`, `검토 필요`를 구분한다. 온라인 판매 확정의 최종 기준은 서버 커밋이다. 공급자별 STT 결과는 하나의 공통 발화 형식으로 바꾸고, 온라인 최종 판매 판단은 공통 서버 규칙을 거치게 한다. PC의 즉시 후보 표시는 가능하되 서버와 서로 다른 규칙으로 최종 판매를 만들지 않게 한다.

동시 수정에는 `expected_revision`을 필수로 사용한다. 서버가 현재 revision과 비교해 조건부 갱신하고 다르면 충돌을 반환한다. 화면 전체 데이터를 일괄 upsert하지 않고 주소 변경·판매 취소·문자 요청처럼 변경 목적이 명확한 명령을 보낸다. 거래 취소와 정정은 원래 거래를 삭제해 숨기지 않고 이력으로 보관한다.

Realtime은 변경을 빨리 알리는 수단이다. 재접속하면 서버가 관리하는 커서로 누락된 변경을 복구한다. 커서는 트랜잭션의 커밋 순서를 반영하는 change log 또는 검증된 동기화 계층에서 발급한다. 단순 기기 시각이나 순번의 최댓값만으로 커서를 만들면 늦게 커밋한 변경을 빠뜨릴 수 있다. 커서 보관 기간이 지났을 때에는 범위별 snapshot을 다시 받는다.

Supabase private Broadcast 채널을 작업공간·회차별로 구성하고 접근 권한을 검증한다. 확정 데이터와 일시적인 자막·장치 상태를 구분해 전송한다. Supabase도 확장성 측면에서 Broadcast를 권장한다. [Realtime 가이드](https://supabase.com/docs/guides/realtime/subscribing-to-database-changes).

## 7. 방송 PC 한 대만 수집하게 하는 방법

회차마다 수집 담당 `device_id`, 만료 시각, 권한 세대 번호를 서버에 둔다. 앱이 수집 시작 시 권한을 획득하고 주기적으로 갱신한다. 다른 PC는 누가 수집 중인지 확인하고 관리 모드로 작동한다.

호스트 변경은 서버에서 원자적으로 처리한다. 새로운 권한 세대가 발급되면 이전 세대의 판매 확정 요청을 거절한다. UI에 방송 버튼을 숨기는 것만으로는 중복 실행을 막을 수 없다. 출력 담당·문자 담당 기기는 수집 담당과 별도로 지정한다.

인터넷 단절 시 기존 방송 PC는 캡처·준비된 로컬 STT·판매 초안을 보관할 수 있다. 클라우드 공유, 새 문자 발송, 서버 승인 전 신규 출력은 대기한다. Soniox 자체 연결까지 끊기면 Soniox 인식은 멈추며, 준비된 로컬 엔진으로의 전환 또는 보관된 음성 복구가 필요하다.

단절 중 다른 PC로 수집 권한이 넘어갔다면 이전 PC의 자료는 복구용 원문으로 수신하고 자동 확정과 구분해 검토한다. 단절된 두 PC가 동시에 최종 판매 권한을 가진다고 가정하지 않는다.

## 8. Soniox와 로컬 STT

실사용 중인 Soniox를 주요 클라우드 경로로 유지하고 로컬 Whisper를 선택 경로로 제공한다. Deepgram은 추가 공급자로 분리한다. 공급자 전환 시 발화 구간·기기·회차·권한 세대를 보존해 중복 판매를 막는다.

Soniox에는 앱이 직접 음성을 전송하고, 자사 API는 사용자 권한·동시 방송·사용량을 검사해 단기 접속키를 발급하는 구성을 우선 권장한다. 장기 키는 서버에만 보관한다. 확정 전사와 필요한 음성 근거는 별도로 자사 클라우드에 저장한다.

단기 키 만료는 새 연결을 제한하며 기존 스트림을 종료하지 않는다. 공식 지원하는 `single_use`, `max_session_duration_seconds`, `client_reference_id`를 함께 활용해 재사용·세션 길이·사용량 추적을 관리한다. 장시간 방송의 재연결과 누락·중복 처리는 별도 검증한다. [Soniox 단기 키 문서](https://soniox.com/docs/guides/temporary-api-keys).

앱이 보고한 사용 시간만으로 정산하지 않고 공급자 사용량과 서버 발급 기록을 대조한다. 직접 연결한 기존 스트림을 즉시 강제 종료할 수 있다고 가정하지 않는다. 즉시 차단이 필수인 상품이라면 상주 스트리밍 중계의 운영비를 따로 평가한다.

## 9. Android 문자 기능을 핵심 출시 조건으로 설정

문자는 `관리 PC 작성 → 클라우드 발송 작업 → 지정 Android·SIM 실행 → 결과 클라우드 반영 → 모든 PC 확인`으로 처리한다. 수신은 `업무폰 수신 → 기기 영속 저장 → 클라우드 업로드 → 구매자·거래 연결 → PC 알림`이다. 방송 PC가 꺼져 있어도 업무폰과 관리 PC가 온라인이면 기존 거래의 문자 업무는 계속되어야 한다.

Android에는 Room 기반의 수신 inbox·발송 journal을 두고 프로세스 종료에도 복구한다. SIM과 실제 발신 번호를 선택·표시하고, 한 번 제출한 작업을 다른 폰으로 무조건 재배정하지 않는다. 문자 외부 ID에는 작업공간·기기 설치 세대·메시지 종류·원본 ID 범위를 포함해 휴대폰 교체나 여러 폰의 같은 로컬 ID 충돌을 막는다.

FCM은 새 발송 작업의 알림·동기화 계기로 사용하고 작업 원본은 DB에서 인증 후 가져온다. 작업 조회·실행은 Android 생명주기에 맞게 처리하며 주기적 재동기화를 보완책으로 둔다. FCM 수신만으로 화면이 꺼진 모든 폰에서 즉시 실행을 보장하지 않는다. 높은 우선순위는 사용자에게 보이는 긴급 알림에 맞게 사용한다. [FCM 우선순위 문서](https://firebase.google.com/docs/cloud-messaging/android-message-priority).

문자 상태는 최소 `대기 → 기기 인수 → 전송 제출 중 → 전송 결과 확인`으로 구분하고, 지원되는 경우 배달 확인을 별도로 기록한다. 긴 문자는 부분별 결과를 합산한다. 전송 직후 앱이 죽어 결과가 불확실하면 확인 필요 상태로 두고 자동 중복 발송을 피한다. 사업용 발송량을 무제한·무료라고 약속하지 않고 실제 회선 조건과 사용량을 확인한다.

대량 판매를 위해서는 배포 방식이 제품 설계의 일부다. Google Play는 기본 SMS 앱 이외에도 휴대폰과 PC 간 문자 동기화를 예외 심사 항목으로 명시하고 있다. 해당 용도에 맞는 완성된 문자 연동 시제품으로 이 경로를 조기에 검증하는 것을 우선 제안한다. 승인은 보장되지 않는다. 예외 승인이 어려우면 실제 기본 메시지 앱 기능을 갖춘 방식 또는 정식 양방향 업무 메시징 연동을 평가한다. 후자는 기존 휴대폰 번호·문자 수신을 그대로 대체하는지 별도 확인해야 한다. [Google Play 문자 권한 정책](https://support.google.com/googleplay/android-developer/answer/10208820).

현재 앱처럼 기본 SMS 역할을 선택하는 구성에서는 메시지 수신·보관·발송 등 기본 기능을 실제로 수행해야 한다. 권한 요청 화면만 추가하는 것으로 완료되지 않는다. 고객용 제품의 첫 현장 검증에 기본 앱 전환, 신규 SMS/MMS, 긴 한글 문자, 답장, 수면·재부팅·네트워크 단절을 포함한다. [Android 기본 핸들러 요구사항](https://developer.android.com/guide/topics/permissions/default-handlers).

## 10. 출력과 문자 작업의 공통 원칙

서버 작업 ID·대상 기기·내용 버전·처리 세대를 고정한다. 작업 claim과 상태 전환은 DB 잠금 또는 조건부 갱신으로 원자적으로 처리한다. PC/Android는 실행 전에 로컬 journal을 남기고, 외부 장치에 제출한 다음 결과를 서버에 보고한다.

DB의 판매 중복 방지와 실제 종이·SMS의 정확히 한 번 실행은 다른 문제다. 프린터와 통신사에 제출한 직후 결과를 잃으면 성공 여부가 불확실할 수 있다. 이 상태를 숨기지 않고 확인 필요로 표시한다. 자동 재시도는 안전하게 실패를 확인한 경우와 제출 전 단계에 제한한다.

관리 PC는 출력·문자를 요청할 수 있지만 실제 실행은 지정 기기가 한다. 지정 기기가 오프라인이면 클라우드 큐에서 대기하고 모든 기기에서 원인을 확인한다. 수정된 판매는 최신 revision의 정정 전표로 연결하며 과거 인쇄·발송 이력을 보존한다.

## 12. 판매 규모와 원가를 고려한 설계

가입 계정 수 외에 동시 방송 수, 판매자별 연결 기기 수, 댓글/초, 확정 발화/초, 이미지 업로드량, 문자 발송량을 계측한다. 예를 들어 활성 클라이언트 1,000대가 2초마다 조회하면 시간당 180만 요청이다. 이는 현재 운영량 측정값이 아니라 단순 용량 산정 예시다.

댓글은 작은 배치로 적재하고 DB에서 batch upsert한다. 페이지별 변경 조회·집계 테이블·회차별 접근·인덱스를 사용한다. 원문을 모든 기기에 매번 전체 재전송하지 않는다. 댓글과 발화의 장기 보관량이 커지면 시간별 파티션과 Storage 아카이브를 검토한다. 파일은 서명 URL로 직접 업로드하고 API가 큰 base64 데이터를 반복 중계하지 않게 한다.

작업 큐는 영속 DB 큐로 시작해 판매자별 처리량과 우선순위를 관리한다. 한 판매자의 댓글 폭주·AI 요청이 다른 판매자의 판매·문자 작업을 막지 않게 한다. Redis·별도 브로커·DB 분할은 실제 병목과 운영 규모를 측정한 뒤 도입한다.

요금제는 작업공간 단위로 구성한다. 여러 관리 PC 사용은 기본 가치에 포함하고, 동시 방송 수·클라우드 STT 시간·AI 사용량·보관 용량 등을 과금 축으로 삼는 것을 제안한다. PC 설치 대수만으로 사용량과 원가를 추정하지 않는다. 결제 승인은 결제사 서버 이벤트로 반영하고, API에서 이용권과 한도를 확인한다.

제품 원가는 STT 시간×단가, AI 호출, DB·Realtime·파일 전송·보관, worker 실행, 메시징, 고객지원으로 구분한다. 공급자별 할당량과 동시 연결 상한은 유료 플랜·계약에 맞게 검증한다. 특정 판매자 수까지 무조건 지원된다고 약속하지 않는다.

운영 환경과 시험 환경을 분리하고 백업·시점 복구·첨부 파일 복원 절차를 검증한다. 일반 판매자는 다른 판매자 데이터를 볼 수 없고, 운영자 지원 접근도 사유·대상·변경 이력을 남긴다. 업데이트는 방송 중 실행 적용을 미루고 앱/API 버전 호환과 DB 마이그레이션 복구를 검증한다.

`HANDOFF.md`에는 2026-09-13 시점의 Supabase 사용량 경고가 기록되어 있다. 이번 검토에서는 현재 청구·제한 상태를 조회하지 않았으므로 출시 준비 단계에서 별도로 확인한다.

## 13. 개발 순서와 완료 기준

| 단계 | 개발 범위 | 통과 기준 |
| --- | --- | --- |
| 1. 공통 기반·문자 검증 | tenant 권한, 독립 기기 로그인, 서버 명령 계약, Android 신규 문자·실제 답장 | PC 두 대와 업무폰이 같은 데이터를 보고, 다른 판매자 자료는 접근 불가 |
| 2. 거래와 작업 큐 | 판매·수정·출력·문자 트랜잭션, 영속 outbox, revision·멱등성 | 동시 요청·응답 유실에서 중복 판매 없고 출력·문자 불확실 상태 식별 |
| 3. Windows 방송 앱 | Soniox, 캡처, 댓글, 수집 담당 lease, 클라우드 발화 저장 | 방송 PC 한 대에서 판매하고 관리 PC에서 댓글·원문·결과를 확인 |
| 4. 전체 업무 | 보류·AI 정정, 정산·입금·배송·문자, 사진·캡처, 선택형 로컬 STT | PC 세 대와 Android의 실제 하루 업무가 이어짐 |
| 5. 유료 출시 | 결제·이용권·사용량, 설치·업데이트, 스토어, 백업·지원, 부하 | 현장 시험과 목표 동시 사용량 검증 후 확대 |

첫 시제품에는 Windows 방송 PC 1대, 관리 PC 1대, Android 업무폰 1대, 실제 프린터를 포함한다. 방송 PC의 판매 한 건이 관리 PC에 나타나고, 관리 PC가 보낸 문자가 휴대폰 번호로 전송되며 고객 답장이 다시 양쪽 PC에 나타나는 흐름을 완성한다. 이어 방송 PC를 종료해도 기존 거래의 관리·문자 업무가 유지되는지 확인한다.

초기 수용 시험은 다음과 같다.

- A계정 PC 세 대 로그인, 한 PC 로그아웃, 다른 PC 업무 유지.
- 판매자 A/B 간 판매·댓글·발화·문자·파일·Realtime·작업 명령 격리.
- 두 PC가 같은 판매를 동시 수정했을 때 충돌과 최신 결과 표시.
- 수집 PC가 끊긴 뒤 다른 PC로 전환하고 이전 PC가 돌아왔을 때 중복 판매 방지.
- 같은 판매 명령 10회 재전송·동시 전송, DB 처리 직후 응답 유실, 부분 실패 복구.
- 정상·잘못된 회차 댓글, 댓글 적재 오류, 100건 이상 수신 누적과 재연결 복구.
- 판매와 무관한 확정 발화까지 다른 PC에서 회차별 조회, 캡처·정정 근거 연결.
- PC 앱 종료·재시작·업데이트 뒤 SQLite 대기열 복구와 계정별 로컬 데이터 분리.
- 출력 제출 직전·직후 종료에서 자동 중복 출력 방지와 UNKNOWN 표시.
- Android 잠금·절전·재부팅·네트워크 단절·SIM 변경·긴 한글 SMS·MMS 첨부·답장.
- 문자 제출 직후 앱 종료와 서버 ACK 유실에서 중복 발송 방지·불확실 상태 표시.
- Android 스토어 권한·실제 배포 검증과 필요한 기본 SMS 기능 점검.
- 실제 방송 8시간 및 단계별 10/100/1,000 동시 방송 부하 목표 시험. 숫자는 개발 목표이며 현재 처리 능력의 주장과 구분.

## 14. 이행 원칙

새 앱과 기존 클라이언트가 잠시 공존하더라도 거래 생성·출력·문자 실행의 책임은 작업공간별로 하나의 경로에 둔다. 클라우드 작업 큐로 전환한 작업공간에서 구형 로컬 자동 출력 경로를 함께 실행하지 않는다.

API·스키마·계약 테스트를 먼저 맞추고 읽기 비교, 제한된 시험 판매자, 단계적 전환으로 진행한다. 저장되지 않은 과거 브라우저 메모리의 전사 기록은 새 시스템이 자동 복구할 수 없으므로 실제 보존 자료와 복구 불가능한 자료를 구분한다. 기존 판매·댓글·고객·정산·문자·첨부 데이터는 이행 검증의 입력으로 사용한다.

최종 출시 판단은 화면 완성도와 함께 여러 기기의 동시 작업, 실제 문자 왕복, 거래 기록 보존, 장애 복구, 판매자별 원가를 기준으로 한다.
