# 판매 보류·음성 정정 AI 구현용 에이전트 지시문

이 문서는 [PLAN.md](PLAN.md)의 구현을 여러 작업으로 나누어 다른 코딩 에이전트에게 맡길 때 사용하는 복사본이다. 각 작업은 앞선 번호의 작업이 완료되어 기본 브랜치에 반영됐다는 전제다. 여러 작업을 동시에 실행하면 DB 스키마·공통 타입·서버 라우팅 충돌이 생길 수 있으므로 순서대로 진행한다.

모든 작업 지시문에는 다음 공통 규칙을 적용한다.

- 먼저 현재 코드와 기존 미커밋 변경을 검토한다. 사용자가 만든 변경을 덮어쓰거나 되돌리지 않는다.
- [PLAN.md](PLAN.md)를 구현 기준으로 사용한다. 계획과 현행 코드가 충돌하면 실제 동작·마이그레이션 상태를 확인하고, 임의로 요구사항을 약화하지 않는다.
- API 키·토큰·원문 민감정보를 브라우저 또는 브라우저 로컬 저장소에 저장·반환·로그로 남기지 않는다.
- AI 결과는 판매 데이터에 직접 쓰지 않는다. 서버 검증과 판매 revision 확인이 끝난 결과만 반영한다.
- 변경에 필요한 테스트를 추가하고, 관련 테스트·타입 검사·빌드를 실행한다. 실패가 기존 문제라면 원인과 영향을 구분해 보고한다.
- 완료 보고에는 변경 파일, 동작, 테스트 결과, 다음 작업에 제공해야 할 API·데이터 구조를 포함한다.

## 작업 1 — 관리자 AI 설정·비밀정보·기초 데이터

> [PLAN.md](PLAN.md)의 8번 개발 순서 중 1단계를 구현하세요.
>
> 관리자만 판매 보류·정정 AI의 1번과 2번 슬롯을 설정할 수 있게 만드세요. 각 슬롯은 활성화 여부, 우선순위, 자체 운영/클라우드 유형, 공급자·엔진, 모델명, 실행 위치, 요청 경로, API 주소, 제한 시간을 저장해야 합니다. 자체 운영 LLM은 같은 PC, 내부망, 외부 IP/도메인을 지원하고 요청 경로는 서버 직접 또는 지정 PC 도우미 경유입니다.
>
> 클라우드 API 키와 서버 직접 호출 자체 운영 LLM의 인증정보는 서버 전용 비밀 저장소에 보관하세요. 브라우저에는 설정 여부·마스킹 정보만 반환하세요. 기존 STT 키 전달 방식을 그대로 복제하지 마세요.
>
> 설정 초안 저장과 운영 적용을 구분하고, 설정 버전을 도입하세요. 변경·폐기된 설정에 의해 진행 중 작업이 잘못 적용되지 않도록 필요한 상태를 설계하세요. 기존 `voicecap-onboard`의 관리자 권한 검증 구조를 재사용하거나 동등한 서버 권한 검증을 구현하세요.
>
> 이 단계에서는 모델 호출, 건강 점검, 자동 전환, 판매 보류·정정 반영은 구현하지 마세요. DB 마이그레이션, 서버 API, 관리자 설정 UI, 타입과 테스트까지만 구현하세요.

## 작업 2 — LLM 어댑터와 공통 분석 규격

> [PLAN.md](PLAN.md)의 8번 개발 순서 중 2단계를 구현하세요.
>
> 범위는 자체 운영 LLM 어댑터와 클라우드 LLM 어댑터, 그리고 두 경로가 공통으로 사용하는 요청·응답 규격입니다.
>
> - 자체 운영 LLM은 같은 PC, 내부망, 외부 IP/도메인 서버를 모두 지원해야 합니다.
> - 호출 경로는 서버 직접 호출과 PC 도우미 경유를 구분하세요. 외부 IP 서버는 PC 도우미 없이 서버에서 직접 호출할 수 있어야 합니다.
> - 클라우드 LLM은 서버 전용 비밀정보로 호출하고, 브라우저에 API 키를 내려보내지 마세요.
> - 두 어댑터는 같은 구조화된 결과를 반환해야 합니다: 처리 가능 여부, 판매 후보 ID, 변경 전후 값, 근거 ID, 부족한 정보, 충돌 사유.
> - 외부 주소의 인증·TLS·주소·포트·기본 경로를 검증하고, 임의 내부 주소 접근과 리디렉션을 막으세요.
> - 아직 보류/정정 결과를 실제 판매 데이터에 반영하거나, 1번→2번 자동 전환을 구현하지 마세요. 그것은 다음 단계입니다.
> - 자체 운영 LLM의 PC·내부망·외부 IP/도메인 경로와 클라우드 경로에 대한 테스트를 추가하고 실행하세요.

## 작업 3 — 건강 점검과 모델 가용성 상태

> [PLAN.md](PLAN.md)의 8번 개발 순서 중 3단계를 구현하세요. 작업 1·2에서 만든 설정과 공통 LLM 어댑터를 사용하세요.
>
> AI 슬롯별 건강 점검과 상태 전파를 구현하세요. 상태는 최소 `미설정`, `점검 중`, `준비 중`, `사용 가능`, `지연`, `사용 불가`, `복구 시험 중`, `상태 만료`를 지원해야 합니다.
>
> 점검은 다음 세 단계로 구분하세요.
>
> 1. 실제 요청 경로에서의 연결·DNS·TLS·인증 확인
> 2. 모델 접근·설치/로딩/메모리 상태 확인. 원격 서버가 관리 API를 제공하지 않으면 `조회 불가`로 표시하고 장애로 단정하지 않음
> 3. 판매를 변경하지 않는 합성 정정 문장으로 구조화 응답·정답·지연을 검증하는 실제 추론 시험
>
> 합성 시험은 적어도 다음을 포함하세요: `0.9가 아니고 1.2입니다`의 기존/새 금액 구분, `xxx님이 아니시고 ooo님`의 기존/새 구매자 구분, 복수 후보에서 임의 선택 금지, 부정 명령의 미실행, 분리 발화의 미완성 상태.
>
> PC 도우미 경유 경로는 기기별 상태를 관리하고, 서버 직접 호출 외부 IP/도메인 경로는 PC 도우미가 종료돼도 영향을 받지 않게 하세요. 건강 상태는 요청 경로·실행기·주소·모델·인증 범위·설정 버전별로 분리하세요.
>
> 관리자 UI에 수동 연결 시험·실제 처리 시험·전체 점검을 추가하세요. 아직 보류·정정 작업의 자동 전환이나 판매 데이터 반영은 구현하지 마세요.

## 작업 4 — AI 작업 대기열과 1번→2번 자동 전환

> [PLAN.md](PLAN.md)의 8번 개발 순서 중 4단계를 구현하세요. 작업 1~3의 AI 설정, 어댑터, 건강 상태를 사용하세요.
>
> 서버 중심의 AI 작업 관리자와 보류/정정 분석 작업 대기열을 구현하세요. 각 작업은 작업 ID, 판매 ID, 판매 revision, 설정 버전, 근거 스냅샷 버전, 현재 유효 시도 ID를 가져야 합니다.
>
> 슬롯 1을 먼저 시도하고, 연결 실패·도우미 종료·DNS/TLS/인증 오류·모델 로딩 실패·메모리 부족·한도 초과·서버 오류·시간 초과·빈 응답·잘못된 구조에서는 동일 작업을 슬롯 2로 자동 전환하세요. 정상 응답이지만 근거 부족인 경우는 장애가 아니며 보류 유지·추가 자료 대기입니다.
>
> 시작 제한 시간은 설정 가능하게 하고, 기본 제안값인 연결 3초·자체 운영 분석 20초·클라우드 분석 15초를 초기값으로 사용하세요. 슬롯 1이 일시 장애 2회면 30초 동안 우회하고, 복구 시험을 연속 2회 통과하면 다음 새 작업부터 다시 슬롯 1을 사용하세요. 이 수치는 설정 또는 상수로 한곳에서 관리하세요.
>
> 슬롯 2로 전환할 때 슬롯 1 결과의 적용 권한을 즉시 만료시키세요. 늦게 도착한 슬롯 1 결과가 판매에 반영되거나 전표를 만들면 안 됩니다. 두 슬롯 모두 실패하면 작업과 기존 판매값을 보존하고 재시도 대기 상태로 두세요.
>
> 이 단계에서는 AI 분석 결과를 판매 데이터에 실제 적용하지 마세요. 작업·시도·상태·전환 이력과 관리자/메인 화면에 표시할 조회 API까지만 구현하세요.

## 작업 5 — 자동 적재 판매 보류 해결

> [PLAN.md](PLAN.md)의 1-A와 8번 개발 순서 중 5단계의 `판매 보류` 범위를 구현하세요. 작업 1~4의 AI 작업 관리자와 공통 분석 결과를 사용하세요.
>
> 자동 적재 판매의 보류 사유를 구조화해 저장하고, 원본 발화·인식 시각·관련 댓글 ID·상품·가격·수량·화면 캡처 근거를 보존하세요. 하나의 판매에 여러 보류 사유가 있을 수 있어야 하며 일부 해결로 다른 사유를 지우면 안 됩니다.
>
> 기존 규칙을 먼저 사용해 닉네임 오인식, 끝번호 유일 일치, 금액 누락, 분리 발화, 지연 댓글을 해결하세요. 해결되지 않은 경우에만 AI 작업을 생성하세요. 새 댓글·후속 발화·판매자 후보 선택이 들어오면 해당 보류 작업만 새 근거로 재분석하세요. 동일 근거 스냅샷으로 반복 호출하지 마세요.
>
> AI 결과는 실제 댓글/구매자 존재 여부, 같은 판매자·회차, 상품 연결, 가격·수량 근거를 서버에서 검증한 뒤에만 반영하세요. AI가 만든 닉네임이나 추정 금액만으로 보류를 해제하면 안 됩니다.
>
> 보류 해제·보완 저장·변경 이력·필요한 출력 작업은 판매 revision을 확인하는 하나의 서버 확정 처리로 만드세요. 사용자가 직접 수정했거나 판매 revision이 바뀐 경우 오래된 AI 결과는 적용하지 마세요.
>
> `남은 보류 건 일괄 확정`은 필수 값과 근거 검증을 통과한 판매만 확정하도록 변경하세요. 미확인 값이 남은 판매는 보류를 유지하고 남은 사유를 반환하세요.
>
> 이 단계에서는 판매자의 음성 정정 요청 처리는 구현하지 마세요. 다음 작업 범위입니다.

## 작업 6 — 음성 정정과 정정 보류 해결

> [PLAN.md](PLAN.md)의 1-B와 8번 개발 순서 중 5단계의 `정정 보류` 범위를 구현하세요. 작업 5의 보류·근거·서버 확정 구조를 재사용하세요.
>
> 일반 판매 추출보다 음성 정정 의도를 먼저 판단하세요. `아니고`, `아니시고`, `정정`, `잘못 말씀드렸네요`, `변경하겠습니다` 등을 문맥과 함께 분석해 정정 항목, 기존 값, 새 값, 대상 지칭, 적용 범위, 근거 발화를 추출하세요.
>
> 아래 예시를 정확히 처리해야 합니다.
>
> - `가격이 0.9가 아니고 1.2입니다` → 기존 9,000원, 새 12,000원
> - `좀전에 판매한거 xxx님이 아니시고 ooo님께 판매하겠습니다` → 기존 구매자 xxx, 새 구매자 ooo
> - `1.2로 변경하지 마세요`와 질문은 수정 명령으로 실행하지 않음
>
> 정정 대상은 같은 판매자·회차의 상품번호, 기존 구매자, 기존 금액, 앞뒤 발화, 판매 시각으로 찾으세요. 마지막 판매 한 건이라는 이유만으로 수정하면 안 됩니다. 후보가 여럿이면 별도 `정정 보류` 요청을 저장하고, 이후 `12번이요` 같은 후속 발화를 기존 요청에 안전하게 연결해 다시 분석하세요.
>
> 정정 보류 중에는 기존 판매값을 유지합니다. 저장 전 판매 초안은 수정 후 한 번 저장하고, 이미 저장·확정된 판매는 동일 판매 ID에 정정 이력을 추가하는 조건부 갱신으로 처리하세요. 닉네임 변경은 실제 댓글 또는 등록 구매자의 고유 ID와 연결한 뒤 적용합니다.
>
> 단가·수량·총액을 일관되게 유지하고, 특정 판매의 정정과 상품의 향후 가격 정정을 구분하세요. 적용 범위가 불명확하면 범위를 확인하는 보류로 남기세요. 다른 주문·고객 정보·과거 판매를 임의로 바꾸거나 신규 판매를 중복 생성하면 안 됩니다.
>
> `방금 수정한 거 취소`는 판매 삭제와 구분하세요. 미적용 정정은 취소하고, 적용된 정정은 이력을 남기는 복원 처리로 구현하세요. 결제·출고 등 후속 처리와 충돌하면 자동 복원하지 말고 확인 대상에 남기세요.
>
> 이미 출력된 판매를 정정하면 같은 판매번호의 새 revision으로 수정 전표를 한 번만 만들고, 수정 전표임을 표시하세요.

## 작업 7 — 판매자·관리자 화면과 운영 완성

> [PLAN.md](PLAN.md)의 6번과 8번 개발 순서 중 6·7단계를 구현하세요. 작업 1~6의 API와 상태를 사용하고, 서버 핵심 규칙을 UI에 중복 구현하지 마세요.
>
> 메인 라이브 화면 상단에 `보류·정정 AI` 상태를 표시하세요. 실제 현재 작업에 사용 중인 번호를 정확히 보여줘야 합니다. 예: `AI 1번 · 로컬 · 사용 가능`, `AI 1번 → 2번 전환 중 · 응답 시간 초과`, `AI 2번 · 클라우드 · 대체 처리 중`, `AI 사용 불가 · 보류 3건 재시도 대기`.
