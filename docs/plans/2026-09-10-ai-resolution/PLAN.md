**1. 적용 범위와 기본 동작**

- 판매 적재 보류와 음성 정정 보류에 동일한 AI 처리 체계를 적용한다.
- 기존 규칙으로 판매 대상과 값을 명확하게 결정할 수 있으면 바로 처리한다. 해결되지 않는 건을 AI 작업으로 등록한다.
- 관리자가 두 개의 AI 슬롯을 설정한다. 1번이 우선, 2번이 대체이며 순서는 변경할 수 있다.
- 각 슬롯은 로컬 LLM 또는 클라우드 LLM을 선택할 수 있다. 기본 구성은 1번 로컬, 2번 클라우드로 제안하며 역순도 지원한다.
- 여기서 로컬 LLM은 직접 운영하는 모델을 뜻하며, 실행 위치는 판매자 PC·내부망 서버·외부 공인 IP 서버·도메인 서버 모두 가능하다. 모델 유형과 네트워크 접속 방식은 별도 설정으로 관리한다.
- AI는 수정 제안과 근거를 반환한다. 판매 반영은 공통 서버 검증을 거친다.
- 정정 보류는 기존 판매 상태와 별도로 저장한다. 해결 전에는 기존 판매값을 유지하고 정정 요청을 보존한다. 남은 원래 보류 사유를 자동으로 없애지 않는다.
- 정상 응답의 '자료 부족'과 모델 장애를 구분한다. 두 모델 모두 사용할 수 없으면 보류 작업을 보존하고, 일반 판매 적재는 계속한다.

기본 처리 순서: 보류 등록 → 근거 수집 → 1번 가용성 확인 → 1번 분석 → 실패 시 2번 분석 → 근거·판매 버전 검증 → 보완 또는 정정 저장 → 합계·출력 반영.

**1-A. 자동 적재 판매의 보류 해결 규칙**

판매 적재는 계속 진행하면서 보류 원인을 별도로 기록한다. 원인은 한 건에 여러 개 존재할 수 있고, 일부 값이 해결되더라도 나머지 원인은 유지한다. 현재 상태 하나나 메모 문자열만으로 원인을 판단하지 않도록 한다.

| 보류 원인 | 확인 자료·처리 | 자동 해결 조건 |
|---|---|---|
| 닉네임 미추출·오인식 | 판매자의 발화, 앞뒤 문장, 같은 회차의 실제 댓글 닉네임과 고유 ID 비교 | 실제 구매자 후보가 한 명으로 특정되고 해당 판매와 연결되는 근거가 있음 |
| 끝번호만 인식 | 같은 회차 댓글·확인된 구매자 정보의 끝번호 및 식별자 대조 | 일치 후보가 한 명이고 발화의 주문에 연결됨; 후보가 여럿이면 보류 |
| 금액 누락 | 앞뒤 발화와 판매 당시 연결된 상품·가격·수량 스냅샷 확인 | 해당 주문의 가격과 수량이 명확하며 단가·총액을 구분할 수 있음 |
| 여러 문장으로 나뉜 발화 | `러블리님 구매확정` 다음의 `가격 일점칠` 등을 같은 주문 문맥으로 연결 | 다른 주문으로 넘어가지 않았고 두 발화의 대상이 같다는 근거가 있음 |
| 댓글 지연 | 새 댓글 도착 후 관련 보류 건의 구매자 검증 재실행 | 늦게 도착한 실제 댓글로 대상이 명확해짐 |
| 복수 후보·가격 충돌 | 후보와 충돌 근거를 정리하고 부족한 정보 표시 | 판매자 추가 발화·후보 선택 등으로 충돌이 해소될 때 반영 |

숫자 가격 변환·명확한 끝번호 대조 등은 기존 규칙을 먼저 실행한다. AI에는 해결되지 않은 항목과 필요한 주변 자료를 전달한다. AI가 제시한 자신감 점수만으로 자동 확정하지 않는다. 실제 댓글/구매자 존재 여부, 판매자·회차 범위, 가격 근거, 상품 연결을 서버에서 확인한다.

원본 전사와 인식 시각, 댓글 ID, 판매 당시 상품·가격·수량을 보존한다. 기존 화면 캡처가 연결돼 있으면 근거 보기에서 접근할 수 있게 한다. 잘못 인식된 값을 고쳐도 원본을 새 값으로 덮어쓰지 않는다. 근거가 없는 값을 만들어 빈칸을 채우지 않는다.

새 댓글·후속 발화·판매자 후보 선택이 들어오면 관련 보류 작업에만 근거를 추가하고 재검증한다. 근거 스냅샷이 같으면 같은 분석을 반복 호출하지 않는다. API 장애 재시도와 추가 자료에 따른 재분석을 구분한다.

판매 카드에는 `AI 확인 중`, `AI 보완 완료`, `판매자 확인 필요`를 기존 판매 상태와 별도로 표시한다. `금액 미확인 → 17,000원 / 후속 발화에서 확인`처럼 보완 내용과 이유를 제공하고 `근거 보기`, `후보 적용`, `되돌리기`를 제공한다. 필수 값과 모든 보류 사유를 검증한 후에만 판매 보류를 해제한다.

현재 화면의 `남은 보류 건 일괄 확정`도 필수 값·구매자·근거 검증을 통과한 건만 확정하도록 변경한다. 미확인 값을 남겨 둔 채 상태만 확정으로 바꾸지 않는다. 통과한 건수와 남은 보류 사유를 보여준다.

첫 적용 범위는 닉네임 보정, 늦게 도착한 댓글 재검증, 분리된 금액 발화 연결로 제안한다. 실제 보류 사례와 판매자가 수정한 정답을 비교해 검증하고, 정확성이 확인된 유형부터 자동 반영을 적용한다.

**1-B. 판매자의 음성 정정과 정정 보류 해결 규칙**

보류 판매와 이미 자동 저장·수정·확정된 판매 모두 음성 정정 대상이다. 판매자가 명시한 정정 발화를 해당 주문의 새 값에 대한 근거로 사용한다. 처음 저장된 값만으로 정정 발화를 배척하지 않는다.

정정 의도를 일반 상품 등록·가격 추출·신규 판매 추출보다 먼저 판별한다. `아니고`, `아니시고`, `정정`, `잘못 말씀드렸네요`, `변경하겠습니다` 등을 문맥과 함께 해석한다. AI/파서 결과는 정정 항목, 부정한 기존 값, 긍정한 새 값, 대상 상품·구매자 지칭, 적용 범위, 근거 발화로 구성한다.

| 발화 | 의도·값 | 처리 |
|---|---|---|
| `xxx님 가격이 0.9가 아니고 1.2입니다` | xxx님이 구매한 상품의 금액 정정, 기존 9,000원 → 새 12,000원 | 앞뒤 문맥과 기존 값으로 해당 주문을 특정한 뒤 정정 |
| `xx님 구매하신거 가격이 0.9가 아니고 1.2입니다` | 구매자 xx의 주문 가격 정정 | 해당 구매자·기존 금액·상품 근거로 대상을 찾음 |
| `좀전에 판매한거 xxx님이 아니시고 ooo님께 판매하겠습니다` | 기존 구매자 xxx → 새 구매자 ooo | 해당 판매 한 건의 구매자 ID를 교체 |
| `12번 상품, 러블리님 금액 1.2로 정정합니다` | 상품·구매자·새 가격 명시 | 일치하는 판매가 특정되면 정정 |
| `아니요, 방금 수정한 거 취소할게요` | 직전 정정 철회 | 직전 정정 요청을 특정해 미적용 초안을 취소하거나 충돌 확인 후 복원 |

`1.2인가요?` 같은 질문, `1.2로 변경하지 마세요` 같은 부정 명령, 인용된 발화를 실행 명령과 구분한다. `0.9가 아니고…`에서 문장이 끊기면 새 값이 완성될 때까지 정정 초안으로 보관한다. 단지 잠시 조용해졌다는 이유로 불완전한 값을 저장하지 않는다. 연속 정정은 같은 초안에 반영해 완성된 변경 묶음을 한 번 적용한다.

대상 탐색은 같은 판매자·방송 회차의 상품번호, 기존 구매자, 기존 금액, 앞뒤 발화, 판매 시각을 대조한다. `좀 전에`라는 이유만으로 마지막 저장 한 건을 선택하지 않는다. 우선순위와 최근 시각은 후보를 좁히는 보조 정보이며 자동 적용의 유일한 근거가 아니다.

예: `xxx님이 아니고 ooo님입니다`라는 정정에 xxx님의 최근 주문이 두 건이면 별도 `정정 보류` 요청을 만든다. 후보 상품을 보여주고 `상품번호를 말씀해 주세요`라고 안내한다. 이후 `아까 12번 상품이요` 또는 `12번이요`가 들어오면 기존 정정 요청과 연결해 AI가 재분석한다. 보류 정정이 여러 개라면 후속 발화가 어느 요청을 가리키는지도 확인하고 임의로 연결하지 않는다. 정정 요청·후보·근거는 화면을 다시 열어도 이어서 확인할 수 있게 보존한다.

정정은 기존 규칙으로 대상·새 값·적용 범위가 명확하면 반영한다. 불명확하면 AI에 원래 판매 발화, 정정 발화, 앞뒤 대화, 같은 회차 댓글, 상품 정보와 최근 판매 후보를 전달한다. 근거가 충분해지면 자동 반영하고, 해결되지 않으면 후보와 부족한 정보를 남긴다. 가격만 해결됐지만 구매자 문제 등이 남아 있으면 그 판매의 보류를 계속 유지한다.

구매자 변경은 ooo를 실제 댓글 작성자 또는 등록 구매자의 고유 ID와 연결해 수행한다. 동명이인·복수 후보는 추가 확인 대상이다. 해당 판매 한 건을 새 구매자에게 연결하고 구매자별 합계를 다시 계산한다. xxx의 다른 주문이나 고객 정보 전체를 바꾸거나 신규 판매를 중복 생성하지 않는다.

가격 정정은 단가인지 총액인지 구분한다. 단가 정정이면 수량에 따라 합계를 재계산해 `unitPrice`, `quantity`, `amount`의 일관성을 유지한다. `방금 판매한 건의 가격`과 `이 상품의 앞으로 판매할 가격`도 구분한다. 과거 판매 전체까지 정정한다는 명시가 없으면 변경 범위를 임의로 넓히지 않는다. 범위가 불분명하면 그 부분만 추가로 확인한다.

저장 전이면 판매 초안을 수정한 후 한 번 저장한다. 이미 저장된 건이면 동일 판매 ID에 정정 이력을 추가하고 기존 판매를 조건부 갱신한다. UI는 실제 저장 성공 전에 `정정 완료`로 표시하지 않는다. 정정이 보류되는 동안에는 기존 판매값과 별도 정정 요청을 함께 보존한다.

완료 카드에는 `음성 정정 완료 · 상품 12번`, `구매자 xxx → ooo`, `금액 9,000원 → 12,000원`, 사용한 AI 번호와 근거를 표시한다. 원래 발화·정정 발화·변경 전후 값·시각·처리 주체를 이력에 남긴다. `정정 근거 보기`, `후보 적용`, `되돌리기`를 제공한다.

되돌리기는 정정 이력을 삭제하지 않고 복원 이력을 추가한다. 아직 적용되지 않은 정정은 요청과 진행 중 시도를 취소한다. 이미 반영된 정정은 이후 수정·결제·출고 등과 충돌하는지 확인한 후 복원하며, 충돌하면 복원할 범위를 확인할 수 있게 표시한다. 음성의 `방금 수정한 거 취소`는 판매 자체의 삭제와 구분한다.

정정 저장 후 구매자별 합계·정산 화면을 갱신한다. 이미 전표가 출력됐다면 같은 판매번호와 새 revision으로 `수정 전표`를 한 번 생성한다. 출력된 종이가 회수된 것으로 간주하지 않고 수정본임을 표시한다. 결제·출고까지 연결된 주문은 관련 처리와 정정을 함께 확인하는 화면으로 연결한 뒤 필요한 후속 조치를 수행한다.

**2. 관리자 화면과 설정**

관리자 메뉴에 `판매 AI 설정`을 추가하고, 기존 음성인식(STT) 설정과 구분한다. 관리자 대시보드에는 현재 설정 및 장애 요약을 표시한다.

| 항목 | 설정 내용 |
|---|---|
| AI 사용 | 판매 보류 해결 / 정정 보류 해결 각각 사용 여부 |
| 1번·2번 슬롯 | 우선순위, 로컬·클라우드 유형, 공급자/실행 엔진, 모델명 |
| 로컬 연결 | 실행 위치(같은 PC·내부망·외부 IP/도메인), 전체 API 주소(프로토콜·호스트·포트·기본 경로), 실행 엔진·모델 |
| 요청 경로 | 서버 직접 호출 또는 지정 PC 도우미 경유; 내부망/VPN 접근이 필요한 경우 실제 접근 가능한 실행기 지정 |
| 자체 운영 서버 인증 | 미사용·Bearer 토큰·API 키 등 지원 인증 방식, 비밀정보 등록·교체 |
| 클라우드 연결 | 지원 공급자, 모델, API 키, 필요 시 검증된 API 주소 |
| 제한 시간 | 연결 제한, 전체 분석 제한, 최초 모델 준비 제한 |
| 전환 | 자동 대체 사용, 복구 점검 간격, 1번 자동 복귀 정책 |
| 사용량 | 클라우드 사용 한도, 호출·실패·자동 전환 횟수, 응답 시간 |
| 시험 기능 | 연결 점검, 실제 정정 시험, 두 모델 전체 점검 |
| 적용 상태 | 저장된 설정 버전, 적용 버전, 마지막 점검 시각, 실패 이유 |

설정은 초안 저장과 적용을 구분한다. 변경한 모델은 연결 시험과 실제 처리 시험 후 운영 설정에 적용한다. 운영 중인 작업은 시작 시점의 설정 버전을 유지하고, 새 작업부터 새 설정을 사용한다. 키 폐기·사용 중단은 진행 중 작업의 취소 및 결과 무효화에 반영한다.

공통 우선순위는 관리자가 설정하고, 실제 요청 경로와 접근 권한은 판매자/작업공간별로 관리한다. 관리자 화면의 시험은 운영 요청과 동일한 실행 위치·주소·인증·모델로 수행한다. PC 도우미 경유이면 지정 PC에서, 서버 직접 호출이면 백엔드에서 시험한다. 관리자 PC에서의 연결 성공을 다른 경로의 정상 상태로 간주하지 않는다. 설정한 외부 IP가 로컬 LLM이라는 이유만으로 PC 도우미 경유를 강제하지 않는다.

클라우드와 서버 직접 호출 방식의 자체 운영 LLM 인증 정보는 서버 전용 비밀 저장소에 보관한다. PC 도우미 경유 연결에서 인증이 필요하면 해당 작업공간·연결에 권한이 있는 도우미의 보호된 저장소로 전달하거나 단기 연결 자격증명을 사용한다. 관리자는 등록·교체·삭제할 수 있고, 조회 화면에는 등록 여부와 마스킹한 값만 표시한다. 판매자 브라우저와 브라우저 로컬 저장소로 공용 키를 내려보내지 않는다. 설정 변경 권한은 서버에서 ADMIN 역할을 검증한다.

외부 IP/도메인 연결은 HTTPS와 인증을 기본으로 하고 인증서 오류를 숨기거나 검증을 끄지 않는다. 접속 주소는 실행 위치에 맞춰 등록·검증한다. 승인된 내부망/VPN 서버는 지정된 경로로 접근할 수 있게 하되, 임의 주소 입력으로 서버 내부 관리 주소나 메타데이터에 접근하지 못하도록 목적지·포트·리디렉션을 제한한다. 주소 검증과 리디렉션 제한은 [OWASP 서버 요청 보안 지침](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)을 참고한다. 웹 브라우저에서 외부 LLM으로 직접 요청하는 대신 서버 또는 인증된 도우미가 호출한다.

모델명은 하드코딩하지 않는다. 최초 지원 자체 운영 엔진은 Ollama를 기준으로 설계하며, 같은 어댑터를 PC·내부망·외부 서버 주소에 사용할 수 있게 한다. 클라우드는 공식 API에 맞춘 공급자 어댑터를 둔다. 관리자에게 제공할 모델 목록은 한국어 정정 이해, 구조화 결과, 응답 시간 검증을 통과한 모델로 구성한다. 실제 모델 선정은 실행 서버의 메모리·GPU와 현장 발화 평가 결과를 기준으로 한다.

**3. 연결 구조와 공통 작업 관리**

| 구성 요소 | 책임 |
|---|---|
| 웹 앱 | 보류·정정 요청 등록, 근거 동기화, 진행 상태 및 결과 표시 |
| 서버 AI 작업 관리자 | 작업 보존, 실행 모델 결정, 제한 시간, 자동 전환, 결과 검증·확정 |
| 로컬 PC 도우미 | 기기 인증, 지정된 PC/내부망/외부 LLM 점검·호출, 작업 수신, 결과·상태 보고 |
| 자체 운영 LLM 직접 호출 어댑터 | 서버에서 등록된 외부 IP/도메인 또는 접근 가능한 내부망 LLM을 호출하고 상태 보고 |
| 클라우드 어댑터 | 서버에서 API 키로 모델 호출, 공급자 응답·오류를 공통 형식으로 변환 |
| 결과 적용 처리 | 판매 버전 확인, 값 수정, 변경 이력 저장, 출력 작업 생성 |

PC 경유 경로: 서버 작업 대기열 ↔ 인증된 PC 도우미 → 해당 PC에서 접근 가능한 자체 운영 LLM.

외부 IP/도메인 직접 경로: 서버 작업 관리자 → 등록된 자체 운영 LLM API.

클라우드 경로: 서버 작업 관리자 → 클라우드 LLM API.

PC 경유 방식에서는 도우미가 서버에 인증된 연결을 시작하거나 작업을 가져간다. 클라우드 서버에서 판매자 PC의 127.0.0.1 주소를 직접 호출하지 않는다. 서버에서 도달 가능한 외부 IP/도메인 LLM은 서버 직접 호출을 기본으로 하며 PC 도우미 없이도 작동하게 한다. 내부망/VPN 주소는 접속 가능한 도우미나 실행기를 지정한다. 클라우드 호출 경로도 PC 도우미가 꺼져 있어도 이용할 수 있게 구성한다. 현재 `cloudPrintWorker`의 기기 인증·작업 수신 방식을 참고하되 AI 작업용 권한과 대기열을 별도로 둔다.

인터넷이 끊긴 경우에도 도우미와 같은 PC 또는 도달 가능한 내부망 모델이 실행 중이고 근거가 로컬에 있다면 분석과 임시 결과 보존은 가능하게 설계한다. 외부 IP의 자체 운영 LLM은 해당 네트워크 경로가 살아 있어야 사용할 수 있으며, `로컬`이라는 유형만으로 오프라인 가능이라고 표시하지 않는다. 서버에 저장되지 않은 분석 결과는 `분석 완료·동기화 대기`로 표시한다. 연결 복구 후 최신 판매 버전과 대조해 반영하며, 그 전에 중앙 저장 완료나 수정 전표 완료로 표시하지 않는다.

AI 입력은 판매자·회차·대상 판매 범위의 발화, 관련 댓글, 판매 당시 상품 정보 및 확인된 후보로 제한한다. 댓글은 분석 자료로 취급하고 AI 실행 지시로 취급하지 않는다. 두 모델에는 같은 근거 스냅샷과 같은 출력 규격을 사용한다.

출력에는 처리 가능 여부, 판매 후보 ID, 변경 전후 값, 근거 ID, 부족한 정보 및 충돌 사유를 포함한다. 근거가 없는 닉네임 생성이나 금액 추정은 반영하지 않는다. JSON 형식이 맞더라도 내용의 근거 검증은 별도로 수행한다. 로컬 Ollama의 스키마 기반 출력 기능을 활용할 수 있다. [Ollama 구조화 출력 문서](https://docs.ollama.com/capabilities/structured-outputs)

**4. 1번 → 2번 자동 전환 정책**

| 상황 | 처리 |
|---|---|
| 1번이 최근 점검에서 사용 불가 | 현재 작업을 바로 2번에 전달 |
| 지정 요청 경로의 도우미 종료·연결 거절·DNS/TLS/통신 장애 | 1번 시도 종료 후 2번 실행; 서버 직접 호출 모델은 도우미 종료의 영향을 받지 않음 |
| 모델 미설치·모델 로딩 실패·메모리 부족 | 해당 로컬 슬롯 사용 불가, 2번 실행 |
| 키 오류·권한 없음·잘못된 모델 설정 | 2번 실행, 1번은 설정 수정/명시 점검까지 제외 |
| 공급자 사용량 제한·속도 제한 | 2번 실행, 공급자가 제공한 재시도 시각과 관리자 한도 적용 |
| 서버 오류·분석 제한 시간 초과 | 2번 실행, 일시 장애 횟수 집계 |
| 빈 응답·잘못된 구조·완료되지 않은 응답 | 응답 실패로 기록하고 2번 실행 |
| 정상 응답이지만 근거 부족 | 장애로 표시하지 않고 보류 유지, 추가 자료 수신 시 재분석 |
| 1번 결과의 근거가 자료와 불일치 | 자동 반영 차단, 검증 실패 기록; 선택 정책으로 2번에 독립 재검토 1회 |
| 두 모델 모두 장애 | `AI 사용 불가·재시도 대기`, 기존 값과 작업 보존 |

한 작업에서는 기본적으로 1번 한 번, 2번 한 번까지 순서대로 시도한다. 같은 모델을 오래 재시도하다가 대체가 지연되지 않게 한다. 1번이 정상적으로 자료 부족을 판단한 경우의 2번 재검토는 장애 대체와 별개인 옵션이며, 기본은 추가 근거 대기다. 안전상 거절을 다른 모델로 우회하는 정책은 두지 않는다.

초기 제한 시간 제안: 연결 3초, 이미 준비된 자체 운영 모델 분석 20초, 클라우드 분석 15초. 실제 외부망 지연과 서버 성능에 맞춰 연결별로 조정한다. 최초 자체 운영 모델 준비는 사전 점검에서 별도로 최대 60초를 두고, 실시간 요청이 이 준비 시간을 모두 기다리지 않도록 한다. 제한 시간은 요청 접수·대기·모델 응답 완료까지의 전체 경과 시간을 기준으로 하며, 일부 토큰이 도착했다고 무한정 연장하지 않는다.

현재 요청의 실패는 즉시 대체 실행한다. 별도로 1번에서 일시 장애가 연속 2회 발생하면 이후 요청은 30초간 바로 2번으로 보내도록 제안한다. 복구 실패가 계속되면 점검 간격을 1분·2분·최대 5분으로 늘린다. 장애 모델의 반복 호출을 제한하고, 제한된 시험으로 복구를 확인하는 방식이다. [Microsoft 장애 차단 패턴 문서](https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker)

1번은 30초 이상 간격의 실제 처리 시험을 연속 2회 통과하면 복구로 판단하고 다음 새 작업부터 사용한다. 2번에서 처리 중인 작업은 그대로 끝낸다. 양쪽 장애에서 복구되면 보류 작업을 한꺼번에 실행하지 않고 제한된 동시 실행 수로 재개한다.

장애 집계는 요청 경로·실행기·접속 주소·모델·인증 범위·설정 버전별로 분리한다. 한 판매자 PC의 연결 장애로 서버에서 정상 접근 가능한 외부 LLM을 제외하지 않는다. 같은 경로·주소·모델·인증을 공유하는 작업은 건강 상태를 공유할 수 있다. 두 슬롯이 같은 서버나 네트워크를 공유하면 함께 장애가 날 수 있으므로 관리자에 연결 위치를 나란히 표시하고, 양쪽 실패 시 보류 유지 정책을 적용한다.

**5. 작동 불가 사전 점검**

연결 성공, 모델 준비, 실제 정정 처리 능력을 세 단계로 점검한다. 단순 상태 응답 성공만으로 준비 완료를 표시하지 않는다.

| 단계 | 로컬 LLM | 클라우드 LLM |
|---|---|---|
| 연결 | 지정 경로에서 LLM 서버 접근·인증·해당 시 DNS/TLS 검사; PC 경유이면 도우미·선택 기기도 확인 | 실제 호출 서버에서 DNS·TLS·인증 확인 |
| 모델 준비 | 선택 모델 접근, 준비/로딩 상태, 서버가 제공하는 설치·메모리·실행 오류 | 선택 모델 접근 권한, API 호환성, 알려진 한도 상태 |
| 실제 처리 | 합성 정정 문장 추론, 구조와 정답 검사, 지연 측정 | 동일 규격으로 실제 소량 추론, 구조와 정답 검사, 지연 측정 |

Ollama는 설치된 모델 목록과 현재 실행 중인 모델 목록을 별도로 제공한다. 설치되어 있으나 아직 메모리에 올라오지 않은 모델은 `준비 중`으로 구분하고, 실제 준비 시도 결과로 사용 가능 여부를 결정한다. [설치 모델 조회](https://docs.ollama.com/api/tags), [실행 모델 조회](https://docs.ollama.com/api/ps)

외부 서버의 관리 API가 공개되지 않아 설치 목록이나 GPU 상태를 읽을 수 없는 경우 그 항목은 `조회 불가`로 표시하고, 허용된 실제 추론 시험으로 가용성을 판단한다. 모델 목록 조회 권한 부족을 추론 기능 장애와 동일시하지 않는다. 원격 서버가 따로 보고한 정상 상태만으로 현재 호출 경로의 사용 가능성을 확정하지 않는다.

시험은 실제 판매를 변경하지 않는 합성 자료로 진행한다. 예시는 다음과 같다.

- `xx님 구매하신거 가격이 0.9가 아니고 1.2입니다` → 기존 9,000원 / 새 12,000원.
- `xxx님이 아니시고 ooo님께 판매하겠습니다` → 기존 xxx / 새 ooo, 제공된 구매자 ID와 연결.
- 같은 구매자의 판매가 두 건이고 지칭 근거가 없음 → 임의 선택 없이 보류.
- `1.2로 변경하지 마세요` → 변경 실행 없음.
- 정정 문장이 두 조각으로 도착함 → 새 값이 완성되기 전에 실행 없음.

전체 시험 묶음은 설정 적용·모델 변경·기능 검증 시 사용한다. 주기 점검은 그중 짧은 시험을 교대로 사용한다. 시험 성공은 기본 사용 가능성의 근거이며 모든 실판매 정답을 보장하지는 않는다.

| 점검 시점 | 초기 운영안 |
|---|---|
| 설정 등록·변경 | 변경한 슬롯의 연결·모델·실제 처리 시험 |
| 방송 시작 | 두 슬롯의 최근 결과 확인, 오래됐으면 실제 시험 및 로컬 준비 |
| 방송 중 자체 운영 모델 상태 | PC 경유이면 도우미가, 서버 직접이면 서버 점검기가 15초 간격으로 경량 점검; 45초 이상 신선한 결과가 없으면 상태 만료/도달 불가 |
| 대기 모델 점검 | 방송 중 최근 성공 추론이 5분 이상 없으면 소량 실제 시험 |
| 실행 중 | 실제 호출의 성공·오류·지연·검증 결과를 즉시 상태에 반영 |
| 장애 복구 | 30초부터 간격을 늘려 실제 시험, 연속 성공 후 복귀 |
| 도우미 재시작·절전 복귀·네트워크/주소/인증 변경 | 영향받은 경로의 기존 결과를 만료시키고 준비 상태 재확인 |

클라우드와 외부 자체 운영 서버의 점검은 같은 경로·주소·인증·모델·설정을 공유하는 판매자별로 중복 실행하지 않고 결과를 공유한다. PC 경유 연결은 기기별 실제 접근 경로를 반영해 점검한다. 방송하지 않는 시간에는 추론 점검을 줄이고, 모델 호출량·예산을 집계한다. 한도를 제공하지 않는 공급자의 남은 잔액은 `확인 불가`로 표시한다.

건강 상태에는 `미설정`, `점검 중`, `준비 중`, `사용 가능`, `지연`, `사용 불가`, `복구 시험 중`, `상태 만료`를 둔다. 마지막 점검 시각·실제 추론 성공 시각·지연·오류 코드·원인·다음 시험 시각을 함께 기록한다.

사전 점검으로 모든 장애를 예측할 수는 없다. 직전 점검이 정상이어도 실제 요청에서 네트워크나 자원이 실패할 수 있으므로 요청별 제한 시간과 자동 전환을 항상 병행한다. 특히 로컬 STT와 LLM이 같은 GPU를 쓰는 환경에서는 음성 청취와 동시에 점검·추론해 전사 지연과 메모리 경쟁을 확인한다.

**6. 메인 창 표시**

메인 라이브 화면 상단에 `보류·정정 AI` 표시를 추가한다. 관리자에 설정된 우선순위와 실제 현재 실행 모델을 구분해 표시하며, 판매자에게는 자신의 작업공간에 지정된 연결 경로의 상태를 보여준다.

| 상태 | 표시 예시 |
|---|---|
| 요청이 없고 1번 준비 완료 | `AI 1번 · 로컬 · 사용 가능` |
| 1번 분석 중 | `AI 1번 · 로컬 · 정정 분석 중` |
| 외부 IP의 자체 운영 모델 분석 중 | `AI 1번 · 자체 운영(외부 서버) · 정정 분석 중` |
| 대체 시도 시작 | `AI 1번 → 2번 전환 중 · 응답 시간 초과` |
| 2번 분석 중 | `AI 2번 · 클라우드 · 대체 처리 중` |
| 대기 상태에서 2번만 가용 | `AI 2번 사용 가능 · 1번 복구 점검 중` |
| 양쪽 사용 불가 | `AI 사용 불가 · 보류 3건 재시도 대기` |
| 최근 상태가 만료됨 | `AI 상태 확인 중 · 마지막 점검 2분 전` |
| 로컬 분석만 완료됨 | `AI 1번 분석 완료 · 서버 동기화 대기` |

배지를 누르면 두 모델명, 유형, 연결 위치(같은 PC·내부망·외부 서버), 요청 경로, 준비 상태, 점검 시각, 전환 이유를 볼 수 있다. 접속용 비밀정보는 표시하지 않는다. 색상뿐 아니라 번호와 상태 텍스트를 사용한다. 요청이 없을 때는 `처리 중`이라고 표시하지 않는다.

판매 카드에는 `1번 AI 보완`, `2번 AI 정정`, `1번 실패 → 2번 처리`를 작업 이력에 맞게 표시하고 변경 전후 값과 근거를 제공한다. 여러 작업이 다른 모델에서 동시에 실행 중이면 상단에는 `1번 1건 · 2번 2건 처리 중`처럼 표시한다. 대기용 기본 슬롯을 전체 작업의 실제 실행 모델처럼 표시하지 않는다.

관리자 화면은 슬롯별 사용량, 장애와 자동 전환 횟수, 복구 시각, 지연, 접속 주소·요청 경로·기기별 상태를 집계한다. 경고는 장애 발생·대체 전환·복구 등 의미 있는 상태 변화에 표시하고 반복 점검마다 같은 알림을 쌓지 않는다.

**7. 판매 데이터와 중복 처리 보호**

- 각 작업에 고유 작업 ID, 판매 ID, 판매 revision, 설정 버전, 근거 스냅샷 버전, 시도 ID를 부여한다.
- 2번으로 전환할 때 1번 시도는 취소 요청하고 결과 적용 권한을 만료시킨다. 모델이 실제로 취소되지 않아 늦게 반환하더라도 결과는 반영하지 않는다.
- 작업 결과는 서버의 현재 유효 시도와 판매 revision이 일치할 때만 한 번 적용한다.
- 분석 중 판매자가 수동 수정했거나 새 정정이 발생하면 기존 분석 결과를 오래된 것으로 처리한다. 최신 자료로 새 작업을 만들되 무한 반복하지 않는다.
- AI는 판매 데이터에 직접 쓰기 권한을 갖지 않는다. 닉네임·금액·상품·구매자 근거와 다른 보류 사유는 공통 검증기가 확인한다.
- 보완/정정 저장, 변경 이력, 필요한 출력 작업은 서버에서 일관되게 생성한다. 출력 작업은 판매 revision 기준으로 중복을 막는다.
- 양쪽 장애·근거 부족·검증 실패는 서로 다른 보류 이유로 남긴다. 장애 복구로 재시도할 작업과 추가 발화/댓글을 기다릴 작업을 구분한다.

추가 데이터 개념: AI 설정, 접속 주소·실행 위치·요청 경로, 비밀정보 참조, 기기/실행기 연결, 경로별 모델 건강 상태, 보류/정정 작업, 모델별 실행 시도, AI 결과·근거, 판매 정정 이력. 일반 조회 API에는 비밀정보 참조의 실제 값이나 민감한 원문 오류를 포함하지 않는다.

**8. 개발 순서와 완료 기준**

| 순서 | 개발 내용 | 완료 기준 |
|---|---|---|
| 1 | 관리자 두 슬롯 설정·비밀정보·설정 버전·권한 | 관리자만 변경 가능, 판매자 응답에 공용 키 없음, 우선순위 교체 가능 |
| 2 | 자체 운영 LLM 어댑터(PC 경유·외부 서버 직접)·클라우드 어댑터·공통 결과 규격 | 동일 PC·내부망·외부 IP/도메인 경로와 선택한 두 모델이 같은 합성 정정 시험을 통과 |
| 3 | 경량 점검·실제 추론 시험·경로별 상태 전파 | 엔진 종료·인증/TLS 오류·미설치 모델·관리 API 조회 불가·로딩 중·상태 만료를 구분 |
| 4 | 서버 작업 관리자·자동 전환·복구·중복 방지 | 1번 장애 시 동일 작업을 2번에서 처리, 늦은 1번 결과는 미반영 |
| 5 | 판매 보류·정정 보류 연결 및 검증·이력·출력 | 대상 판매와 값이 검증된 경우만 한 번 저장·출력 |
| 6 | 메인 AI 번호·상태·전환 이유·카드 이력 | 실제 실행 모델과 표시 번호가 모든 상태에서 일치 |
| 7 | 현장 발화·장애 주입·동시 음성인식 검증 | 아래 장애 및 업무 시나리오 통과 후 운영 적용 |

검증할 시나리오는 다음과 같다.

1. 로컬→클라우드, 클라우드→로컬 순서를 각각 적용하고 정상 우선 모델이 사용된다.
2. 1번 엔진 종료, 잘못된 키, 한도 초과, 서버 오류, 무응답, 잘못된 JSON에 대해 2번으로 전환된다.
3. 1번 실패와 2번 성공 이후 1번의 늦은 결과가 도착해도 판매/전표가 중복 변경되지 않는다.
4. 둘 다 실패하면 기존 판매와 정정안이 남고, 가용 모델 복구 후 제한된 속도로 재개된다.
5. 자료 부족은 `AI 장애`로 표시되지 않고 새 근거가 도착하면 재분석된다.
6. xxx→ooo, 0.9→1.2 정정과 복수 주문·분리 발화·부정 명령을 구분한다.
7. 사용자 수정과 AI 응답이 겹쳐도 사용자 변경을 덮어쓰지 않는다.
8. 한 PC의 장애가 다른 PC의 정상 상태와 라우팅에 영향을 주지 않는다.
9. 설정 순서 변경·도우미 재시작·절전 복귀 후 상태와 실행 모델 표시가 최신 정보와 일치한다.
10. 로컬 STT와 LLM 동시 실행에서 음성 누락·지연 및 메모리 부족 여부를 측정하고 기본 제한 시간을 조정한다.
11. 두 클라이언트가 같은 작업을 보거나 다시 접속해도 작업 제출·시험·출력이 중복되지 않는다.
12. 인터넷 단절 중 임시 로컬 결과가 저장 완료로 표시되지 않고, 복구 시 서버와 충돌 검사 후 반영된다.
13. 외부 IP/도메인의 자체 운영 LLM을 1번 또는 2번에 지정할 수 있고, 도우미 종료 상태에서도 서버 직접 호출이 작동한다.
14. 관리자 PC에서는 접속되지만 실제 서버/도우미 경로에서는 방화벽·인증·DNS/TLS 등으로 실패하는 경우 해당 경로를 사용 불가로 표시하고 대체한다.
15. API 주소·포트·기본 경로·인증 변경 시 이전 점검 결과와 진행 중 시도의 연결 정보가 혼동되지 않는다.
16. 관리용 모델 목록은 조회 불가여도 실제 추론이 성공하는 외부 서버를 사용 가능으로 판정한다.
17. 같은 외부 서버를 공유하는 판매자들의 점검은 중복 실행되지 않으며, 서로 다른 기기 경로의 실패는 별도로 기록된다.
18. 닉네임 오인식·끝번호·금액 누락·분리 발화·댓글 지연을 각각 검증하고 일부 값만 해결된 판매는 잔여 보류를 유지한다.
19. xxx의 주문 두 건으로 정정이 보류된 뒤 `12번이요`가 도착하면 기존 요청의 상품 12번 판매만 ooo로 바뀐다.
20. 저장 전 초안 정정과 이미 확정된 판매 정정이 각각 한 번 반영되며, 신규 판매 중복이 생기지 않는다.
21. 단가와 총액, 한 주문과 상품의 향후 가격을 구분하고 다른 주문·고객 정보·과거 판매를 임의로 바꾸지 않는다.
22. 금액·닉네임이 따로 도착하는 한 정정 문장은 완성된 변경 묶음으로 저장되고 중간마다 전표가 나오지 않는다.
23. 음성 정정 철회와 화면 되돌리기가 미적용 요청 취소·충돌 없는 복원·충돌 시 확인으로 구분된다.
24. 이미 출력한 판매의 정정은 같은 판매번호의 수정 전표 한 번으로 이어지고, 결제·출고 연결 건은 후속 처리 확인 화면으로 연결된다.
25. 남은 보류 일괄 확정은 필수 값과 근거 검증을 통과한 건만 확정하며 미확인 값이 남은 건은 보류한다.
26. 근거 보기·후보 적용·되돌리기가 해당 판매·정정 요청에 연결되고 화면 재접속 후에도 정정 대기를 이어갈 수 있다.

운영 지표는 자동 해결률, 잘못된 자동 수정률, 사람의 되돌리기 비율, 처리 시간 분포, 대체 성공률, 양쪽 실패율, 모델별 사용량으로 잡는다. 정확성과 성능 목표 수치는 대표 발화 평가 후 확정하며 측정 전 성공률을 단정하지 않는다.

현재 STT 설정은 공급자와 키를 관리하는 UI가 있으나 LLM 작업·장애 전환은 새로 구현해야 한다. 현재 음성 정정은 마지막 저장 참조에 필드를 즉시 덮는 방식이므로 대상 판별·초안·버전 검증을 함께 보완해야 한다.

오늘 대화 중 기존 추출기를 직접 확인했을 때 `가격이 0.9가 아니고 1.2입니다`에서는 9,000원, `좀전에 판매한거 xxx님이 아니시고 ooo님께 판매하겠습니다`에서는 xxx가 추출됐다. 이 결과는 정정 전후 값을 별도로 해석해야 한다는 설계 근거다. 이는 당시 코드의 점검 기록이며 구현 착수 시 최신 코드와 테스트를 다시 확인한다.
