# VoiceCAP 상품 판매관리 통합 인수 테스트

작성일 2026년 9월 7일 · 단일 에이전트 실행안 개정 2026년 9월 8일 · 결과 기록용 체크리스트

이 문서는 개발 완료 여부를 판정하는 테스트 절차다. 모든 항목의 초기 상태는 미실행이다. 기대 결과를 적은 것과 실제 테스트를 통과한 것은 다르다. 테스트 실행자는 버전, 환경, 실제 결과, 증거 위치를 기록하고 실패는 재현 순서와 함께 등록한다.

## 1 테스트 준비

운영 판매자의 실제 거래 대신 개발 또는 테스트 workspace 두 개를 준비한다. W1은 테스트 판매자, W2는 다른 판매자다. W1에 웹 로그인, Android 판매 권한 기기, 댓글 수집과 출력 권한 PC를 연결한다. 권한 없는 기기와 연결 해제된 기기도 준비한다. 테스트 전표에는 테스트 표시를 넣고 실제 고객에게 문자나 정산서를 보내지 않는다.

다음 환경을 기록한다.

| 항목 | 기록할 값 |
| --- | --- |
| 소스 | 브랜치와 commit |
| 웹 | 빌드 및 배포 주소 |
| 서버 | migration 식별자와 sales-api 버전 |
| Android | APK 버전과 기기 모델 및 API 수준 |
| PC | 도우미 버전과 Windows 및 GPU |
| 출력 | 프린터 이름과 용지 크기 및 테스트 여부 |
| 음성 | 사용 공급자와 모델 및 입력 장치 |

먼저 02_SHARED_CONTRACT.md와 실제 API fixture를 맞춘다. 오류 응답을 재현할 개발 전용 네트워크 제어와 테스트용 STT 이벤트 주입을 준비한다. 개인정보나 토큰을 화면 증거에 남기지 않는다.

## 2 계산 검증용 고정 데이터

W1의 현재 회차 S1과 현재 상품 P101을 사용한다. P101의 가격은 20,000원이고 아직 판매는 없다. 예전 상품 P100에는 철수 수량 2, 단가 20,000원, 합계 40,000원인 ACTIVE 판매 한 행이 있다. 따라서 S1은 2개, 40,000원이다.

철수는 과거 회차까지 합쳐 ACTIVE 판매가 5행, 누적금액 120,000원이다. 이 중 S1의 P100 한 행이 포함되어 있다. 영희의 기존 기록은 없다. 댓글 C1과 C2는 철수의 서로 다른 원본 메시지이며, C3은 영희의 메시지다. 닉네임이 철수로 같지만 platform user ID가 다른 세 번째 사람도 별도 준비한다.

| 단계 | 회차 수량 | 회차 금액 | 철수 누적 횟수 | 철수 누적 금액 | 영희 누적 횟수와 금액 |
| --- | --- | --- | --- | --- | --- |
| 초기 | 2 | 40,000 | 5 | 120,000 | 0회 0원 |
| C1 C2 C3 선택만 | 확정 2 | 확정 40,000 | 확정 5 | 확정 120,000 | 확정 0회 0원 |
| 철수 수량 2와 영희 수량 1 저장 | 5 | 100,000 | 6 | 160,000 | 1회 20,000원 |
| P101 가격 25,000으로 수정 | 5 | 115,000 | 6 | 170,000 | 1회 25,000원 |
| P101 영희 판매 취소 | 4 | 90,000 | 6 | 170,000 | 0회 0원 |

가격 수정과 취소는 구매횟수를 새로 추가하지 않는다. 마지막 줄은 직전 상태에서 영희의 25,000원 한 행만 취소한 경우다. 테스트가 서로 영향을 주면 해당 단계 직전의 fixture를 복원하고 시작한다.

3. 이름과 사진이 없는 입력을 번호이미지 방식으로 등록한다.

### T09 최신 댓글과 상품 동기화

실행 담당은 통합 에이전트다. 관련 R10, R12.

PC 수집기에서 같은 문구의 서로 다른 메시지, 동일 원본 ID의 재전송, 같은 시각의 댓글을 보낸다. Android에서 과거 댓글을 읽으며 일부 구매자를 선택한 뒤 새 댓글 100건을 보낸다. 새 댓글이 없는 상태에서 웹이 현재 상품·회차 합계·선택 구매자의 통계를 바꾸고 Android가 이를 갱신하는지도 확인한다. 탭 이탈과 재진입, 연결 끊김 뒤 복구를 검사한다.

### T11 구매자 식별과 누적 통계

## 8 결과 기록과 최종 인수

각 테스트에 테스트 ID, 실행자, 실행일, 환경, 실제 결과, 로그 또는 화면 증거, 실패 이슈, 재시험 결과를 남긴다. 개발자가 예상값을 수동으로 화면에 입력한 결과는 API 통합 검증 증거로 사용하지 않는다.

최종 인수는 R01부터 R18과 T01부터 T22의 연결을 검토하고, 실제 Android 입력 또는 음성 입력이 서버 저장과 웹 표시 및 PC 전표까지 이어지는 모습을 확인하는 것으로 끝낸다. 물리 인쇄를 확인할 프린터가 없으면 해당 항목은 미검증으로 명시하고 통과로 바꾸지 않는다.

수용 목표는 상품과 판매 및 정정 작업의 누락 없음, 같은 요청 재시도의 중복 매출 없음, 다른 판매자 데이터 접근 차단, 두 화면의 합계 일치이다. 인쇄 시스템의 접수와 실제 용지 출력의 차이 및 결과 불명확 상태를 사용자에게 정확히 보여주는 것도 완료 조건이다.
