## 2 먼저 합의한 규칙

사용자가 확인한 내용은 다음 두 가지다.

- 같은 구매자의 여러 댓글을 선택하면 한 구매자로 합치고 수량을 직접 바꿀 수 있다.
- 상품 가격 변경은 영향 대상과 변경 전후 금액 확인 후 기존 판매에도 적용한다.

상품번호와 사진은 사람이 찾는 기준이며 내부에는 변경되지 않는 상품 ID를 둔다. 가격과 구매자 수정은 기존 판매 ID를 유지하고 이력과 정정 전표를 남긴다. 상품을 등록하는 것만으로 판매금액이나 전표가 발생하지 않는다.

## 3 두 개발자의 시작 순서

1. 두 사람이 01 계획서의 요구사항 R01부터 R18과 기본안을 함께 읽는다.
2. 02 명세의 필드, 오류코드, 통계 계산과 정상 및 실패 JSON 예제를 합의한다.
3. A는 DB와 공통 API 및 fixture를 준비한다. B는 Android 빌드와 기존 SMS 기준을 확인하고 같은 fixture로 화면을 만든다.
4. A의 03 지시서와 B의 04 지시서에 따라 작은 기능 단위로 구현한다.
5. 05 테스트의 고정 데이터로 두 화면과 서버 및 전표 결과를 함께 확인한다.

A는 src, server, supabase, desktop/comment-helper와 공통 계약을 소유한다. B는 android/voicecapSMS를 소유한다. 파일 경계 밖의 수정이 필요하면 담당자에게 요청하고 계약과 테스트를 함께 변경한다. A의 백엔드와 인쇄 업무가 더 크므로 B는 모의 데이터 작업과 통합 검수 준비를 병행한다.

## 4 문서 상태와 우선순위

우선 개발은 웹과 Android 상품 중심 판매관리다. Windows 별도 통합 앱은 제안서로 보관한다. 다만 Android 판매를 기존 PC 프린터로 출력하기 위한 도우미 변경은 이번 범위에 포함한다.

문서 작성 때 실제 저장소는 `C:\dev\voice-pin-web`, `main`의 `0414e3b`였고 origin/main도 같은 커밋이었다. 루트 HANDOFF.md 머리말에는 과거 작업 경로 `C:\dev\voice-pin-anti`와 `9e4291b`가 남아 있으므로 새 개발자는 그 두 값만 복사하지 말고 `git rev-parse --short HEAD`, 현재 작업 경로와 원격을 다시 확인한다. HANDOFF의 인증·배포·비밀값 보호 원칙은 계속 따른다.

문서의 새 API와 파일명은 구현 예정 설계다. 기존 파일과 새 파일을 각 작업서에서 구분했다. 인수 테스트의 초기 상태는 미실행이다. 문서의 JSON은 구조 예제이며 실제 서버 fixture는 개발자 A가 유효 ID로 작성한다.

상품등록 OFF 동작, 누적 구매횟수 정의, 카메라 준비 완료 후 시간 계산, 웹 상품사진 영역 등은 구현 기본안으로 표시했다. 기본안을 바꾸면 01 계획서, 02 명세, 해당 A 또는 B 작업서와 05 기대값을 함께 갱신한다. 사용자 확정사항은 별도 지시 없이 바꾸지 않는다.

## 5 개발 중 변경 기록 양식

계약 변경 때 날짜, 변경한 요구사항 ID, 이전 규칙, 새 규칙, 변경 이유, A와 B 영향, 테스트 변경을 남긴다. API 응답을 한쪽만 바꾼 채 작업 완료로 보고하지 않는다. 구현 완료 보고에는 변경 파일, 실행한 테스트, 미검증 항목, migration 및 배포 필요 여부를 포함한다.
