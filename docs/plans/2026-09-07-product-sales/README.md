## 2 먼저 합의한 규칙

사용자가 확인한 내용은 다음 두 가지다.

- 같은 구매자의 여러 댓글을 선택하면 한 구매자로 합치고 수량을 직접 바꿀 수 있다.
- 상품 가격 변경은 영향 대상과 변경 전후 금액 확인 후 기존 판매에도 적용한다.

상품번호와 사진은 사람이 찾는 기준이며 내부에는 변경되지 않는 상품 ID를 둔다. 가격과 구매자 수정은 기존 판매 ID를 유지하고 이력과 정정 전표를 남긴다. 상품을 등록하는 것만으로 판매금액이나 전표가 발생하지 않는다.

## 3 단일 에이전트의 시작 순서

하나의 Antigravity 대화와 하나의 기능 브랜치에서 작업한다. 장시간 작업이므로 전체 문서를 한 번에 구현하라고 지시하지 않고 아래 체크포인트별로 실행·검토·커밋한 뒤 다음 단계로 넘어간다.

1. 01 계획서의 요구사항 R01부터 R18과 구현 기본안을 읽고 현재 브랜치·커밋·작업 트리를 기록한다.
2. `ANDROID-01`과 함께 Android 기존 debug 빌드와 SMS 기준 동작, 웹 빌드, 서버와 PC 도우미 테스트 기준을 먼저 확보한다.
3. 02 명세를 기준으로 `contracts/product-sales/v1/`의 JSON Schema와 정상·실패 fixture를 만든다. 계약 fixture 검증이 끝나기 전에는 DB·API·Android 모델을 확정하지 않는다.
4. 03 작업서의 `CORE-02`부터 `CORE-05`까지 수행해 DB, 인증, 상품과 댓글 API 기반을 만든다.
5. 04 작업서의 `ANDROID-02`부터 `ANDROID-06`까지 수행해 기존 SMS를 보존하면서 동일 fixture 기반 Android 화면과 카메라를 만든다.
6. 03 작업서의 `CORE-06`부터 `CORE-10`까지 수행해 웹, 판매 transaction, 수정과 PC 출력 큐를 완성한다.
7. 04 작업서의 `ANDROID-07`부터 `ANDROID-10`까지 실제 API 연결, 오류 복구, 회귀 검증을 수행한다.
8. 03 작업서의 `CORE-11`과 `CORE-12`, 05 인수 테스트를 수행하고 배포 전 승인을 요청한다.

작업 범위 전체는 `src/`, `server/`, `supabase/`, `desktop/comment-helper/`, `android/voicecapSMS/`, 신규 `contracts/product-sales/v1/`이다. 에이전트는 단계 전환 전에 `git status`, 변경 파일, 테스트 결과와 미검증 항목을 보고하고 기능별 작은 커밋을 남긴다. 실제 진행 상태는 06_IMPLEMENTATION_STATUS.md에 계속 기록한다. `main` 직접 작업, 운영 배포, 실제 고객 대상 문자와 인쇄는 별도 승인 전까지 금지한다.

## 4 Antigravity 시작 지시문

Antigravity Project에는 이 저장소 폴더 하나만 연결하고 격리된 기능 브랜치 또는 New Worktree Mode에서 아래 지시문으로 시작한다.

```text
docs/plans/2026-09-07-product-sales/README.md부터 읽고 안내된 문서를
순서대로 모두 읽어라. 너는 상품 중심 판매관리 전체를 담당하는 단일
구현 에이전트다. 별도 역할 분담이나 병렬 브랜치를 만들지 마라.

01 계획서의 G0부터 G4까지, 03 작업서의 CORE 티켓과 04 작업서의
ANDROID 티켓을 문서에 적힌 순서로 수행하라. 단계마다 선행 조건을
확인하고 작은 커밋을 남기며 변경 파일, 테스트 결과, 미검증 항목을
작업 기록에 적어라. 계약 변경은 02 명세, Schema, fixture, 모든 소비자와
05 테스트를 함께 갱신하라. 각 체크포인트와 커밋 후에는
06_IMPLEMENTATION_STATUS.md를 실제 결과로 갱신하라. 기존 웹·SMS·STT·정산·배송 기능을 보존하라.

00 Windows 통합 앱은 이번 범위에서 구현하지 마라. main에 직접 작업하거나
운영 Supabase/Vercel, 실제 고객 문자, 실제 판매 전표를 건드리지 마라.
운영 배포와 되돌리기 어려운 작업은 로컬 구현과 인수 테스트를 완료한 뒤
사용자 승인을 요청하라. 막히면 임의 계약을 만들지 말고 재현 결과와
```

에이전트가 문서를 읽은 직후에는 현재 경로, 브랜치, HEAD, 원격, 작업 트리, 사용 가능한 테스트 환경과 실제 기기·프린터 유무를 먼저 보고하게 한다. 이미 통과한 증거가 없는 체크리스트는 완료로 간주하지 않는다.

## 5 문서 상태와 우선순위

우선 개발은 웹과 Android 상품 중심 판매관리다. Windows 별도 통합 앱은 제안서로 보관한다. 다만 Android 판매를 기존 PC 프린터로 출력하기 위한 도우미 변경은 이번 범위에 포함한다.

최초 문서 작성 때 저장소는 `C:\dev\voice-pin-web`, `main`의 `0414e3b`였다. 단일 에이전트 실행안 개정 기준은 `C:\dev\voicecap-web`, `main`의 `ad97ca2`다. 루트 HANDOFF.md에는 과거 작업 경로와 커밋이 남을 수 있으므로 에이전트는 값을 복사하지 말고 `git rev-parse --short HEAD`, 현재 작업 경로, 작업 트리와 원격을 직접 확인한다. HANDOFF의 인증·배포·비밀값 보호 원칙은 계속 따른다.

문서의 새 API와 파일명은 구현 예정 설계다. 기존 파일과 새 파일을 각 작업서에서 구분했다. 인수 테스트의 초기 상태는 미실행이다. 문서의 JSON은 구조 예제이며 에이전트가 실제 서버 fixture를 유효 ID로 작성한다.

상품등록 OFF 동작, 누적 구매횟수 정의, 카메라 준비 완료 후 시간 계산, 웹 상품사진 영역 등은 구현 기본안으로 표시했다. 기본안을 바꾸면 01 계획서, 02 명세, 03 또는 04 작업서와 05 기대값을 함께 갱신한다. 사용자 확정사항은 별도 지시 없이 바꾸지 않는다.

## 6 개발 중 변경 기록 양식

계약 변경 때 날짜, 변경한 요구사항 ID, 이전 규칙, 새 규칙, 변경 이유, 웹·서버·Android·PC 도우미 영향과 테스트 변경을 남긴다. API 응답이나 한 클라이언트만 바꾼 채 작업 완료로 보고하지 않는다. 구현 완료 보고에는 변경 파일, 실행한 테스트, 미검증 항목, migration 및 배포 필요 여부를 포함한다.
