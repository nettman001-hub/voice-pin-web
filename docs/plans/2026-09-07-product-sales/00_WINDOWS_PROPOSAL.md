# VoiceCAP Windows 통합 앱 개발 제안서

작성일 2026년 9월 7일 · 기존 웹과 댓글 도우미의 별도 Windows 제품화 제안

## 1 권장 방향

현재 React 웹 화면과 Windows 댓글 도우미를 통합해 별도 설치형 제품인 VoiceCAP Windows를 만드는 것을 권장한다. 기반 기술은 기존 도우미에서 사용 중인 Electron을 이어 쓴다. 실행 프로그램, 설치 파일, 설정, 업데이트를 별도 제품으로 관리하고 계정과 판매 데이터는 기존 Supabase를 공유한다.

이번 문서는 앞서 논의한 Windows 제품화 방향을 보관하는 제안서다. 사용자 우선순위에 따라 당장은 웹과 Android의 상품 중심 판매관리 개선을 먼저 진행한다. 해당 개발계획은 01_DEVELOPMENT_PLAN.md에 별도로 정리했다. Windows 통합 앱 구축은 아직 착수하지 않는다.

## 2 판매자가 사용하게 될 모습

설치 후 기존 계정으로 로그인하고 마이크, 프린터, GPU를 점검한다. 프로그램 안에서 방송 청취, 댓글 확인, 판매 확정, 전표 출력, 정산과 배송 관리를 진행한다. 홈페이지와 별도 도우미를 각각 열고 설정하는 절차를 한 화면으로 통합한다.

Windows 사용자가 개발 도구, Node.js 명령, Python 설치 배치 파일을 직접 실행하지 않도록 한다. 앱 안에서 필요한 엔진과 모델을 준비하고 진행 상태 및 오류 복구를 안내한다.

PC 화면은 왼쪽 업무 메뉴, 중앙 댓글과 인식 결과, 오른쪽 판매 확정과 수정 영역을 기본 배치로 권장한다. 마이크 입력, STT 상태, 프린터, 클라우드 저장 상태는 항상 확인할 수 있게 한다. 창을 최소화한 상태에서도 진행 중인 방송과 출력 상태를 유지한다.

## 3 기존 구현 활용

| 영역 | 활용 방향 |
| --- | --- |
| 로그인과 판매 및 정산과 배송 | 현재 React 화면과 업무 로직 공유 |
| 댓글 수집 | 현재 Node 서버를 앱 내부에서 관리 |
| 음성인식 | Vulkan과 CUDA 및 CPU 엔진 관리 코드 활용 |
| 전표 출력 | 프린터 선택과 출력 큐 및 전표 화면 활용 |
| 회원 권한과 공유 데이터 | 기존 Supabase 인증과 workspace 구조 유지 |
| 트레이와 자동 시작 | 기존 Electron 도우미 기반 활용 |
| 설치와 업데이트 | 정식 Windows 앱 전용 식별자와 배포 경로 추가 |

확인된 근거는 desktop/comment-helper/main.cjs의 utilityProcess 서버 실행, 프린터 및 트레이 관리와 desktop/comment-helper/package.json의 NSIS 설치 설정이다. Windows판 UI 파일도 설치 패키지에 포함해 웹 배포와 앱 배포 시점을 독립적으로 관리한다. 클라우드 API는 이미 배포된 앱 버전과의 호환성을 유지한다.

## 4 기술 선택과 비용 판단

Electron을 선택하는 이유는 이미 구현된 Windows 연동과 React 화면을 활용할 수 있기 때문이다. 프로그램 자체의 메모리와 설치 용량 부담은 있다. STT 성능은 별도로 GPU, 모델, 입력 오디오 처리 구조를 검증해야 하며 Electron 선택 자체가 인식 속도를 보장하지 않는다.

Tauri도 가능하지만 현재 Node 서버와 STT 실행 환경을 별도 외부 실행 파일로 구성하고 통신과 배포를 재검증해야 한다. C#으로 화면까지 전면 재작성하면 React 업무 화면을 옮기고 검증하는 비용이 커진다. 현 시점에는 Windows 통합 품질에 집중할 수 있는 기존 Electron 확장이 합리적이다.

## 5 반드시 보강할 기능

### 5 1 방송 소리와 캡처

현재 웹은 브라우저의 화면 또는 탭 공유를 사용한다. Windows 앱에서는 창과 화면 선택 및 시스템 오디오 입력을 구성해야 한다. Chrome의 특정 탭 소리만 수집하던 동작과 같다고 가정하지 않는다. 마이크, 방송 창 캡처, 시스템 소리 및 다른 앱 알림음 혼입 여부를 첫 시제품에서 확인한다.

### 5 2 판매 기록 보존

현재 판매는 로컬 저장과 클라우드 저장이 병행되지만 클라우드 실패 후 반드시 재전송하는 구조는 없다. Windows판에는 SQLite 등 영속 저장소에 작업 기록과 전송 대기열을 두는 것을 권장한다. 서버 성공이 확인된 작업만 대기열에서 제거하고 같은 작업 재시도로 중복 판매가 생기지 않게 한다. 계정별 데이터는 분리한다.

브라우저 localStorage는 새 Windows 앱과 자동 공유되지 않는다. 클라우드 원본을 우선 불러오고, 로컬에만 남은 기존 데이터는 확인 가능한 내보내기와 가져오기 절차로 이전한다. 회원 권한과 공용 STT 키를 로컬 데이터 원본으로 되돌리지 않는다.

### 5 3 새 PC의 STT 준비

GPU 감지, 엔진 준비, 모델 다운로드, 짧은 음성 테스트를 앱 안에서 진행한다. 진행률, 취소, 재시도, 파일 무결성 검사와 실패한 다운로드 정리가 필요하다. NVIDIA용 Python 런타임은 앱 전용 구성으로 설치하거나 패키징해 사용자 수동 작업을 줄인다.

인계문서의 RX 6800 XT 측정값은 특정 환경의 기록이다. 모든 GPU의 보장 성능으로 표시하지 않는다. 실제 장치 테스트를 바탕으로 모델과 연산 장치를 추천한다. 모델을 내려받은 후 로컬 STT를 사용할 수 있다는 점과 첫 준비 때 인터넷이 필요하다는 점을 구분한다.

### 5 4 기존 도우미와 동시 실행

현재 도우미 서버는 2137, Vulkan 엔진은 2139 포트를 사용한다. 새 앱을 같은 설정으로 실행하면 포트뿐 아니라 GPU와 출력 소유권이 충돌할 수 있다. 정식 앱이 엔진을 관리할 때 기존 도우미의 방송과 인쇄 상태를 확인하고 명시적으로 전환한다. 단순히 포트만 바꾸어 두 엔진을 동시에 돌리는 것으로 해결하지 않는다.

설정과 출력 이력은 제품별 userData에 보관한다. 모델은 버전과 무결성을 확인한 읽기용 공통 캐시를 선택적으로 활용할 수 있다. 현재 서버의 상대 데이터 경로와 helper 전용 하드코딩 경로를 앱 설정으로 분리한다.

### 5 5 인증과 프로그램 보안

앱 주소에 맞춰 이메일 인증과 비밀번호 재설정의 복귀 경로를 설계한다. 로그인 유지 기능은 기존 탭 세션 정책과 구분해 검토하고, 도입 시 Windows 보안 저장소와 서버 권한 재확인을 사용한다.

현재 stage-server 스크립트에는 Euler 키를 설치 리소스에 포함하는 경로가 있다. 정식 배포에서는 서버 측 서명 처리 또는 사용자를 구분하는 자격 증명 방식으로 바꾸는 것을 권장한다. 앱 화면에는 필요한 기능만 제한된 preload API로 제공하고 context isolation과 sandbox를 유지한다.

## 6 저장소와 배포 구성

같은 저장소에서 공통 화면과 판매 및 댓글과 STT 로직을 공유하고, Windows 전용 빌드 대상을 추가한다. 장기간 코드를 복사한 별도 저장소 두 개를 운영하면 버그 수정과 데이터 계약이 서로 달라질 수 있다. 제품 분리와 소스 전체 분리는 다른 결정이다.

새 appId, package name, 설치 파일 이름, 설정 폴더, 버전을 부여한다. 기존 도우미와 같은 GitHub latest.yml을 사용하지 않는다. 제품별 고정 업데이트 주소 또는 별도 릴리스 저장소를 사용한다. 태그 접두사만 달리하는 것으로 업데이트 분리가 완료되었다고 보지 않는다.

업데이트 다운로드와 실제 적용을 구분한다. 방송과 음성인식이 진행 중이거나 출력 큐가 남았으면 재시작 설치를 미룬다. 이전 버전의 데이터와 새 버전 데이터가 호환되는지 설치형 테스트로 확인한다.

## 7 권장 진행 단계

| 단계 | 완료 조건 |
| --- | --- |
| 실행 시제품 | 새 설치 후 로그인과 방송 소리 입력 및 로컬 STT와 판매 1건 저장 및 전표 출력 연결 |
| 업무용 베타 | 판매와 정산 및 배송 화면 통합, 데이터 이전, 저장 재시도, 장치 설정과 도우미 충돌 처리 |
| 정식 배포 | 개발 도구 없는 새 PC 설치, AMD와 NVIDIA 및 CPU 테스트, 장시간 방송, 업데이트와 재설치 데이터 보존 |

첫 검증은 실제 방송 소리에서 음성인식, 판매 기록, 전표 출력까지 연결하는 흐름이다. 이 경로가 안정적으로 동작하는 것을 확인한 뒤 전체 업무 화면을 통합한다.

## 8 범위와 운영 조건

완전한 인터넷 독립형 제품은 추가 범위다. 모델 준비 후 로컬 STT와 프린터 처리는 PC에서 할 수 있지만 TikTok 댓글 수집, 신규 로그인, 클라우드 동기화는 인터넷이 필요하다. 일시 단절 때의 작업 보존과 완전한 오프라인 계정 운영을 구분한다.

현재 AppDataContext의 구독 결제는 결제사 호출 없이 앱 상태를 바꾸는 구현이다. 실제 유료 결제 기능으로 제공하려면 별도 개발이 필요하다. 초기 Windows 출시 범위는 판매자의 방송, 기록, 출력, 정산 업무에 집중하는 것을 권장한다.
