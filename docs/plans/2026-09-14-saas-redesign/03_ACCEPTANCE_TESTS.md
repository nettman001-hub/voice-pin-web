# VoiceCAP 인수시험·출시 체크리스트

작성일: 2026-09-14 · 연결 문서: [재설계서](C:/dev/voice-pin-anti/docs/plans/2026-09-14-saas-redesign/01_REDESIGN.md), [작업지시서](C:/dev/voice-pin-anti/docs/plans/2026-09-14-saas-redesign/02_JUNIOR_WORK_ORDERS.md)

이 문서는 시험 계획이다. 아래 시험을 현재 실행했거나 PASS 판정했다는 뜻이 아니다. 초기 상태는 모두 NOT RUN이다. 앱 코드·운영 DB·문자 발송·프린터·Play 배포를 이번 문서 작성 중 변경하지 않았다.

## 1. 시험 준비와 판정 방법

### 1.1 필요한 환경

| 이름 | 준비 내용 |
| --- | --- |
| 시험 서버 | 운영과 분리한 API·Supabase DB·private Storage·댓글 수집 worker |
| 판매자 A | 같은 계정으로 PC-A1, PC-A2 로그인. 업무폰 Android-A 연결 |
| 판매자 B | A와 다른 workspace의 PC-B1, 별도 합성 거래·문자 |
| Android-A | 기존 Play 비공개 설치본과 업무 SIM. 업데이트 시험 전 삭제 금지 |
| 상대 시험폰 | 발송·답장·긴 문자·MMS 시험에 동의한 번호 |
| 프린터 | 실제 시험용 프린터와 출력 담당 PC |
| 외부 서비스 | Soniox 시험 자격증명, 허용된 댓글 시험 방송, 결제 sandbox |
| 장애 장치 | 네트워크 차단, 프로세스 중단, API 응답 유실, DB 오류를 시험 환경에서 주입할 방법 |

실제 고객에게 시험 문자를 보내지 않는다. 문자·Soniox·결제 비용 발생 여부를 기록한다. Phone 오프라인 직접 답장 시험은 Wi-Fi/모바일 **데이터**만 끄고 이동통신 SMS 이용은 유지한다. 비행기 모드로 이동통신까지 끈 상태와 혼동하지 않는다.

### 1.2 시험 증거와 상태

- `PASS`: 기대 결과를 실제 확인했고 증거가 있음.
- `FAIL`: 실행했지만 기대 결과와 다름.
- `BLOCKED`: 장비·권한·외부 장애 등 구체적 이유로 실행 불가.
- `NOT RUN`: 아직 실행하지 않음. PASS와 같지 않음.

자동 시험은 commit·시험 이름·실행 결과를 기록한다. 실기기 시험은 기종·Android 버전·통신사·SIM 구성·앱 versionCode·서버 버전·발신/수신 결과를 남긴다. 토큰, 전체 전화번호, 실제 고객 원문은 기록에서 마스킹한다.

```text
시험 ID / 실행 시각 / 담당자:
앱·서버·DB schema·기기 버전:
시험 입력과 재현 절차:
기대 결과:
실제 결과:
상태: NOT RUN / PASS / FAIL / BLOCKED
DB 조회·로그·화면 등 증거:
남은 이슈 / 재시험 조건:
```

시험 기록은 앞으로 `C:/dev/voice-pin-anti/docs/implementation/saas-v2/acceptance` 아래에 보관한다. 이 문서의 예상 결과를 그대로 복사한 것은 실제 증거가 아니다.

### 1.3 반드시 비교할 숫자

화면이 정상인지 외에 다음을 DB/로컬 journal과 대조한다.

| 대상 | 비교할 값 |
| --- | --- |
| 전사 | 입력 확정 chunk 수·ID·순서·원문 해시 / 로컬 보존 / 서버 ACK / 전체 조회 |
| 댓글 | 원본 이벤트 ID·시간 출처 / spool / 서버 행 / 늦은 변경 전달 |
| 판매 | 고유 command 수 / 판매 수 / 근거 수 / 자동 출력 작업 수 |
| SMS | 사용자 발송 의도 수 / job·attempt 수 / OS 송신 호출 수 / 콜백 / 상대 수신 |
| 출력 | 출력 job·attempt 수 / spool 제출 수 / 실제 전표 / UNKNOWN |
| 동기화 | 서버 최종 revision / PC·폰 로컬 revision / cursor / 남은 대기 |

## 3. 보안·기초 자료

### SEC-01. 다른 판매자 자료 접근 차단 — API/DB 통합

1. A와 B에 각각 방송·판매·전사·댓글·문자·첨부를 만든다.
2. A 토큰으로 B의 ID를 조회/수정/삭제 요청에 넣는다. B의 parent ID를 A의 새 자료에 연결하는 요청도 보낸다.
3. B의 Storage key, private Realtime 채널, sync cursor로 접근한다.

기대: 자료 유출과 변경이 없고 적절한 거절 응답이다. service-role을 사용하는 서버 API도 같은 결과다. 실패 후 B의 revision·행 수가 그대로인지 검사한다.

### SEC-02. 관리자 값·기기 ID 위조 차단 — API 통합

1. 시험 사용자 A의 수정 가능한 metadata에 관리자처럼 보이는 값을 넣는다.
2. 운영자 API 호출, 다른 기기의 claim/begin/status 보고를 시도한다.
3. 해제된 기기 토큰으로 새 작업 수신·결과 변조를 시도한다.

기대: 서버 관리 역할·등록 기기 권한 없이는 모두 거절한다. 사용자 입력 device_id만 바꿔 타 기기를 사칭할 수 없다. 기존 대기 자료는 로컬에서 삭제하지 않고 연결 복구 상태로 남는다.

### SEC-03. 같은 계정의 독립 로그인 — PC 두 대

1. A 계정으로 PC-A1/A2에 각각 로그인한다.
2. A1에서 ‘이 기기 로그아웃’을 한다.
3. A2에서 새 판매 목록 조회·허용된 관리 수정을 한다.

기대: A2 세션이 유지된다. 별도 ‘전체 기기 로그아웃’은 구분해 제공하며 선택한 경우에만 전체 범위를 처리한다.

### SEC-04. 계정 전환·비밀 노출 — PC/Android·빌드 산출물

1. A에서 미전송 항목을 만든 뒤 로그아웃하고 B로 로그인한다.
2. B 화면·API 요청에 A 원문이나 outbox가 포함되는지 검사한다.
3. 저장소·앱 패키지·일반 로그에 Soniox 장기 키, service-role, 토큰, 전체 전화번호가 노출되는지 검사한다.

기대: 작업공간별 데이터가 분리되고 A 재로그인 후 A 자료만 복구된다. 서버 장기 비밀은 클라이언트에 없다. 보안 저장소 밖의 자격증명 복사본 정리도 이행 시험 후 확인한다.

### DATA-01. 기존 DB 자료의 추가 migration — DB 통합

1. 기존 형태의 text 판매 ID, 댓글 시간, SENT 문자, 정산/입금/배송 관계를 시험 DB에 넣는다.
2. 새 migration을 적용하고 전후 행 수·원문 해시·참조 관계를 비교한다.
3. 신규 DB에도 같은 migration 전체를 적용한다.

기대: 기존 ID를 강제로 UUID로 바꾸거나 원문을 잃지 않는다. 알 수 없는 과거 시간·송신 성공은 legacy/UNKNOWN 근거를 남긴다. 과거 문자 이행으로 새 발송 job이 생성되지 않는다.

## 4. 저장·동기화

### SYNC-01. 저장 성공 후 응답 유실 — API/로컬 통합

1. 서버가 항목을 commit한 직후 응답만 차단한다.
2. 로컬 앱을 종료·재시작하고 동일 event/operation ID로 재전송한다.
3. 같은 ID에 다른 payload도 보내 본다.

기대: 같은 내용은 기존 저장 결과를 돌려주고 행/외부 작업이 늘지 않는다. 다른 내용은 409다. HTTP 200이더라도 항목 실패는 ACKED로 처리하지 않는다.

### SYNC-02. 중간 DB 오류의 전부 취소 — 실제 PostgreSQL

1. 판매 insert 뒤 출력/sync 기록 직전에 시험 오류를 주입한다.
2. 판매·출력·근거·operation·sync 표를 조회한다.
3. 오류를 제거하고 같은 operation으로 재요청한다.

기대: 실패 transaction의 일부만 남지 않는다. 재요청 성공 때 판매와 출력 작업이 정확히 하나씩 생긴다. 네트워크 호출 여러 개를 순서대로 실행한 것을 transaction으로 인정하지 않는다.

### SYNC-03. 알림 유실·로컬 적용 도중 종료 — PC/Android

1. Realtime/FCM을 끄고 서버 자료를 여러 번 변경한다.
2. 변경분 조회 후 로컬 자료 적용·cursor 저장 도중 프로세스를 중단한다.
3. 재실행하고 마지막 확정 cursor에서 동기화한다.

기대: 변경과 cursor가 함께 commit되거나 함께 취소된다. 놓친 알림이 있어도 최종 자료가 일치하고 원문이 누락되지 않는다.

### SYNC-04. 커밋 순서·늦은 데이터 — 실제 DB 동시 연결

1. A transaction을 지연시키고 B transaction이 같은 workspace에 기록하려고 하게 한다.
2. 이 동안 클라이언트가 changes를 읽도록 한다. 다른 workspace의 쓰기도 동시에 실행한다.
3. 지연을 풀고 모든 commit 이후 동기화한다.

기대: 같은 workspace 순서가 일관되며 먼저 발급된 번호 때문에 나중 commit이 영구 누락되지 않는다. 다른 workspace 전체가 같은 잠금에 묶이지 않는다. 과거 발생 시각 자료도 전달된다.

### SYNC-05. 충돌·만료 cursor·snapshot — API/PC 통합

1. PC 두 대가 같은 revision을 읽고 각기 다른 수정을 제출한다.
2. 보관 세대가 만료된 cursor로 조회한다.
3. snapshot을 페이지로 읽는 도중 서버 자료를 추가/수정한다.

기대: 후행 수정은 충돌을 알리고 사용자 변경을 보존한다. 만료 cursor는 410과 재시작 절차를 제공한다. snapshot watermark 이후 변경까지 받아 최종 상태가 맞으며 자료를 건너뛰지 않는다.

## 5. 전체 판매 멘트

### TR-01. 판매와 무관한 전체 발화 보존 — fake+PC 두 대

1. 인사·설명·일반 발화 15개와 판매 후보 5개, 총 20개 발화를 넣는다.
2. 후보 판정에 일부 실패하게 해도 원문 저장을 계속한다.
3. 방송 종료 후 PC-A2에서 해당 회차의 전체 전사를 조회·내보낸다.

기대: 20개 모두 존재한다. 판매에 연결된 5개만 저장하거나 화면의 최근 목록만 export하면 실패다. 원문 chunk 순서·내용 해시가 입력과 맞는다.

### TR-02. 긴 발화·반복 발화·partial 수정 — 공급자 어댑터 단위/통합

1. 1,200자보다 긴 확정 원문을 여러 chunk로 넣고 첫 부분이 남는지 검사한다.
2. 실제로 같은 문장을 연속 두 번 말한 것으로 서로 다른 발화 ID를 입력한다.
3. 수정되는 partial과 반복 수신된 final 이벤트를 섞는다.

기대: 긴 원문을 자르지 않고 실제 반복 발화 두 개는 남긴다. partial 수정본을 모두 확정으로 저장하거나 동일 chunk를 재조립하지 않는다. confidence 미제공 값은 null이다.

### TR-03. 발화 종료 신호 전 끊김 — 어댑터/로컬 통합

1. final token이 왔지만 endpoint는 아직 오지 않은 시점에 연결을 끊는다.
2. 앱을 종료하고 재실행한다.
3. 클라우드에 확정 chunk와 미완결 발화를 조회한다.

기대: endpoint를 못 받았어도 확정 원문이 남고 CLOSED_INCOMPLETE 같은 표시가 있다. 확정되지 않은 내용을 임의로 추가하지 않는다.

### TR-04. 네트워크 단절·회차 종료·재시작 — Windows 실제 앱

1. 확정 chunk가 로컬에 기록된 뒤 클라우드 연결을 끊는다.
2. 방송을 종료하고 앱을 재시작한다.
3. 연결 복구 후 다른 PC에서 원문을 조회한다.

기대: 이전 회차의 outbox가 남아 동일 ID로 업로드된다. 새 회차 시작이 이전 대기를 삭제하지 않는다. Soniox 자체 중단 구간은 별도 gap으로 표시한다.

### TR-05. 검색·페이지·정정·전체 export — API/관리 UI

1. 화면 한 페이지보다 많은 발화와 과거 회차를 넣는다.
2. 첫 페이지 밖의 단어를 검색하고 마지막 페이지까지 export한다.
3. 한 발화를 정정한 뒤 원문/정정문을 각각 확인한다.

기대: 페이지 밖 자료도 검색·내보내기에 포함된다. 원본을 덮어쓰지 않고 정정자·시각·이유·revision이 남는다. 다른 PC에서 같은 정정이 보인다.

### TR-06. 복구 전사의 판매 재실행 금지 — 거래 통합

1. 이미 판매가 확정된 구간과 겹치는 오디오를 복구 전사로 처리한다.
2. 과거 lease epoch에서 늦게 올라온 원문도 보낸다.
3. 판매·출력·문자 job 수를 확인한다.

기대: 복구 원문은 보존하고 검토 후보로 표시한다. 자동 판매·출력·문자가 다시 생성되지 않는다. 동일 시간의 원문을 무조건 삭제하는 것으로 해결하지 않는다.

### TR-07. 실제 Soniox와 임시 오디오 경계 — 실서비스/PC

1. 동의한 시험 방송을 실제 Soniox로 전사하고 공급자 final 출력과 저장 원문을 비교한다.
2. 중간에 연결 장애·입력 장치 제거·PC 시계 변경을 발생시킨다.
3. 임시 오디오 예산에 도달하는 시험과 처리 구간 ACK를 수행한다.

기대: capture sample 시간축이 유지된다. 미처리 구간을 텍스트 일부 ACK만 보고 삭제하지 않는다. 디스크 상한은 경고/gap으로 드러나며 Whisper가 실행되지 않는다. 실제 STT 오인식은 저장 유실과 분리해 기록한다.

## 6. 댓글 시각·수집

### CM-01. 플랫폼 시각이 있는 댓글 — API/DB

1. 플랫폼 생성 `2026-09-14T01:00:01.100Z`, 수집 `01:00:01.400Z`인 댓글을 넣는다.
2. 서버 적재를 약 2분 지연시킨다.
3. 원본 행과 한국 시각 화면을 확인한다.

기대: 세 시각이 각각 보존되고 time_source=PLATFORM이다. 화면 발생 시각은 10:00:01.100이며 저장 시각을 발생 시각으로 바꾸지 않는다.

### CM-02. 플랫폼 시각 없음·이상한 시각 — API/UI

1. 생성 시간이 없는 댓글, 단위 확인이 안 되는 원본 값, 비정상 미래 시각 예제를 넣는다.
2. 수집 시각을 따로 기록하고 화면 표시를 확인한다.

기대: 모르는 플랫폼 시간은 null, 출처는 COLLECTOR 또는 검증 상태에 맞는 값이다. UNKNOWN/SKEWED가 드러난다. 초/밀리초를 추측하거나 수집 시간을 원본 생성 시간으로 위장하지 않는다.

### CM-03. 늦은 댓글·원문 중복 — 수집/동기화 통합

1. 최신 댓글을 먼저 동기화한 후 과거 발생 시각 댓글을 새로 적재한다.
2. 동일 플랫폼 메시지를 다른 collector 인수 후 다시 전송한다.
3. 내용은 같지만 다른 실제 메시지 ID인 댓글도 보낸다.

기대: 늦은 댓글은 다음 sync에서 전달되고 화면의 과거 위치에 나타난다. 같은 플랫폼 ID는 하나, 다른 실제 ID는 각각 보존한다.

### CM-04. API 오류·수집기 재시작 — 서버 worker 통합

1. 댓글을 받은 후 API를 실패시키고 worker를 재시작한다.
2. API를 복구하고 spool을 전송한다.
3. 유효하지 않은 항목을 배치 중 하나에 넣는다.

기대: 영속 spool에 있던 댓글이 재전송된다. 성공/중복/일시 실패/영구 거절을 구분하고 실패를 전부 중복 처리하지 않는다. 영구 거절 자료도 원인 확인 가능한 보존 상태다.

### CM-05. 다중 판매자·관리 PC·클라우드 실연결 — 실제 배포 환경

1. 시험 방송 두 개를 서로 다른 workspace에서 연결한다.
2. A 관리 PC를 추가하고 방송 PC를 인계한다.
3. 수집기 두 개가 같은 회차를 인수하게 하고 플랫폼 단절도 발생시킨다.

기대: 댓글이 섞이지 않으며 관리 PC/오디오 인계 때문에 연결이 중복되지 않는다. 서버 환경에서 실제 수집이 된다. 복원 불가능한 단절 구간은 공백으로 남긴다.

## 7. Android 로컬 데이터·문자함

### AND-01. Room 저장·프로세스 종료 — 로컬 통합/실기기

1. 메시지와 발송 대기·outbox를 같은 transaction으로 저장한다.
2. transaction 직전/도중/직후에 시험 중단점을 넣고 앱을 종료한다.
3. 재실행해 관련 표를 확인한다.

기대: 서로 연결된 기록이 전부 있거나 전부 없다. 전송 중이던 작업은 journal에 따라 복구하고 단순히 QUEUED로 되돌리지 않는다.

### AND-02. 데이터 네트워크 없는 수신·재시작 — 실기기

1. Android-A의 인터넷만 끄고 상대 시험폰에서 SMS를 보낸다.
2. 앱을 다시 열고 문자함을 확인한다.
3. 인터넷 복구 후 PC 대화를 확인한다.

기대: 폰에서 즉시 또는 OS 수신 후 로컬 처리 가능한 시점에 본문을 확인할 수 있다. 네트워크가 없다고 원문을 잃지 않으며 클라우드에는 한 번만 저장된다.

### AND-03. Provider/Room 사이 중단·대량 누락 복구 — 실기기+자동화

1. Provider 기록과 Room 매핑 사이에 앱을 중단한다.
2. Receiver 처리 누락을 흉내 낸 100개 초과 SMS/30개 초과 MMS 시험 자료를 준비한다.
3. 커서 backfill 도중 새 문자가 들어오게 한다.

기대: receipt journal·원본 ID 매핑으로 중복 없이 복구한다. 최근 N개 제한 때문에 오래된 미처리 메시지가 영구 누락되지 않는다. 실제 통신사 대량 발송 대신 시험 fixture/Provider 접근 가능한 시험 환경을 사용한다.

### AND-04. 한글 장문·MMS 본문/첨부 — 실제 통신사

1. 상대폰에서 분할되는 긴 한글 SMS를 보내고 전문을 비교한다.
2. 사진과 본문이 있는 MMS를 보내 수신·다운로드·첨부 열람을 확인한다.
3. 첨부 업로드 중 인터넷을 끊고 복구한다.

기대: 누락·문자열 깨짐 없이 표시한다. MMS notification만 받고 본문까지 받았다고 처리하지 않는다. 첨부는 권한 있는 PC에서 열리고 실패 시 재시도 상태가 남는다.

### AND-05. 업무 대화 범위·기기 식별 충돌 — 로컬/서버 통합

1. 등록된 업무 고객에게서 자유 형식 답장을 받고 개인 번호에게서도 문자를 받는다.
2. 서로 다른 기기/설치의 같은 Provider 숫자 ID를 동기화한다.

기대: 업무 고객 답장은 주문 양식이 아니어도 보존한다. 동기화 동의 범위 밖 개인 문자는 자동 업로드하지 않는다. 기기·설치·SMS/MMS 종류 식별로 정상 자료가 충돌하지 않는다.

### AND-06. 문자함·직접 작성·회전·중복 클릭 — UI/fake

1. 대화 검색·미읽음·첨부·새 문자·직접 답장을 사용한다.
2. 전송 버튼을 연속 클릭하고 화면 회전·앱 재실행을 한다.
3. 기존 전송 본문과 입력창의 새 초안을 비교한다.

기대: 같은 발송 의도는 안정적인 client_message_id 하나다. 이미 만든 job의 본문은 새 입력 때문에 바뀌지 않는다. 의도적으로 같은 문자를 다시 작성해 보내는 새 작업은 허용한다.

### AND-07. 권한·기본 역할·절전·재부팅 — 실기기

1. 기본 문자 앱 역할/필요 권한을 해제하고 SIM을 제거하거나 변경한다.
2. 재부팅·절전·배터리 최적화·앱 강제 중지 상태를 각각 시험한다.
3. 앱을 다시 열고 권한/연결을 복구한다.

기대: 불가능한 동작을 성공 표시하지 않는다. 대기는 보존되고 복구 후 안전하게 재개한다. OS 강제 중지 중 백그라운드 실행이 보장된다고 판정하지 않는다. 실행 불확실 작업은 자동 송신하지 않는다.

## 8. PC 요청과 업무폰 직접 문자

### SMS-01. PC 요청·원자적 claim — API/fake/실기기

1. PC에서 동일 operation의 발송 요청을 반복한다.
2. worker 두 개 또는 폰의 병렬 작업이 같은 job을 claim하게 한다.
3. 지정 기기와 다른 기기로 begin을 시도한다.

기대: 서버 job은 하나이며 지정 Android의 한 attempt만 실행 가능하다. PC의 접수 화면과 실제 송신 상태를 구분한다.

### SMS-02. 폰 직접 답장·클라우드 업로드 — 실기기/서버

1. Android 문자함에서 고객에게 직접 답장한다.
2. local job이 DEVICE_OWNED인지 확인한다.
3. 서버 업로드 이벤트를 반복하고 PC 대화를 조회한다.

기대: 실제 송신은 폰에서 한 번 수행하고 서버는 이력만 편입한다. 서버 CLOUD_OWNED 발송 대기나 다른 폰의 job을 생성하지 않는다.

### SMS-03. 제출·SENT·DELIVERED 구분 — fake+실기기

1. SmsManager 호출 반환 뒤 sent callback을 지연시킨다.
2. sent 성공, 실패, delivery 미지원/미도착을 각각 시험한다.
3. 실제 통신사와 상대 시험폰 결과를 대조한다.

기대: 호출 반환만으로 SENT가 되지 않는다. 전송 성공 근거와 배달 성공 근거를 구분한다. delivery가 없으면 DELIVERED를 지어내지 않는다.

### SMS-04. 송신 경계의 앱 중단 — fake 장애 주입+실기기

1. claim 후 begin 전, journal commit 후 OS 호출 전, OS 호출 후 결과 저장 전, 콜백 수신 후 cloud ACK 전을 각각 중단한다.
2. 앱/worker를 재시작하고 동일 job을 다시 조회한다.

기대: 실행 전임이 확인된 경우만 안전하게 재개한다. 실제 제출 여부가 모호한 경우 UNKNOWN으로 남고 자동 재발송하지 않는다. 저장된 콜백은 같은 이벤트로 업로드한다. ‘상대가 한 번만 받았다’와 ‘전송 결과가 확정됐다’를 구분한다.

### SMS-05. multipart 일부 실패·콜백 역전 — 자동화+실기기

1. 한글 장문을 여러 part로 분할하고 한 part만 실패시킨다.
2. 같은 콜백을 두 번, delivery를 sent보다 먼저, 예전 attempt 결과를 새 attempt 뒤에 전달한다.

기대: 모든 part 성공 전에는 전체 SENT가 아니다. 부분 실패를 표시하고 전체 문자를 조용히 재발송하지 않는다. 중복/늦은 이벤트가 새 상태를 퇴행시키지 않는다.

### SMS-06. lease 만료·취소·전송 소유권 — 서버/로컬 통합

1. 실행 시작 전 CLAIMED job의 lease를 만료시킨다.
2. SUBMITTING 이후에도 lease를 만료시키고 다른 기기가 claim하게 한다.
3. begin과 취소 명령을 동시에 보내고 PHONE origin의 job에도 서버 배정을 시도한다.

기대: 실행 시작 전 안전한 상태만 정책대로 재인수한다. SUBMITTING 이후는 만료만으로 재배정하지 않는다. 취소가 먼저 확정되면 begin 거절, begin이 먼저면 ‘취소 보장 불가’ 응답이다. PHONE job은 서버 재배정 대상이 아니다.

### SMS-07. 이중 SIM·교체·잘못된 회선 — 실기기

1. 지원 대상 이중 SIM 폰에서 업무 회선을 지정해 보낸다.
2. SIM 이동·교체로 subscription ID가 달라지는 상황을 시험한다.
3. 유효하지 않은 대상 회선으로 발송을 시도한다.

기대: 잘못된 회선으로 조용히 보내지 않는다. 업무 회선의 영구 ID와 현재 SIM 매핑을 구분하고 확인이 필요하면 대기 상태로 남긴다.

### SMS-08. UNKNOWN 확인·사용자 재발송 — UI/fake

1. UNKNOWN 문자를 만들어 대화/대기 목록에서 확인한다.
2. 자동 worker를 여러 번 실행한다.
3. 사용자가 중복 가능성 안내를 확인하고 명시적으로 재발송한다.

기대: 자동 송신 호출은 늘지 않는다. 사용자 재발송은 새 attempt·원작업 연결·사유·시각을 남긴다. 이전의 불확실 기록은 삭제하지 않는다.

### SMS-09. 인터넷 없는 직접 답장·푸시 유실 — 실제 통신사

1. Android의 데이터 인터넷만 끄고 고객에게 직접 답장한다.
2. 상대폰이 실제 수신하는지 확인하고 Android를 재시작한다.
3. 인터넷을 켜되 FCM을 일부러 누락시킨 뒤 앱 시작/WorkManager 동기화를 수행한다.

기대: 로컬에 발송 결과가 남고 PC에 한 번만 공유된다. 뒤늦은 업로드가 새 발송을 만들지 않는다. PC에서 온 미실행 대기는 다시 발견되지만 불확실 작업은 자동 재실행하지 않는다.

## 9. 기존 Play 앱 업데이트

### UP-01. 등록 앱·서명·versionCode — 배포 전 점검

1. applicationId `shop.voicecap.smsbridge`가 유지됐는지 비교한다.
2. Play 전체 트랙 최고 versionCode와 새 값을 비교한다.
3. AAB 업로드 키와 Play App Signing 설치 서명 체계를 확인한다.

기대: 같은 등록 앱의 업데이트다. 새 versionCode가 최고값보다 크다. 기존 키를 임의 재생성하지 않았다. 승인/비공개 테스트 완료는 이미 확보한 사용자 사실로 기록한다.

### UP-02. 실제 기존 설치본 위 업데이트 — Play 비공개 트랙

1. 이전 Play 설치 앱의 연결·동의·업무 연락처·문자·첨부를 기록한다.
2. 앱을 삭제하지 않고 새 비공개 버전으로 업데이트한다.
3. 기본 문자 역할, 연결 기기 ID, workspace, 과거 대화, 직접 답장, PC 요청을 확인한다.

기대: 설정·자료가 보존된다. 재연결이 불가피한 특별한 이유가 없다면 업데이트만으로 새 기기가 되지 않는다. debug 신규 설치 시험은 이 항목을 대체하지 못한다.

### UP-03. 설정/Room 이행 중단·기존 SENT — 자동화+실기기

1. SharedPreferences→새 저장소, Room schema migration 중 중단점을 넣는다.
2. 기존 uploaded 표식과 SENT/SENDING 기록을 포함한다.
3. 업데이트를 재개하고 클라우드 발송 작업 수를 확인한다.

기대: 이행을 다시 실행해도 중복되지 않고 원본이 보존된다. 기존 SENT는 legacy 검증 상태로 남으며 과거 문자를 재전송하지 않는다. destructive fallback이 없다.

### UP-04. 구형·신형 클라이언트 공존/전환 — 서버+앱

1. 시험 workspace에서 구버전 PC/폰과 신버전을 잠시 함께 연결한다.
2. workflow_version 전환 전후로 동일 업무 요청을 발생시킨다.
3. 구형 실행 경로의 재접속과 이행 실패를 시험한다.

기대: 호환 어댑터를 거치거나 구형 위험 실행이 차단된다. 한 SMS·판매·출력을 구형/신형이 각각 실행하지 않는다. 읽기 호환과 실행 권한을 구분한다.

## 10. Windows·방송 권한·판매·출력

### WIN-01. 로컬 서버 없는 실행·영속화 — 설치/재시작

1. 새 Windows 앱을 설치하고 UI 실행 경로·필요 프로세스를 확인한다.
2. 인터넷 없이 캐시/대기를 조회하고 앱을 재시작한다.

기대: 화면 실행에 `127.0.0.1:2137`이나 Node HTTP 서버가 필요하지 않다. SQLite 대기·최근 업무를 유지하며 오프라인과 서버 미확정 상태를 표시한다.

### WIN-02. Soniox만 현재 제공·Qwen 확장 경계 — 패키지/코드/실행

1. STT 선택 UI, 설치 파일, 실행 프로세스, provider 구현을 확인한다.
2. Soniox를 연결하고 장애를 발생시킨다.

기대: 현재 필수 공급자는 Soniox다. Whisper/Qwen 모델을 설치·실행하지 않으며 자동으로 다른 유료 공급자에 전환하지 않는다. 후속 provider 인터페이스는 있어도 미구현 엔진을 사용 가능으로 표시하지 않는다.

### HOST-01. 두 PC 동시 방송 시작 — 서버 동시성

1. A1/A2에서 같은 회차를 동시에 시작한다.
2. 서로 다른 회차를 만들어 판매자별 동시 방송 한도 1도 우회하려 시도한다.

기대: 허용된 방송 PC 한 대만 활성 권한을 얻는다. UI 버튼 비활성화만이 아니라 서버에서 제한한다. 관리 PC 조회는 계속 가능하다.

### HOST-02. 인계·지연 원문·이전 epoch — 서버/PC

1. A1의 lease를 만료/인계하고 A2가 새 epoch를 받는다.
2. A1에서 늦게 도착한 원문과 새 자동 판매 요청을 보낸다.

기대: 유효한 과거 자료는 복구 원문으로 보존하되 이전 epoch의 자동 판매는 거절한다. 동일 회차 댓글 연결을 불필요하게 새로 만들지 않는다.

### HOST-03. 시계 변경·수면·단기 키 — PC/인증

1. PC 시계를 바꾸고 절전 후 복귀한다.
2. lease/단기 접속 키가 만료된 상태에서 새 연결을 시도한다.
3. 이미 열린 Soniox 스트림과 새 접속 제한의 차이를 확인한다.

기대: lease 판정은 서버 시각, 오디오 진행은 sample/monotonic 기준이다. 새 권한 없는 실시간 판매를 만들지 않는다. 키 만료가 기존 스트림을 즉시 끊는다고 잘못 가정하지 않는다.

### SALE-01. 같은 판매 명령 반복 — API/실제 DB

1. 같은 operation으로 확정을 10회 요청하고 동시 요청도 섞는다.
2. 판매·근거·출력 작업 수를 센다.

기대: 확정 판매 하나, 해당 자동 출력 작업 하나다. 재시도 때문에 결제/문자 등 후속 효과가 늘지 않는다.

### SALE-02. 공동 수정 충돌 — PC 두 대

1. 같은 판매 revision을 두 PC에서 연다.
2. 수량/단가를 각각 수정하고 순서대로 저장한다.

기대: 두 번째 요청이 첫 변경을 조용히 덮어쓰지 않는다. 서버 최신값과 내 미반영 변경을 보여준다.

### SALE-03. 모호한 구매자·뒤늦은 정정 — 업무 통합

1. 비슷한 닉네임, 같은 금액, 지연 댓글을 포함한 후보를 만든다.
2. 판매 정정/취소와 원문 정정을 각각 수행한다.

기대: 시간/이름 하나만으로 잘못 확정하지 않고 검토가 가능하다. 원래 판매·전사·댓글·정정 이력이 남는다.

### SALE-04. 파서 재시도·복구 자료 — worker 통합

1. 같은 발화의 후보 처리 worker를 중단·재실행한다.
2. 복구 전사와 새 정상 발화를 함께 처리한다.

기대: 동일 intent의 후보가 중복 생성되지 않는다. 복구 자료는 검토 대상이며 새 정상 판매와 구분한다. 전체 원문은 둘 다 보존한다.

### PRINT-01. 출력 담당 독점 — fake+실제 프린터

1. 지정 출력 PC와 다른 PC가 동시에 claim한다.
2. 동일 job을 재조회하고 실제 전표를 확인한다.

기대: 지정 기기의 한 실행만 가능하다. 관리 PC 접속만으로 중복 출력하지 않는다.

### PRINT-02. spool 경계 중단·오프라인 프린터 — 실제 장치

1. 서버 begin 후/로컬 journal 후/spool 제출 후에 각각 앱을 중단한다.
2. 프린터 오프라인·용지 없음 상태도 시험한다.

기대: 제출과 종이 배출을 구분한다. 불확실하면 UNKNOWN으로 남기고 자동 재출력하지 않는다. UI가 종이 배출을 보장한다고 표시하지 않는다.

### PRINT-03. 명시적 재출력 — PC/서버

1. 실패/UNKNOWN/기출력 항목을 열고 사용자가 재출력을 요청한다.
2. 이유·원작업·새 작업을 확인한다.

기대: 명시적 새 작업만 실행되고 감사 이력이 남는다. 원래 상태를 지워 최초 출력처럼 꾸미지 않는다.

## 11. 전체 업무·상용 운영

### MULTI-01. 판매자 실제 하루 흐름 — 두 PC+Android+프린터

1. A1에서 방송 시작 → Soniox 전체 멘트/댓글 수집 → 상품 캡처 → 판매 확정 → 전표 출력.
2. A2에서 같은 자료 조회 → 판매 검토 → 정산 문자 요청.
3. 업무폰에서 발송 결과 확인 → 고객 답장 수신 → 업무폰 직접 답장.
4. A2에서 입금 확인·배송 처리 → 회차 종료 → 전체 전사/댓글 조회·export.

기대: 기기별 자료가 일치한다. 방송은 한 대만 담당하고 관리 PC는 캡처 없이 업무를 수행한다. 고객 답장과 폰 직접 답장이 같은 업무 대화에 남는다.

### MEDIA-01. 캡처·사진·MMS 업로드 복구/권한 — PC/폰/Storage

1. 화면 캡처, Android 상품사진, MMS 첨부를 각각 만든다.
2. 업로드 도중 인터넷을 끊고 앱을 재시작한다.
3. 다른 PC와 다른 판매자로 열람을 시도한다.

기대: 파일이 실제 확인된 뒤 AVAILABLE이 된다. 로컬 미전송 파일이 남고 복구 업로드가 가능하다. 같은 workspace의 허용 사용자만 볼 수 있다. 서명 URL 만료 후 재인증 발급이 필요하다.

### BIZ-01. 정산서 발송 뒤 판매 금액 변경 — 업무 통합

1. 판매로 정산서를 생성하고 시험 고객에게 보낸다.
2. 판매 단가/수량을 수정한다.

기대: 기존 발송 문자·정산 금액이 보존되고 재확인 필요 상태가 나온다. 이미 발송한 내용이 새 금액으로 몰래 바뀌지 않는다.

### BIZ-02. 입금·배송·취소 공동 작업 — PC 두 대+Android

1. 같은 고객의 서로 다른 주문과 같은 금액 입금 후보를 만든다.
2. 두 기기에서 입금 확인·배송/취소를 동시에 변경한다.

기대: 애매한 입금을 자동 확정하지 않는다. revision 충돌을 처리하며 원래 주문·입금·배송 근거가 남는다. 오래된 전체 배열로 새 메시지/배송을 덮어쓰지 않는다.

### BIZ-03. AI 실패·지연·재시도 — worker 통합

1. AI를 timeout/오류로 만들고 같은 작업을 재시도한다.
2. 그동안 전사·댓글을 계속 수집하고 사람이 후보를 검토한다.

기대: 원문 저장과 수동 업무가 계속 가능하다. AI 지연 동안 DB 잠금을 오래 유지하지 않고 작업·비용·적용 이력을 남긴다. 결과를 중복 적용하지 않는다.

### OPS-01. 결제·이용권·webhook 중복 — 공급자 sandbox

1. 클라이언트만 결제 완료를 주장해 본다.
2. 정상 서명 webhook, 위조 서명, 같은 webhook 반복, 환불/해지를 시험한다.

기대: 검증된 서버 결과만 이용권을 바꾼다. 중복 webhook이 금액/기간을 반복 추가하지 않는다. 실패/환불을 실제 상태로 반영한다.

### OPS-02. 한도·사용량·관측·비밀 — 서버/모니터링

1. 시험 한도를 넘겨 새 Soniox 세션을 요청한다.
2. 이미 받은 원문·문자 상태·판매 대기를 업로드한다.
3. 운영 화면과 로그를 검사한다.

기대: 정책에 따라 새 유료 사용만 제한하고 기존 자료를 버리지 않는다. 대기/ACK/UNKNOWN/원가가 workspace별로 보인다. 로그에 비밀·원문이 기본 노출되지 않는다.

### OPS-03. 백업·파일 복구·export·삭제 — 별도 복원 환경

1. DB 백업과 Storage 파일을 각각 복원한다.
2. 전사·댓글·문자·판매 참조와 파일 해시를 비교한다.
3. 합성 workspace export와 정해진 보관/삭제 절차를 시험한다.

기대: DB 복원만으로 파일도 자동 복원된다고 가정하지 않는다. 원문·참조·첨부가 일치하고 다른 workspace는 영향을 받지 않는다. 실제 복원 시간과 복원 가능한 시점을 기록한다.

### OPS-04. Windows 업데이트·지원 버전 — 설치/실기기

1. 서명 패키지로 업데이트하고 SQLite migration을 수행한다.
2. 방송/출력 실행 중 업데이트를 제안하고 schema 이행 실패도 주입한다.

기대: 진행 중 업무를 강제 종료하지 않는다. 이행 실패 때 원본을 보존한다. 서버의 최소 지원/실행 버전 안내가 명확하며 구형 위험 경로를 조용히 허용하지 않는다.

### LOAD-01. 장시간·다중 판매자·폭주 후 복구 — 합성 부하

1. 우선 workspace 10개 × PC 3대, workspace당 댓글 10개/초·전사 chunk 2개/초를 30분 실행한다. 이후 예상 판매 규모에 맞게 단계적으로 늘린다.
2. 3배 순간 입력, DB 5분 장애, 수집기/worker 재시작을 넣는다. 실제 SMS는 fake로 대체한다.
3. 대표 PC/폰은 한 방송 길이의 연속 시험을 하고 메모리·배터리·DB 크기·큐 지연을 측정한다.

기대: 시험 입력 대비 영속 원문 누락 0, 중복 판매/외부 실행 0, 장애 후 큐가 계속 줄어 최종 일치한다. 공급자 자체 단절로 받지 못한 구간은 gap으로 구분한다. 정상 네트워크의 관리 화면 반영 p95 3초 이내를 초기 목표로 측정하되, 이는 측정 전 보장값이나 수용 고객 수 확정값이 아니다. 방송 길이·회복 시간·동시 판매자 한도는 시험 결과와 배포 자원으로 확정한다.

### ROLL-01. 제한 출시·중단·운영 대응 — 배포 리허설

1. 시험 workspace 하나를 v2로 전환하고 구형 대기/불확실 작업을 매핑한다.
2. 오류를 가정해 신규 자동 판매/문자/출력 실행을 중지한다.
3. 원문 보존·대기 조회·수동 확인·수정 버전 배포 절차를 수행한다.

기대: 오류 중단이 대기 기록 삭제로 이어지지 않는다. 구버전 두 번째 실행 경로를 열어 복구하려 하지 않는다. 담당자·연락/지원 절차·필요 로그·고객 안내 범위가 정해져 있다.

## 12. 출시 직전 체크리스트

- [ ] 전체 확정 멘트가 다른 PC의 전체 조회/export와 대조됐다.
- [ ] 댓글의 발생/수집/적재 시각과 없는 원본 시간 표시를 확인했다.
- [ ] Whisper는 포함되지 않았고 Qwen은 후속 인터페이스만 있다.
- [ ] A/B 작업공간 격리·독립 로그아웃·기기 위조 시험이 통과했다.
- [ ] PC SQLite와 Android Room의 재시작/동기화 복구가 통과했다.
- [ ] 폰 직접 답장이 서버 재발송으로 이어지지 않는다.
- [ ] 실제 한글 SMS 왕복·장문·MMS 수신·직접 답장이 통과했다.
- [ ] 콜백·부분 실패·UNKNOWN·SIM 교체를 확인했다.
- [ ] 기존 Play 설치 앱 위 업데이트로 연결·동의·이력을 보존했다.
- [ ] 실제 프린터 제출 경계와 명시적 재출력을 확인했다.
- [ ] 정산·입금·배송·사진·AI 장애의 회귀 시험을 마쳤다.
- [ ] 구형/신형 실행 경로가 같은 업무를 중복 수행하지 않는다.
- [ ] 실제 결제 sandbox·이용권·사용량·백업/파일 복원을 시험했다.
- [ ] 서명 패키지·배포 중단·자료 보존·고객 지원 절차가 준비됐다.
- [ ] 필수 시험의 FAIL/BLOCKED/NOT RUN을 숨기지 않고 출시 범위를 판정했다.

최종 완료 보고에는 PASS 개수뿐 아니라 미시험 항목과 출시 제한을 함께 적는다. ‘기존 문서에 PASS라고 적혀 있음’이나 ‘화면이 열림’은 이 체크리스트의 통과 근거가 아니다.
