# 댓글터치 판매방식 · VoiceCAP 판매 앱 설계

Oct 21, 2026 · @학현님

## 요약

폰은 "누가, 얼마"만 정하고, PC는 지금처럼 "전표 출력과 화면 캡처"를 맡고, 서버는 판매를 저장하는 구조를 추천합니다. 음성인식(소닉스), 4단 멘트 규칙, AI 판단은 이 방식에서 전혀 쓰지 않습니다.

- **댓글을 폰으로 보내는 길:** PC 라이브 청취 홈은 지금도 댓글 도우미에게서 모든 댓글을 실시간으로 받고 있습니다. 이 댓글을 PC와 폰의 직접 연결(WebRTC)로 바로 보냅니다. Supabase는 처음 연결할 때와, 직접 연결이 안 될 때 예비 길로만 씁니다. 댓글은 DB에 저장하지 않으므로 "구매·취소 댓글만 올린다"는 규칙을 그대로 지키고, 댓글 도우미는 고치지 않습니다.
- **판매 확정:** 폰에서 확정하면 서버에 새 기능(터치 판매 저장)으로 한 건 저장하고, 고른 댓글 1개만 근거로 함께 올립니다.
- **전표와 캡처:** PC 화면은 이미 서버의 판매 변경을 실시간으로 받고 있습니다. 새 터치 판매가 오면 PC가 즉시 전표를 뽑고, 확정 4초 뒤에 틱톡 화면 지연(자동 측정)을 더한 시각에 공유 중인 틱톡 화면을 캡처해 그 판매의 사진 1장으로 붙입니다.
- **"확인 대기"는 지금 판매 상태값이 아닙니다.** 라이브 청취 홈의 목록 제목("판매 내역 · 확인 대기")일 뿐입니다. 새 상태를 만들지 않고 기존 "자동저장" 상태에 이미 있는 출처 "앱"을 붙여 저장하면, 구매자 합계, 문자 연결, 정산이 코드 수정 없이 그대로 동작합니다.
- **앱은 웹앱으로 만듭니다.** 폰 브라우저에서 판매자 계정으로 로그인하고, 홈 화면에 "VoiceCAP 판매"로 추가해 앱처럼 씁니다. 지금 웹의 코드를 그대로 쓰고, 안드로이드와 아이폰 모두 되며, Vercel 배포만으로 반영됩니다. 처음에는 안드로이드 전용 앱을 추천했지만, 2026-10-21 학현님 질문을 받고 웹앱으로 바꿨습니다.
- **고객 숫자:** 청취 홈이나 댓글터치를 시작할 때 고객별 총구매금액, 구매횟수, 미이행 횟수 표를 PC에 한 번 만들고, 댓글마다 틱톡 사용자 번호(없으면 같은 닉네임)로 찾아 댓글 끝에 붙입니다. 폰에는 PC가 댓글과 함께 숫자를 보냅니다.
- **관리자 화면:** 관리자 메뉴에 "판매 폰 연결 현황"을 두고, 판매자별 직접·예비 연결과 장애 기록, 이번 달 Supabase 메시지 추정치를 봅니다.

코드에서 확인한 사실은 2026-10-21 main(51e5daf) 기준입니다.

폰 화면 시안(눌러 볼 수 있는 5개 화면, 이름과 금액은 예시): [VoiceCAP 판매 폰 화면](https://claude.ai/artifact/LFuTcc14oUAKKHs25xQqD1)

## 전체 구조

판매자가 손으로 하는 일은 폰에서 구매자를 누르고 가격을 넣는 것뿐이고, 나머지는 자동으로 이어집니다. PC는 댓글 전달, 전표, 캡처를 맡고, 서버는 판매를 저장하고 PC와 폰에 알려 줍니다.

댓글은 ②처럼 PC에서 폰으로 직접 가고, Supabase는 처음 연결할 때와 직접 연결이 안 될 때만 씁니다. DB에 남는 것은 ④에서 판매와 함께 올라가는 댓글 1개뿐입니다.

## PC 라이브 청취 홈: 판매방식 옵션

라이브 청취 홈 상단에 **판매방식: \[음성인식\] \[댓글터치\]** 선택을 두고, 고른 값은 판매자 계정 설정에 저장합니다. 방송(판매) 중에는 선택을 잠그고, 판매를 멈춘 뒤에만 바꿀 수 있게 합니다.

댓글터치를 고르면 화면이 이렇게 바뀝니다.

- **청취 시작 버튼 → "판매 시작" 버튼.** 누르면 회차를 시작하고, 틱톡 라이브 창 화면 공유를 요청하고, 댓글 도우미에 댓글 수집을 켜고, 받은 댓글을 폰에 직접 연결로(안 되면 Supabase 채널로) 전달하기 시작합니다. 틱톡 탭 소리는 음성인식에는 쓰지 않지만 틱톡 화면 지연을 재는 데 쓰므로, 공유 창의 "탭 오디오도 공유"는 켜 둡니다(아래 "틱톡 화면 지연 보정").
- **꺼지는 것:** 소닉스 연결, 파형 표시, 자막, 닉네임 힌트 전송, 4단 멘트·보류 판단, AI 보류 확인, "캡처하세요" 짝짓기. 음성 사용량과 AI 비용이 0이 됩니다.
- **새로 생기는 상태 줄:** 판매 폰 접속(접속 중인 폰 수, 직접/예비 연결, 마지막 신호 시각), 댓글 도우미, 프린터, 화면 공유, 틱톡 지연("5.2초 자동" 또는 "6초 설정값"). 하나라도 끊기면 빨간 표시를 냅니다.
- **판매 내역 · 확인 대기 목록은 그대로** 쓰고, 각 판매에 "앱" 출처 표시, 전표 상태(출력됨 / 대기 / 실패), 캡처 상태(n초 뒤 촬영 예정 / 완료 / 없음)를 보여 줍니다. 지금도 "앱" 출처 표시 칸이 있어서 자리가 마련돼 있습니다.
- **PC에서도 수동 등록은 계속 가능**하게 둡니다. 폰이 고장 나면 PC에서 바로 입력할 수 있어야 하기 때문입니다.

코드상 주의할 점이 하나 있습니다. 지금의 화면 캡처 함수(LiveContext의 captureCurrentScreen)는 "청취 중"일 때만 동작하도록 막혀 있습니다. 댓글터치에서는 "판매 진행 중"일 때도 캡처할 수 있게 조건을 넓혀야 합니다.

## 폰에서 여는 법과 회차

폰은 앱을 설치하지 않고 브라우저로 판매 화면 주소를 열어, PC와 같은 판매자 계정으로 로그인합니다. "자동 로그인"을 켜 두면 다음부터는 로그인 없이 바로 열립니다.

1. PC 라이브 청취 홈의 "판매 폰 열기" 버튼을 누르면 판매 화면 주소가 QR로 나옵니다.
2. 폰 카메라로 QR을 찍어 열고, 판매자 계정으로 로그인합니다.
3. 브라우저 메뉴의 "홈 화면에 추가"로 "VoiceCAP 판매" 아이콘을 만들면 다음부터 앱처럼 전체 화면으로 열립니다. 지금 웹에는 아이폰용 설정만 있어서, 안드로이드용 앱 정보 파일(manifest)을 하나 추가합니다.
4. 판매 화면은 라이브 청취 홈과 다른 가벼운 페이지입니다. 음성 청취, 화면 캡처, 댓글 도우미 연결을 하지 않으므로 PC의 청취·캡처와 부딪히지 않습니다.

**회차는 폰이 만들지 않고 PC를 따라갑니다.** PC에서 "판매 시작"을 누르면 폰 상단에 "10/21 1회차 판매 중"이 뜨고, PC에서 회차가 없으면 폰에는 "PC에서 판매 시작을 눌러 주세요"만 보입니다. 이렇게 해야 폰과 PC가 다른 회차에 판매를 넣는 일이 없습니다.

판매하기 화면이 켜져 있는 동안에는 브라우저의 화면 켜두기 기능(Wake Lock)으로 폰 화면이 꺼지지 않게 합니다. 안드로이드 크롬과 최신 아이폰 사파리에서 됩니다. 이 폰에서는 판매자 계정 전체(정산, 문자)가 열리므로, 직원이 이 폰을 쓴다면 나중에 판매 화면만 열리는 판매 전용 로그인을 따로 만듭니다. 폰은 한 대만 쓰는 것을 기본으로 합니다.

판매 폰은 문자 앱이 깔린 안드로이드 폰입니다(2026-10-21 학현님 답변). 문자 앱은 뒤에서 계속 문자를 받고, 판매 화면은 같은 폰의 크롬에서 엽니다. 방송 중 고객 문자 알림이 화면 위쪽을 잠깐 가릴 수 있어서, 확인·확정 버튼과 선택한 구매자는 화면 아래쪽에 둡니다. 화면이 계속 켜져 있으므로 방송 중에는 충전기를 꽂아 둡니다. 필요하면 나중에 문자 앱에 "판매 화면 열기" 버튼을 달 수 있습니다.

## 판매하기 탭

가장 큰 위험은 댓글이 빠르게 올라가서 엉뚱한 사람을 누르는 것입니다. 그래서 만지는 순간 목록을 멈추고, 확정 전에 고른 사람을 크게 보여 주는 것을 설계의 중심으로 두었습니다.

### 화면 구성 (위에서 아래로)

1. **탭:** \[판매내역\] \[판매하기\]
2. **상태 줄:** "10/21 1회차 · 댓글 ● 직접 · PC ● · 12건 / 214,000원". PC 신호가 일정 시간(직접 연결 5초, 예비 길 12초) 넘게 끊기거나 PC가 댓글 도우미·틱톡 연결 끊김을 알려 오면 빨간 글자로 바뀝니다. PC는 댓글이 없을 때도 몇 초마다 신호를 보내므로 조용한 방송에서 잘못 빨개지지 않습니다. 예비 길로 받는 중이면 "직접" 대신 "예비"가 뜹니다.
3. **검색·필터:** 닉네임 검색창, \[전체\] \[구매댓글만\] 칩. "구매댓글"은 지금 쓰는 구매 의사 판별(저요, ㅈㅇ, 구매, 제가 살게요 등)을 그대로 씁니다.
4. **실시간 댓글 목록:** 틱톡처럼 새 댓글이 아래에 붙고 자동으로 내려갑니다. 한 줄에 시각(작게), 닉네임(크게), 댓글 내용, 끝에 고객 숫자(예: "12건/4회 45.5만 · 오늘 2건", 아래 "댓글 옆 고객 숫자" 참고)를 넣고, 구매 댓글은 배경색을 넣고 판매자가 누르기 전까지 깜빡입니다(아래 "목록 동작").
5. **하단 고정 바:** "선택: 하니 · '저요'  \[취소\] \[확인\]".

### 목록 동작

- 손가락이 목록에 닿거나 댓글을 선택하면 자동 스크롤이 멈추고, 아래에 "새 댓글 12개 ↓" 버튼이 뜹니다. 누르면 다시 따라갑니다.
- 댓글을 한 번 누르면 선택(강조색), 다른 댓글을 누르면 선택이 바뀝니다. 한 판매에 구매자는 한 명입니다.
- **구매 댓글 깜빡임:** 구매 의사를 밝힌 댓글("구매댓글" 필터와 같은 판별)은 한 줄 전체가 눈에 띄는 노란색으로 깜빡이고, 판매자가 누를 때까지 계속됩니다. 구매 댓글 두 개가 함께 깜빡이는 중이어도 그중 하나만 누르면 모든 깜빡임이 멈추고, 누른 댓글만 선택 표시(파란 테두리, 체크)가 남습니다. 누르지 않은 구매 댓글은 깜빡임만 멈추고 "구매" 표시는 남아 있어서, 나중에 눌러 팔 수 있습니다. 깜빡이지 않는 댓글을 누르는 것은 깜빡임에 영향이 없고, 새 구매 댓글이 오면 그 댓글만 다시 깜빡입니다. 판매가 확정된 댓글은 "판매됨"으로 바뀔어 깜빡이지 않습니다. 깜빡임은 1초에 한 번 정도로 하고, 폰의 "애니메이션 줄이기"가 켜져 있으면 깜빡이지 않고 진한 노란 배경만 유지합니다. 폰 판매 화면에만 적용하고, PC 음성 방식의 댓글 목록은 그대로 둡니다(2026-10-21 학현님 요청).
- 닉네임을 길게 누르면 그 사람 댓글만 모아 봅니다. 같은 닉네임이 두 명이면 닉네임 아래에 틱톡 아이디를 작게 보여 구분합니다.
- 화면에는 최근 500개 정도만 두고, 더 오래된 댓글은 검색으로 찾게 합니다.

### 가격 입력 화면 (확인을 누른 뒤)

- 맨 위에 구매자를 크게: "하니님" + 고른 댓글 내용.
- 큰 숫자 키패드(0\~9, 점, 지우기). 판매자가 방송에서 말하는 대로 **1.5를 누르면 "15,000원"이 바로 아래에 크게** 보입니다.
- 변환 규칙(제안): 100 미만의 숫자는 만원 단위(1.5 → 15,000원, 3 → 30,000원, 0.8 → 8,000원), 1,000 이상은 원 그대로(15000 → 15,000원). 100\~999는 모호하므로 확정 버튼을 막고 "단위를 확인해 주세요"를 띄웁니다.
- **최근 가격 칩** 3개(예: \[1.5\] \[1.0\] \[2.8\]). 같은 상품을 연달아 파는 일이 많아서 한 번 누르면 끝납니다.
- 수량은 기본 1개이고 \[-\] \[+\]로만 바꿉니다. 상품명은 PC에 등록된 현재 상품이 있으면 자동으로 붙고, 없으면 비워 둡니다.
- &#91;확정\] 버튼은 화면 맨 아래에 크게 둡니다.

### 확정 후

- 누르는 즉시 버튼이 잠기고 "저장 중"이 뜹니다. 보통 1초 안에 서버가 답합니다.
- 저장되면 짧게 진동하고 "013 하니 15,000원 저장 · 전표 출력 중 · 9초 뒤 캡처"를 2초 보여 준 뒤, 선택을 풀고 댓글 목록으로 돌아갑니다.
- 같은 구매자·같은 가격을 10초 안에 다시 확정하면 "방금 같은 판매가 있습니다. 하나 더 저장할까요?"를 물어봅니다. 실제로 두 개를 사는 경우가 있으므로 막지는 않습니다.

## 판매내역 탭

판매내역 탭은 PC의 "판매 내역 · 확인 대기" 목록과 같은 데이터를 보여 줍니다. PC에서 고치면 폰에도, 폰에서 고치면 PC에도 바로 반영됩니다.

- **상단 합계:** 이번 회차 건수와 금액. \[건별\] \[구매자별\] 보기 전환. 구매자별은 PC 판매 내역 목록과 같은 합계 규칙(보이는 판매는 모두 합계에 들어감)을 씁니다.
- **목록(최신이 위):** 번호, 닉네임, 금액, 시각, 전표 상태(출력됨 / 대기 / 실패), 캡처 썸네일. 캡처는 "4초 + 틱톡 지연" 뒤에 찍혀 올라오므로 보통 확정 10초 안팎 뒤에 나타납니다.
- **항목을 누르면 상세:** 큰 캡처 사진, 근거 댓글, \[가격 수정\] \[구매자 변경\] \[전표 다시 출력\] \[다른 장면\] \[캡처 다시 찍기\] \[삭제\]. 동작은 아래 "수정, 삭제, 취소"에 적었습니다.
- **보내는 중 표시:** 인터넷이 끊겨 아직 서버에 못 간 판매는 맨 위에 "보내는 중" 표시로 따로 보여 줍니다.

폰도 PC와 똑같이 로그인한 계정으로 판매 표의 실시간 변경을 구독합니다. PC가 지금 쓰는 구독 코드를 그대로 씁니다. 연결이 끊겨도 탭을 열 때와 다시 연결될 때 한 번씩 새로 읽습니다.

## 댓글 옆 고객 숫자 (음성 방식·댓글터치 공통)

2026-10-21 학현님 요청: 청취 홈이나 댓글터치 판매를 시작할 때 고객별 총구매금액, 구매횟수, 약속미이행횟수를 PC에 담아 두고, 댓글이 올 때마다 찾아서 댓글 끝에 숫자로 붙입니다. PC와 판매 폰 모두 보여 줍니다.

**지금 상태:** PC 청취 홈 댓글 목록에는 이미 "구매 N회 · 누적 N원 · 미이행 N회" 배지가 있습니다(CustomerStatsBadge). 그런데 화면에 있는 댓글 100개가 각각 판매 기록 전체를 비슷한 닉네임 비교로 다시 훑고, 판매가 1건 생길 때마다 100개를 모두 다시 계산합니다. 판매 기록이 쌓일수록 방송 중 화면이 느려지고, 음성인식도 같은 브라우저에서 돌아서 함께 느려질 수 있습니다. 또 비슷한 닉네임까지 합쳐 세서 다른 사람의 숫자가 붙을 수 있습니다. 그래서 말씀하신 대로 시작할 때 표를 한 번 만들고 댓글마다 찾기만 하는 방식이 맞습니다.

### 동작

- **시작할 때 한 번:** "청취 시작"이나 "판매 시작"을 누르면 고객 숫자표를 만듭니다. PC는 페이지를 열 때 이미 이 판매자의 판매 전체, 미이행 표시, 정산·배송·입금 기록을 Supabase에서 받아 두므로, 새로 받는 것은 구매자 목록(틱톡 사용자 번호와 구매자 연결) 하나뿐입니다. 표는 PC 브라우저 저장소에 넣어 두고 시작할 때마다 새로 만듭니다. 댓글 도우미는 고치지 않습니다.
- **계산 규칙은 하나:** 판매 카드와 판매 상세 화면의 배지와 같은 규칙으로 계산해서, 어느 화면에서 보든 숫자가 같게 합니다.
- **댓글이 올 때:** 틱톡 사용자 번호로 먼저 찾고, 없으면 닉네임(공백 무시)이 정확히 같은 고객을 찾습니다. 비슷한 닉네임으로는 붙이지 않습니다. 다른 사람의 미이행이 잘못 붙으면 좋은 고객을 의심하게 되기 때문입니다. 닉네임을 바꾼 단골도 번호로 찾습니다. 같은 닉네임 고객이 둘 이상인데 번호로 못 찾으면 숫자 대신 "동명"만 붙입니다.
- **방송 중 갱신:** 판매가 저장되거나 취소되거나, 판매자가 미이행을 표시하면 그 고객 숫자만 바로 고칩니다. 화면에 이미 있는 그 고객 댓글의 숫자도 같이 바뀝니다.
- **판매 폰:** 폰은 표를 따로 받지 않습니다. PC가 댓글을 폰에 보낼 때 숫자를 붙여 보내고(직접 연결이든 예비 길이든), 숫자가 바뀌면 그 고객의 새 숫자를 한 번 더 보냅니다. 그래서 PC와 폰 숫자가 항상 같고, 폰이 판매 기록 전체를 내려받지 않아도 됩니다.
- 표에서 찾는 데는 댓글 1개당 1천분의 1초도 걸리지 않아서, 댓글이 몰려도 느려지지 않습니다.

### 표기

- 댓글 내용 끝에 작은 글씨로: 저요 · 12건/4회 45.5만 (지난 회차까지 방송 4번에 걸쳐 상품 12건, 합계 455,000원)
- 미이행이 있으면 빨간색으로 덧붙임: 저요 · 12건/4회 45.5만 · 미이행1
- 이번 회차에 이미 산 고객은 "오늘 2건", 처음 사는 고객은 "첫구매"
- 구매 이력이 없는 고객은 아무것도 붙이지 않습니다. 잡담 댓글이 깔끔하게 보입니다.
- 금액은 방송에서 말하는 단위(만원, 소수점 한 자리)로 씁니다. 숫자만 쓰면 어느 숫자가 무엇인지 헷갈려서 "건", "회", "만", "미이행" 같은 짧은 글자를 붙이는 것을 추천합니다.

### 세는 기준

- **총구매금액:** 지난 회차까지의 합계. 보류, 취소, 반품, 환불은 빼고, 지금 합계 규칙처럼 보이는 판매(서버 확인 필요, 서버 저장 대기 포함)는 넣습니다. 이번 회차는 "오늘 n건"으로 따로 보여 줍니다.
- **구매횟수:** 상품 건수와 구매한 방송 수를 "12건/4회"처럼 함께 보여 줍니다(2026-10-21 학현님 결정). 한 방송에서 여러 개를 사면 건수만 늘고 방송 수는 1회입니다.
- **약속미이행:** 방송 단위로 셉니다(2026-10-21 학현님 결정). 판매자가 미이행으로 표시한 방송, 그리고 지난 회차 중 취소·반품·환불, "노쇼"·"미입금" 메모, 취소된 정산서, 기한이 지난 미입금 정산서가 있는 방송을 1회로 셉니다. 한 방송에서 3개를 미입금해도 미이행 1입니다. 판매자가 그 방송을 미이행 아님으로 정했으면 자동 판정은 하지 않습니다(지금과 같음). 지금 배지는 자동 판정을 상품 건마다 세므로 이 부분을 고치고, 판매 카드와 상세 화면의 배지도 같은 기준으로 바뀝니다.
- **범위:** 이 판매자 계정의 고객만 셉니다. 다른 판매자의 고객 기록은 섞지 않습니다.
- 숫자는 판매자 화면(PC 청취 홈, 판매 폰)에만 보이고 전표에는 넣지 않습니다. 자동 캡처는 캡처 영역(틱톡 화면)만 찍으므로 숫자가 들어가지 않습니다.

## 실시간 댓글을 폰에 보내는 방법

**추천은 PC와 폰 직접 연결(WebRTC)이고, Supabase 실시간 채널은 연결용과 예비로 둡니다.** 직접 연결이 되면 댓글이 Supabase를 거치지 않아서, 판매자가 늘어도 Supabase 사용량이 거의 늘지 않습니다. 직접 연결이 안 될 때만 Supabase 채널로 받습니다(2026-10-21 학현님 질문 후 변경).

| 방법 | 지연 | Supabase 부담 | 폰이 LTE일 때 | 문제점 | 판단 |
| --- | --- | --- | --- | --- | --- |
| E. PC 브라우저와 폰 직접 연결(WebRTC) | 가장 빠름 | 연결할 때 수십 건만 | 통신사에 따라 직접 연결이 안 될 수 있음. 그때는 A로 자동 전환 | 만들 양이 조금 늘고, 두 길을 다 시험해야 함 | 추천(기본 길) |
| A. Supabase 실시간 방송(저장 없음) | 1초 이내 | DB 부담은 없고, 실시간 메시지가 댓글 수만큼 늘어남 | 됨 | 판매자가 늘면 메시지 수도 그만큼 늘어남 | 예비 길 + 연결용 |
| B. 폰이 PC 댓글 도우미에 직접 접속(같은 와이파이) | 가장 빠름 | 없음 | 안 됨 | 웹앱(https)에서는 브라우저가 http 집 안 주소 접속을 막음(PC 자신인 127.0.0.1만 예외). 도우미가 지금 PC 안에서만 열려 있어서, 외부에 열면 방화벽 설정, 보안 문제, 공유기 아이피 변경 문제 | 비추천 |
| C. 모든 댓글을 DB에 저장하고 폰이 읽기 | 1\~2초 | 댓글 수만큼 DB 쓰기 | 됨 | "구매·취소 댓글만 올린다" 규칙 위반 | 비추천 |
| D. 폰이 틱톡에 직접 연결 | 1초 이내 | 없음 | 됨 | Euler 서명 사용량이 PC와 폰을 합쳐 두 배가 됨, 서명 키를 폰에 넣어야 함, PC와 폰 댓글 순서가 어긋남 | 비추천 |

### 동작

- **보내는 쪽은 PC 라이브 청취 홈**입니다. 청취 홈은 지금도 댓글 도우미에게서 모든 댓글을 실시간으로 받고 있으므로, 받는 즉시 폰으로 내보냅니다. 전표와 캡처 때문에 어차피 이 화면이 켜져 있어야 하므로 새로 생기는 고장 지점이 없고, 판매자 PC의 댓글 도우미를 업데이트할 필요도 없습니다.
- **직접 연결 맺기:** 폰이 판매 화면을 열면 PC 청취 홈과 Supabase 채널로 연결 정보만 주고받습니다(수십 건). 그 뒤로 댓글은 PC에서 폰으로 바로 갑니다. 브라우저에 들어 있는 기능(WebRTC)이라 따로 설치할 것이 없고, 연결은 암호화되며, 방화벽 설정도 보통 필요 없습니다. 연결을 대신 이어 주는 중계 서버(TURN)는 비용 때문에 두지 않습니다. 폰을 PC와 같은 와이파이에 붙여 두면 직접 연결이 가장 잘 됩니다.
- **예비 길:** 직접 연결이 5초 안에 안 되거나 끊기면 자동으로 Supabase 채널로 받고, 뒤에서 직접 연결을 다시 시도합니다. 폰은 같은 댓글 번호를 한 번만 보여 주므로 길이 바뀌어도 댓글이 겹치거나 빠지지 않습니다. 폰 상단에는 지금 어느 길로 받는지(직접 / 예비)를 작게 표시합니다. 예비 길에서는 연결 신호도 사용량으로 세므로, 댓글이 신호를 겸하고 댓글이 없을 때만 5초마다 신호를 보냅니다.
- PC 탭이 두 개 열려 있으면 "판매 시작"을 누른 탭만 보냅니다.
- **댓글이 몰리면 여러 개를 한 묶음**으로 보냅니다. 댓글마다 순번을 붙여 폰이 빠진 댓글을 알 수 있게 합니다.
- **폰이 늦게 들어오거나 끊겼다 다시 붙으면** "다시 보내줘"를 보내고, 청취 홈이 가지고 있는 최근 댓글 500개를 받아 옵니다.
- **Supabase 채널은 비공개 채널**로 만들어, 같은 판매자 계정으로 로그인한 화면만 듣고 보낼 수 있게 합니다. 이를 위해 Supabase에 권한 규칙 1개를 추가합니다.

**사용량:** 직접 연결이 되면 댓글은 Supabase를 거치지 않고, 연결할 때 쓰는 수십 건만 실시간 메시지로 셉니다. 예비 길로 받을 때는 보내기 1건과 받는 화면마다 1건씩을 셉니다. 댓글 3,000개짜리 방송을 전부 예비 길로 받으면 약 6,000건이고, 하루 2번씩 한 달이면 판매자 1명당 약 36만 건입니다(댓글 수는 예시). 여러 판매자가 같은 Supabase를 쓰므로, 판매자 10명이 모두 예비 길로만 받으면 월 약 360만 건이 됩니다. Supabase 문서 기준 월 한도는 무료 플랜 200만 건, Pro 플랜 500만 건이고, 초당 한도는 무료 100건, Pro 500건입니다. 한도 수치 출처: [Realtime 메시지 사용량](https://supabase.com/docs/guides/platform/manage-your-usage/realtime-messages), [Realtime 한도](https://supabase.com/docs/guides/realtime/quotas).

웹앱으로 하므로 문자 앱 안에 숨겨진 판매관리 탭(방식 C를 전제로 만든 것)은 쓰지 않습니다.

## 판매 확정의 서버 경로와 "확인 대기"

서버(sales-api)에 **터치 판매 저장** 기능을 하나 새로 만듭니다. 기존 음성 판매 저장은 음성 가격 근거를 요구하고, 기존 상품 판매 저장은 상품 단가를 요구해서 둘 다 그대로는 맞지 않습니다.

### 폰이 보내는 것

- 작업 번호: 확정 버튼을 누른 순간 폰이 만드는 고유번호. 같은 번호로 두 번 와도 판매는 한 건만 생깁니다(기존 operations 표 방식 재사용).
- 회차, 고른 댓글 1개(틱톡 메시지 번호, 틱톡 사용자 번호·아이디, 닉네임, 내용, 시각)
- 금액(15000), 판매자가 누른 글자 그대로("1.5"), 수량, 현재 상품(있으면), 확정 시각

### 서버가 하는 일

1. 로그인한 판매자 계정의 요청인지, 회차가 진행 중인지 확인합니다.
2. 고른 댓글 1개를 댓글 표에 저장하고 구매자를 찾거나 만듭니다. 지금 구매 댓글을 올릴 때 쓰는 것과 같은 규칙(틱톡 사용자 번호가 같으면 같은 사람)을 씁니다. 저장하는 댓글은 판매가 있는 댓글뿐이라 "구매 댓글만 올린다" 규칙과 맞습니다.
3. 판매를 저장합니다. 상태는 **자동저장**, 출처는 이미 있는 값 **앱** (ANDROID\_COMMENTS), 근거는 "판매자 터치: 폰, 댓글, 입력값 1.5", 전표 상태는 출력 대기, 캡처는 대기입니다. 같은 처리 안에서 출력 작업도 하나 만듭니다. 출처 값을 새로 만들면 DB 제약을 바꾸는 작업이 필요한데, 이미 있는 "앱" 값은 라이브 청취 홈에도 "앱"으로 표시되므로 그대로 씁니다. 터치 판매인지는 근거 기록으로 구분합니다.
4. 판매 번호, 구매자의 이번 회차 합계를 폰에 돌려줍니다.

같은 댓글로 두 번째 판매를 확정하면 서버가 "이미 이 댓글로 판매됨"을 돌려주고, 폰은 \[추가 판매로 저장\] 버튼을 보여 줍니다. 한 번 "저요"하고 두 개를 사는 경우를 막지 않으려는 것입니다. AI 검사나 음성 근거 재확인은 하지 않습니다. 판매자가 직접 누른 것이 근거이기 때문입니다.

### "확인 대기"를 어디에 둘지

지금 판매 상태값은 자동저장, 수동수정, 확정, 보류, 취소 5가지뿐입니다(src/types/live.ts). "확인 대기"는 라이브 청취 홈 목록의 제목이고, 그 목록에는 이번 회차의 판매가 모두 나옵니다.

| 상태 표시 | 실제 저장 | 합계 포함 | 터치 방식에서 |
| --- | --- | --- | --- |
| 자동저장 | 상태값 | 포함 | 터치 판매의 기본 상태(추천) |
| 확정 | 상태값 | 포함 | 방송 후 일괄 검토에서 판매자가 확정 |
| 수동수정 | 상태값 | 포함 | 가격·구매자를 고친 뒤 |
| 보류 | 상태값 | 제외 | 터치에서는 쓰지 않음(판매자가 직접 골랐으므로) |
| 취소 | 상태값 | 제외 | 삭제했을 때 |
| 서버 저장 대기 | 동기화 표시(PENDING) | 포함 | PC에서 만든 판매에만 해당. 폰 판매는 서버에서 만들어지므로 해당 없음 |
| 서버 확인 필요 | 별도 표시 | 포함 | 음성 근거 재확인용이라 해당 없음 |

**추천:** 새 상태 "확인 대기"를 만들지 않고 자동저장으로 저장합니다. 새 상태를 만들면 구매자 합계, 판매내역 목록, 정산서, 문자 인박스, 입금 대조까지 모두 새 상태를 알게 고쳐야 하고, 하나라도 빠지면 합계가 틀어집니다. 자동저장이면 구매자 번호가 붙은 보통 판매라서 합계, 문자 연결, 정산, 배송비 수동 지정이 그대로 작동합니다.

## 전표 출력과 자동 캡처 (4초 + 틱톡 지연)

전표와 캡처는 **PC 브라우저**(라이브 청취 홈)가 맡습니다. 캡처에 필요한 틱톡 화면 공유가 브라우저 안에만 있고, 전표도 지금 음성 방식과 같은 길(브라우저 → 댓글 도우미 → 프린터, 구매자+금액만)을 그대로 쓸 수 있기 때문입니다.

1. 폰에서 확정 → 서버에 판매 저장.
2. PC 브라우저는 이미 판매 표의 실시간 변경을 듣고 있어서(SalesContext의 Realtime 구독) 보통 1초 안에 새 판매를 받습니다.
3. 터치 판매이고 현재 회차이면 출력 대기열에서 그 판매의 출력 작업을 가져온 뒤 **즉시 전표 출력**을 요청하고 결과(출력됨/실패)를 판매에 기록합니다.
4. 폰에서 확정한 시각부터 **4초 + 틱톡 지연 뒤 화면 캡처**를 하고(아래 "틱톡 화면 지연 보정"), 서버 저장소에 올려 그 판매의 이미지1로 붙입니다. 폰의 판매내역에도 썸네일이 뜹니다.

세부 규칙입니다.

- **이 방식에서만** 판매 후 자동 캡처를 켭니다. 음성 방식의 "판매 후 자동 캡처 없음, 캡처하세요 멘트와 ±10초 짝짓기" 규칙은 바꾸지 않습니다. 판매 1건에 캡처 1장이라는 원칙은 같습니다.
- 캡처 영역은 지금 "캡처 영역 설정"에 저장된 영역을 그대로 씁니다. 4초는 설정에서 2\~10초로 바꿀 수 있게 하고, 틱톡 지연은 그 위에 따로 더합니다.
- 캡처하기 전에 다음 판매가 또 들어오면 판매마다 타이머가 따로 돌아 각각 캡처합니다.
- **전표가 두 번 나오지 않게** 서버에 이미 있는 출력 대기열(print\_jobs)을 씁니다. 터치 판매를 저장할 때 서버가 출력 작업도 하나 만들고, PC는 이 작업을 "내가 출력함"으로 먼저 가져간 뒤에 출력합니다. PC 탭이 두 개거나 PC가 두 대여도 한 번만 출력되고, 캡처도 그 작업을 가져간 탭만 찍습니다. 대기열과 "가져가기·완료 보고" 기능은 코드에 이미 만들어져 있고, 아직 누구도 쓰지 않을 뿐입니다.
- **PC가 잠시 끊겼다 돌아오면** 대기열에 남은 출력 작업을 가져가 전표를 출력합니다. 단, 캡처할 시각이 PC가 보관하는 최근 30초 장면보다 더 지난 판매는 캡처하지 않고 "캡처 없음"으로 표시합니다. 그때는 화면에 이미 다른 장면이 나오기 때문입니다.
- 도우미에는 브라우저 없이 대기열을 직접 읽는 출력 작업자(server/cloudPrintWorker.js)도 있지만 연결돼 있지 않습니다. 첫 버전은 브라우저가 출력하고, 브라우저를 닫아도 전표가 나와야 한다면 다음 단계에서 이것을 켭니다(그때는 캡처만 브라우저가 함).

### 틱톡 화면 지연 보정

2026-10-21 학현님 질문: 판매자 카메라 화면은 틱톡에 몇 초 늦게 나옵니다. 지연이 5초인데 확정 4초 뒤에 찍으면, 판매자가 보여 주는 옷이 틱톡 화면에 뜨기 전 장면이 찍힐 수 있습니다.

**왜 터치 방식에서 생기나:** PC는 라이브가 재생되는 크롬 탭을 화면 공유로 받아 캡처합니다(screenCaptureService가 탭 화면과 탭 소리를 함께 받음). 음성 방식은 기본 설정(방송 탭 소리)에서 "캡처하세요" 소리도 같은 탭에서 화면과 똑같이 늦게 들어오므로 둘이 맞습니다. 터치 방식은 폰 확정이 실제 시각에 일어나고 탭 화면만 늦게 따라오므로 지연만큼 어긋납니다. 음성 방식을 "내 마이크"로 쓸 때도 같은 차이가 있어서, 나중에 같은 보정을 쓸 수 있습니다.

**캡처 시각 = 폰에서 확정한 시각 + 4초(판매자가 상품을 보여 주는 시간) + 틱톡 지연.** 지연이 5초면 확정 9초 뒤, 8초면 12초 뒤 장면을 찍습니다. PC가 판매를 받은 시각이 아니라 폰의 확정 시각을 기준으로 하고, 폰과 PC의 시계 차이는 직접 연결로 주고받는 신호로 맞춥니다(오차 0.1초 안팎).

- **지연 자동 측정(추천):** 판매 폰이 마이크로 판매자 목소리를 듣고, 소리 크기 숫자만(1초에 20개) 직접 연결로 PC에 보냅니다. 녹음하지 않고 소리 자체도 보내지 않습니다. PC는 공유 중인 틱톡 탭 소리에서 같은 숫자를 만들고, 두 패턴이 몇 초 어긋나는지 10초마다 다시 찾습니다(1\~20초 사이). 패턴이 뚜렷하게 맞을 때만 값을 바꾸고, 최근 3번의 가운데 값을 씁니다. 라이브 중 판매자는 거의 계속 말하므로 자주 갱신되고, 방송 중 지연이 늘거나 줄어도 따라갑니다. PC 상태 줄에 "틱톡 지연 5.2초 자동"으로 보입니다.
- **못 잴 때:** 화면 공유에 탭 소리가 빠졌거나 틱톡 탭 소리가 꺼짐, 폰 마이크를 허용하지 않음, 예비 길(Supabase)로 연결 중(사용량 때문에 소리 숫자는 직접 연결로만 보냄), 판매자가 한동안 말하지 않음. 이때는 마지막으로 잰 값(지난 방송에서 잰 값도 PC에 기억)을 쓰고, 그것도 없으면 청취 홈에서 정한 값(기본 6초, 0\~20초)을 씁니다. 상태 줄은 "틱톡 지연 6초 설정값"으로 바뀝니다. 송출 프로그램의 미리보기 창을 캡처 영역으로 쓰는 판매자는 지연이 거의 없으므로 0초로 정합니다.
- **최근 30초 장면 보관:** PC는 캡처 영역을 1초에 2장씩 작게 찍어 최근 30초만 메모리에 둡니다(약 3MB). 판매를 조금 늦게 받거나 그사이 지연 값이 바뀌어도 목표 시각에 가장 가까운 장면을 꺼낼 수 있습니다.
- **판매 1건에 사진 1장 유지:** 목표 시각 장면 1장만 판매에 붙고 서버에 올라갑니다. 같은 때 2초 전과 2초 후 장면도 예비로 꺼내 두지만, PC 브라우저에만 24시간 보관하고 서버에 올리지 않으며 판매 사진으로 세지 않습니다. 판매자가 상품을 늦게 보여 줘서 빗나갔으면 판매 상세의 \[다른 장면\]에서 예비 장면을 누릅니다. 그 장면이 올라가고 원래 사진은 지워지므로, 바꿔도 판매당 1장입니다. 폰에서는 PC가 직접 연결로 예비 장면 썸네일을 보내 주고, 예비 길로 연결 중이면 PC에서만 바꿀 수 있습니다.
- **폰 마이크 허용:** 폰에서 판매 화면을 처음 열 때 마이크 허용을 한 번 묻습니다. 거부해도 판매, 전표, 캡처는 그대로 되고, 지연만 지난 값이나 설정값을 씁니다. 안드로이드는 마이크를 쓰는 동안 화면 위에 표시를 띄우고, 화면이 꺼지면 측정도 멈췄다가 다시 켜지면 이어 갑니다.

## 실패 상황과 대응

원칙은 두 가지입니다. 폰에서 확정한 판매는 어떤 경우에도 사라지지 않고, 같은 확정이 두 건으로 저장되지 않습니다. 두 가지 모두 확정 순간 만든 작업 번호로 지킵니다.

| 상황 | 폰에 보이는 것 | 처리 |
| --- | --- | --- |
| 확정 버튼을 두 번 빠르게 누름 | 한 건만 저장 | 첫 터치에 버튼 잠금 + 같은 작업 번호는 서버가 한 번만 처리 |
| 폰 인터넷이 확정 순간 끊김 | "보내는 중 1건" | 브라우저 저장소에 보관했다가 연결되면 같은 작업 번호로 자동 재전송. 페이지를 닫았다면 다시 열 때 전송. 서버에 도착하기 전에는 전표·캡처도 없음 |
| 서버 응답이 3초 넘게 늦음 | "저장 확인 중" | 같은 작업 번호로 다시 물어봄. 실제로는 저장됐는데 응답만 늦은 경우도 중복 없음 |
| 폰 화면이 잠기거나 문자 앱 등 다른 화면으로 넘어감 | 돌아오면 "댓글 다시 받는 중" | 연결(직접·예비)이 끊겼다 다시 붙으면 최근 댓글 500개와 판매 목록을 다시 받음 |
| PC와 폰 직접 연결이 안 되거나 방송 중 끊김 | 상단 표시가 "직접"에서 "예비"로 바뀜 | 5초 안에 Supabase 채널로 자동 전환하고, 뒤에서 직접 연결을 다시 시도. 빠진 순번은 다시 받아 채우고 같은 댓글은 한 번만 보여 줌. 판매 저장, 전표, 캡처는 영향 없음 |
| 폰 로그인이 풀림 | 로그인 화면 | 자동 로그인이면 다시 묻지 않음. 보내는 중인 판매는 로그인 후 전송 |
| PC 브라우저가 꺼짐 / 잠듦 | "PC 연결 끊김 · 새 댓글·전표 대기" | 이미 보이는 댓글로 판매 저장은 됨. 새 댓글은 PC가 돌아와야 다시 들어옴. PC가 돌아오면 대기 전표 출력, 30초 지난 판매는 "캡처 없음" |
| 댓글 도우미가 꺼짐 | "댓글 수신 끊김 n초" | 폰에 새 댓글 없음, 전표도 안 나옴. PC에 경고. 도우미가 다시 켜지면 대기 전표 출력 |
| 틱톡 연결이 끊김 | "댓글 수신 끊김" | 도우미가 지금처럼 자동 재연결. 급하면 검색으로 이전 댓글을 찾거나 PC에서 수동 등록 |
| 프린터 오류 | "전표 실패" + \[다시 출력\] | 판매는 그대로, 전표 상태만 실패. PC와 폰 모두에서 재출력 가능 |
| 화면 공유가 안 돼 있음 | "캡처 없음" | PC가 화면 공유를 다시 하라고 알림. 판매와 전표는 정상 |
| 틱톡 지연을 잴 수 없음 (탭 소리 공유 꺼짐, 폰 마이크 거부, 예비 길 연결 중) | 변화 없음 (PC 상태 줄에 "틱톡 지연 6초 설정값") | 마지막으로 잰 값, 없으면 설정값(기본 6초)으로 찍음. 빗나가면 판매 상세 \[다른 장면\]에서 2초 전·후 장면으로 바꿈 |
| 방송 중 틱톡 지연이 갑자기 늘거나 줄어듦 | 변화 없음 | 10초마다 다시 재서 따라감. 최근 30초 장면을 들고 있어서 막 확정한 판매도 바뀐 값으로 장면을 꺼냄 |
| 회차가 끝난 뒤 폰에서 확정 | "판매 중인 회차가 없습니다" | 서버가 거부. 연결이 끊겨 있다가 회차 종료 후 도착한 판매는 어느 회차에 넣을지 폰에서 고르게 함 |
| 댓글이 너무 빨라 다른 사람을 누름 | 하단 바에 고른 사람이 크게 보임 | 확인 전에 \[취소\]. 확정 후에는 판매내역에서 구매자 변경 |
| 같은 닉네임이 두 명 | 닉네임 아래 틱톡 아이디 | 닉네임이 아니라 누른 댓글의 틱톡 사용자 번호로 구매자 연결 |

## 관리자 화면: 판매 폰 연결 현황

2026-10-21 학현님 요청: 직접 연결과 예비 길 사용, 끊김과 장애를 관리자가 볼 수 있게 합니다. 모든 판매자가 같은 Supabase를 쓰므로, 예비 길을 많이 써서 사용량을 올리는 판매자도 여기서 찾습니다. 지금 관리자 메뉴의 음성인식 사용량(stt\_usage\_logs 표와 관리자 전용 조회 기능)과 같은 구조로 만듭니다.

### PC가 서버에 남기는 것

- 방송 시작과 끝: 판매방식(음성 / 댓글터치), 판매 폰 수
- 연결 바뀜: 직접 → 예비, 예비 → 직접, 폰 접속과 끊김(시각, 이유)
- 장애: 댓글 도우미 끊김, 틱톡 끊김, 전표 실패, 캡처 없음, 폰에서 "보내는 중"으로 늦게 도착한 판매
- 5분마다 요약: 직접 / 예비로 보낸 댓글 수, 예비 길 메시지 수, 직접 연결 비율, 틱톡 지연(평균·최대)과 지연을 못 잰 시간. PC가 갑자기 꺼져도 마지막 요약까지는 남습니다.
- 방송 1번에 수십 건 정도라 부담이 거의 없습니다. 댓글 내용과 고객 정보는 남기지 않습니다.

### 관리자 메뉴에 보이는 것

- **지금 방송 중:** 판매자별 판매방식, 폰 연결(직접 / 예비 / 끊김), 마지막 신호 시각
- **판매자별 최근 방송:** 직접 연결 비율, 예비 길 시간, 전환 횟수, 장애 건수. 예비 길만 쓰는 판매자는 표시해서, 폰을 PC와 같은 와이파이에 붙이도록 안내할 수 있게 합니다.
- **이번 달 Supabase 실시간 메시지 추정치:** 한도(무료 200만 건, Pro 500만 건) 대비 몇 %인지 보여 주고, 80%를 넘으면 경고합니다. 이 숫자는 앱이 센 추정치이고, 정확한 실제 사용량은 Supabase 관리 화면의 사용량(Usage)에서 봅니다.
- 판매자에게는 지금처럼 상태 줄만 보여 주고, 기록과 통계는 관리자만 봅니다.

## 수정, 삭제, 취소

전표는 확정 즉시 나가므로 "되돌리기"는 따로 두지 않고, 모든 수정은 저장된 판매를 고치는 방식으로 합니다. 폰과 PC 어느 쪽에서 고쳤든 나머지 한쪽에 바로 보입니다.

| 하고 싶은 것 | 방법 | 판매 상태 | 전표 |
| --- | --- | --- | --- |
| 가격 고치기 | 판매내역 → 항목 → \[가격 수정\], 같은 키패드(1.5 입력) | 수동수정 | "수정 전표 출력" 체크(기본 켜짐) |
| 구매자 바꾸기 | \[구매자 변경\] → 댓글 목록이나 검색에서 다시 선택 | 수동수정 | "수정 전표 출력" 체크(기본 켜짐) |
| 잘못 들어간 판매 지우기 | \[삭제\] → "013 하니 15,000원을 삭제할까요?" | 취소(기록은 남기고 합계에서 빠짐) | 출력 없음 |
| 전표만 다시 | \[전표 다시 출력\] | 그대로 | 같은 내용 재출력 |
| 캡처가 잘못 찍힘 | \[다른 장면\] → 2초 전·후 장면 중 하나로 바꿈. 또는 \[캡처 다시 찍기\] → 상품을 다시 보여 주면 PC가 틱톡 지연만큼 기다렸다 찍어 교체. 어느 쪽이든 판매당 1장 | 그대로 | 없음 |

- 삭제는 표에서 완전히 없애지 않고 "취소" 처리합니다. 나중에 "왜 없어졌는지" 확인할 수 있게 수정 이력(누가, 언제, 무엇을)을 남깁니다.
- 판매자가 이미 정산서나 입금 확인에 쓴 판매를 고치면 지금 PC에서 고칠 때와 같은 경고를 보여 줍니다.
- 구매자를 바꾸면 이전 구매자와 새 구매자의 합계가 둘 다 바로 다시 계산됩니다.

## 구현 단계 제안

여섯 단계로 나누고, 단계마다 따로 PR을 올립니다. 학현님이 허락하실 때까지 코드는 쓰지 않고, 합치기와 배포도 "합쳐라 / 배포해라"를 받은 뒤에만 합니다. 웹앱이므로 안드로이드 빌드와 Play 업로드는 없습니다. 음성 방식의 판매 판단은 어느 단계에서도 바뀌지 않아야 하므로, 기존 음성 테스트가 모두 통과하는 것을 단계마다 확인합니다.

1. **고객 숫자표:** PC 청취 홈 댓글 옆 숫자를 시작할 때 만든 표에서 찾게 바꾸고, 틱톡 사용자 번호로 찾기와 방송 중 갱신을 넣습니다. 지금 음성 방식에도 바로 도움이 되므로 먼저 따로 올립니다. 배포: Vercel.
2. **서버:** sales-api에 터치 판매 저장(중복 방지, 댓글 1개 저장, 출력 작업 생성)을 추가하고, 실시간 비공개 채널(직접 연결 맺기와 예비 길에 씀) 권한 규칙 1개와 관리자용 연결 기록 표·조회 기능을 DB에 넣습니다. 지금 db push가 안 되므로 DB 변경은 손으로 적용합니다. 배포: sales-api.
3. **PC 라이브 청취 홈:** 판매방식 옵션, "판매 시작"(음성 없이 화면 공유), 받은 댓글 전달과 재전송(직접 연결 우선, 안 되면 Supabase 채널로 자동 전환, 고객 숫자를 붙여 보냄), 출력 대기열에서 가져와 출력, 확정 + 4초 + 틱톡 지연 캡처(지연 자동 측정, 최근 30초 장면 보관, 예비 장면 2장), 연결 상태 줄, 연결 기록 남기기, "판매 폰 열기" QR.
4. **폰 판매 화면(웹):** 같은 웹 프로젝트에 가벼운 새 페이지(판매하기, 가격 입력, 판매내역), 댓글 받기(직접 연결 우선, 안 되면 예비 채널, 같은 댓글은 한 번만)와 고객 숫자 표시, 보내는 중 보관, 화면 켜두기, 틱톡 지연 측정용 소리 크기 보내기(마이크 허용 시), \[다른 장면\] 고르기, 홈 화면 추가용 앱 정보.
5. **관리자 화면:** 관리자 메뉴 "판매 폰 연결 현황". 3, 4, 5는 함께 Vercel(voice-pin-web, voice-pin-anti)로 배포합니다.
6. **리허설:** 실제 방송 전에 시험 방송으로, 문자 앱 폰에서 댓글 지연(와이파이와 LTE 각각에서 직접 연결이 되는지), 직접 연결을 막았을 때 예비 길로 바뀌는지, PC와 폰의 고객 숫자가 같은지, 전표, 캡처 시각(손뼉을 쳐서 PC에 보이는 틱톡 지연이 실제와 맞는지, LTE처럼 지연이 긴 환경에서도 옷이 보이는 장면이 찍히는지), 폰 인터넷 끄기, 폰 화면 잠금, PC 끄기를 확인하고, 관리자 화면에 기록이 남는지 봅니다.

테스트로 남길 것: 가격 변환(1.5, 0.8, 3, 15000, 150 등), 같은 작업 번호 재전송 시 1건만 저장, 더블탭, 같은 댓글 두 번째 판매, 회차 종료 후 도착, 탭 두 개에서 출력 1번만, PC 재연결 후 대기 전표 출력과 "캡처 없음" 표시, 폰 화면 잠금 뒤 댓글 다시 받기, 직접 연결이 끊겨 예비 길로 바뀔 때 댓글이 겹치거나 빠지지 않음, 고객 숫자(틱톡 번호로 찾기, 닉네임을 바꾼 고객, 동명이인, 비슷한 닉네임에는 안 붙음, 판매·취소 뒤 갱신, 판매 카드 배지와 같은 숫자), 틱톡 지연 측정(소리 크기 패턴을 몇 초 밀어도 그 초를 찾음, 잡음이나 무음이면 값을 바꾸지 않음, PC 스피커 소리가 섞여도 0초로 잘못 잡지 않음), 캡처 시각(폰 확정 시각 기준, 폰과 PC 시계 차이 보정, 값이 없을 때 설정값), 예비 장면(판매 사진으로 세지 않음, 바꿔도 판매당 1장).
