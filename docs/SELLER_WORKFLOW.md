# 판매자별 판매방식 분석·적용

## 범위

판매자마다 함수를 복사하거나 AI가 만든 코드를 실행하지 않는다. 공통 결정 엔진과 검증된 JSON 프로필을 사용한다. 관리자 분석 화면, 서버 재생 검증, 실제 라이브 처리가 같은 `replaySalesWorkflow`를 사용한다.

현재 지원하는 공통 모듈은 다음과 같다.

- `DIRECT`: 저요·ㅈㅇ·제가 살게요 등 구매 신청 후 판매자 배정.
- `ORDER_CODE`: 판매자가 먼저 상품 주문번호를 안내하고 고객이 번호로 신청하는 방식.
- 두 모듈 모두 여러 고객 호명, 댓글 닉네임의 유일 대조, 방송 가격·수량·알려진 재고를 처리한다.
- 프로필에는 구매/확정/제외 표현, 기본 수량, 신청 유효 시간, 상품 문맥 유효 시간을 저장한다. 정규식이나 실행 코드는 저장하지 않는다.

옵션 주문은 자동으로 추측하지 않고 확인 대상으로 남긴다. 경매, 옵션별 재고, 묶음 배정 등 기존 프로필로 표현할 수 없는 새 방식은 AI 보고서에 `NEW_MODULE_REQUIRED`로 남긴다. 관리자는 이 상태를 운영 적용할 수 없다. 필요한 공통 모듈을 개발하고 회귀 사례를 추가한 뒤 다시 분석·검증해야 한다. 모든 가능한 판매방식을 현재 두 모듈이 처리한다고 보장하는 구조가 아니다.

## 관리자 절차

1. 관리자 메뉴의 **판매자 판매방식 분석**에서 등록 판매자를 선택하거나 미등록 판매자를 분석한다. 미등록 판매자는 보고서 작성까지 가능하고 운영 적용에는 등록 계정 연결이 필요하다.
2. TikTok 방송 아이디와 관리자가 알고 있는 판매방식을 입력한다. 기존 라이브 청취·댓글 수집이 꺼진 상태에서 **방송 청취 시작**을 누르고 해당 방송 탭의 오디오를 새로 공유한다. 일시정지된 이전 탭 공유는 교체한다.
3. 분석 청취는 별도 STT/오디오 콜백을 사용한다. 댓글 도우미의 판매 회차 클라우드 게시를 끄고 자료만 수집하므로 판매·전표를 생성하지 않는다. 청취 종료, 탭 오디오 종료, STT 실패, 페이지 이탈 시 자원을 해제한다.
4. 자료를 저장하고 AI 분석을 요청한다. 관리자 설명과 실제 방송 자료를 함께 제공한다. 관리자 AI 설정의 우선 슬롯을 먼저 사용하고 4초 내 유효 응답이 없으면, 대체 사용이 켜져 있는 경우 두 번째 슬롯을 사용한다. 대체 슬롯은 자체 운영 20초, 클라우드 15초로 제한한다. 서버에서 접근할 수 없는 PC_HELPER 전용 슬롯은 명확한 실패로 기록하고 대체한다.
5. 보고서의 판매 흐름, 구매 표현, 확정 표현, 가격, 닉네임, 예외, 미확인 사항, 추가 모듈 요구를 검토한다. 하단 대화에 수정·추가 요청을 입력하면 이전 보고서와 새 요청을 참고하여 새 보고서 버전을 만든다. 각 시도의 질문·응답·실패를 확인할 수 있다.
6. 시각이 포함된 수집 자료로 재생 검증한다. 원본과 확정 후보·보류·누락·오감지를 비교한 뒤 검증 확인을 저장하고 최종 승인한다. 참고용 텍스트만으로는 운영 승인을 위한 재생 검증을 할 수 없다. 시각이 포함된 분석 JSON을 불러오거나 다운로드할 수 있다.
7. 승인한 버전을 **관찰 모드**로 적용한다. 실제 방송에서는 기존 판매 처리를 유지하고 새 설정의 후보만 별도로 저장한다. 실제 관찰 결과를 확인한 뒤 **운영 적용**한다.
8. 문제 발생 시 **이전 버전으로 복귀**, 최초 적용에서는 **기본 처리로 복귀**한다. 분석·승인·프로필·관찰 이력을 삭제하지 않는다.

자료 수정 또는 재분석은 이전 승인을 무효화한다. 오래된 화면이나 보고서로 승인/적용할 수 없도록 서버 revision을 비교한다. 등록 판매자 A의 분석을 B로 바꾸는 것은 거부하고 새 분석을 사용한다.

## 라이브 처리와 안전장치

- 새 회차 시작 시 운영 프로필을 서버에서 고정한다. 관리자 설정이 방송 중 바뀌어도 해당 회차는 고정된 버전을 유지하며 새 회차부터 변경된다. 같은 회차를 이어가면 같은 버전을 쓴다.
- 프로필이 없는 판매자는 기존 처리를 유지한다. ACTIVE 프로필에서는 기존 자동 판매 추출기를 중복 실행하지 않는다. STT 전사 로그 자체와 음성 수정 명령은 계속 동작한다.
- 예: `댓글에 1번 입력, 0.5입니다` → 햇살 `1`, 마가린 `1번이요`, 쥬쥬 `1번저요` → `햇살언니, 마가린언니, 쥬쥬언니께 드릴게요`이면 각 고객 1개·5,000원이다.
- 댓글의 실제 닉네임과 계정이 기준이다. 축약·STT 오타가 유일하게 연결되면 원래 닉네임으로 저장한다. 닉네임 충돌이나 구매 댓글 부재는 임의로 선택하지 않는다.
- 숫자만 있는 댓글은 먼저 안내된 주문번호에 맞을 때만 구매 신청이다. 소수 가격을 주문번호로 읽지 않는다. 재사용된 번호는 별도 상품 문맥으로 분리한다.
- 소수 가격은 만원 단위로 해석한다. 가단·가슴단면·총장·기장·번호는 가격이 아니다. 다음 상품으로 전환하면 이전 가격을 상속하지 않는다. 가격이 뒤따르면 70초 안의 같은 상품 배정을 보완하고 동일한 판매 후보를 갱신한다.
- 해당 상품의 재고를 판매자가 안내했을 때만 초과를 검사한다. 한 발화의 여러 구매자 배정이 알려진 재고를 초과하면 그 배정 묶음을 함께 보류한다. 재고를 말하지 않았다면 임의 재고를 만들거나 이를 이유로 확정을 막지 않는다.
- 질문·부정·조건부·과거 언급·치수 측정·보여주기는 배정으로 확정하지 않는다. 옵션, 금액 미상, 계정 충돌, 알려진 재고 초과는 보류 사유를 표시한다.
- 번호 주문 보류도 승인 프로필과 실제 번호 댓글을 근거로 기존 AI 검토에 연결한다. AI 결과는 판매자 확인용이며 알려진 재고 충돌이나 계정 불확실성을 임의로 해소하지 않는다.
- 자동 확정은 서버에 보관한 원본 발화와 실제 댓글을 다시 재생하여 검증한다. 클라이언트가 주장하는 가격·닉네임·프로필 스냅샷만 믿지 않는다.
- 서버 RPC는 회차 잠금으로 재고와 구매 댓글 중복 사용을 검사한다. 같은 요청의 재전송은 기존 결과를 반환한다. 인쇄는 서버 저장 확인 후 기존 전표 흐름을 따른다.
- 이미 받은 최종 발화의 처리 대기는 일반 청취 중지로 폐기하지 않는다. 계정 변경은 폐기한다. 처리 실패가 STT 로그를 끊지 않으며 라이브 화면에 저장 대기 오류를 표시한다.

## 용량과 확장

관리자 페이지는 lazy chunk로 분리한다. 일반 판매자에게는 선택된 프로필 하나만 전달하고 전체 분석 이력을 보내지 않는다. 관리자 목록 조회도 원본 자료·대화·보고서가 빠진 요약만 조회한다.

프로필 표현은 종류별 30개·2~80자, 수량 1~99, 신청 시간 10~300초, 상품 문맥 30~1,800초로 제한한다. 런타임은 최신 상품/신청 구간만 재생하고 서버 댓글 조회도 동일 구간으로 한정한다. 관찰 저장은 약 30초마다 및 청취 종료 시 실행하며 방송당 최근 후보 500개를 유지한다. 분석 자료는 댓글 2,000개·발화 500개·500KB, 요청 4,000자, 보고서 20버전까지이다. 더 긴 자료는 구간을 나눈다.

새 방식 확장 순서: 실제 사례 수집 → AI가 필요한 모듈/미확인 사항 보고 → 공통 타입·엔진 모듈 개발 → 해당 사례와 기존 사례 회귀 테스트 → 재분석 → 재생 검증 → 승인 → 관찰 검증 → 운영 적용. 판매자마다 코드 분기를 누적하지 않는다.

## 저장소와 배포 순서

아래 마이그레이션을 순서대로 적용한 뒤 sales-api, 웹앱 순서로 배포한다.

- `202610020001_seller_workflow_analysis.sql`: 분석·요약·프로필·적용·관찰·회차 고정 테이블, 관리자 CAS RPC, sales 근거 컬럼.
- `202610020002_workflow_voice_commit.sql`: 원자적인 프로필 음성 판매 적재 RPC.

새 테이블은 RLS를 켜고 anon/authenticated 직접 접근을 차단한다. 관리자 분석/적용은 USER + ADMIN 역할이 필요하며, 회차 고정/관찰은 기존 판매 API 권한 검사를 따른다. 신규 기능은 테이블이 없는 서버에 웹앱부터 배포하지 않는다.

검증: `npm test`, `npm run build`, `npx deno check --no-lock --no-check=remote supabase/functions/sales-api/index.ts`.

DB 테스트는 개발 전용 PGlite에서 실제 신규 SQL을 실행하여 CAS, 관찰 승인, 회차 버전 고정, 기본 복귀, 중복·재고 원자성을 확인한다. 운영 DB나 운영 판매 기록을 수정하지 않는다. `test/fixtures/seller-analysis-preview`는 운영 서버에 연결하지 않는 실제 관리자 컴포넌트의 가상 자료 UI 검증 화면이다.
